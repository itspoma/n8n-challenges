## Ваша вправа з GraphQL у n8n

У цій редакційній вправі вам потрібно спроєктувати процес n8n для GraphQL, який збирає повну колекцію типу connection, перевіряє її записи й дозволяє одну нешкідливу мутацію в тестовому середовищі лише після виконання всіх передумов. GraphQL.org зазначає, що відповіді можуть містити одночасно data й errors, тому самої успішної HTTP-відповіді недостатньо для підтвердження готовності. Рекомендації щодо HTTP спираються на проєкт специфікації, а поведінка кодів стану залежить від медіатипу відповіді та реалізації. Перевіряйте тіло відповіді незалежно від успішності HTTP.

Результат роботи — ваш процес і свідчення його виконання для коректного та навмисно помилкових сценаріїв тестового стенда. Це запропонована вправа з проєктування, а не готовий до імпорту процес чи виконана й перевірена інтеграція. Надана документація не підтверджує сумісність з усіма версіями або редакціями n8n.

На нашу думку, корисна навчальна мета — пояснити, чому запис було дозволено або заблоковано, а не просто забезпечити виконання успішного сценарію.

## Підготуйте контрольований тестовий стенд і явні вхідні дані

![У лотку тестового стенда GraphQL лежать записи, стрічка курсора, ключ доступу та руків’я скидання.](/blog/uk/article-888d4706-a258-4a12-9d12-cad594ee6f71/3ccc529bca2e966fee4c18d238b660af4a9b4ed12722e38bdbff3e644af4a304.webp)

Стенд надає контрольовані записи, параметри доступу, поведінку пагінації та процедуру скидання.

Почніть із наявного середовища n8n і підготовленого, доступного тестового стенда GraphQL. Встановлення та розгортання не входять до цієї вправи. Apollo описує резолвери як функції, що заповнюють поля схеми; отже, навмисно підібрані відповіді резолверів можуть стати основою запропонованого стенда. Наведений нижче контракт є редакційною пропозицією: перед побудовою попросіть власника стенда надати відповідні операції схеми та сценарії, які можна вибирати.

Використайте ці запропоновані вхідні дані. До фінальної тестової гілки процес має лише читати дані. Обмежте пагінацію однією колекцією connection; вкладені колекції, змінні набори даних, авторизація у робочому середовищі, повторні спроби та ідемпотентність мутацій не входять до цієї вправи.

**Пропонований контракт тестового стенда, який слід узгодити до початку**

| Вхідні дані | Пропонований контракт |
| --- | --- |
| Параметри підключення | Кінцева точка, метод автентифікації та облікові дані тестового середовища |
| Сигнатура запиту | records(first: Int!, after: String): RecordConnection! |
| Структура connection | nodes { id name }; pageInfo { hasNextPage endCursor } |
| Очікувані записи | Ідентифікатори A, B і C, кожен із непорожнім ім’ям |
| Сигнатура мутації | markReviewed(recordIds: [ID!]!): ReviewResult! |
| Результат мутації | accepted: Boolean! і recordIds: [ID!]! |
| Засоби керування | Вибір сценарію, журнал мутацій і процедура скидання |
| Сценарії | Коректні дані, часткові помилки, відсутнє ім’я та повторений курсор |

Sources: [Resolvers](<https://www.apollographql.com/docs/apollo-server/data/resolvers>), [GraphQL](<https://spec.graphql.org/September2025/>), [Pagination | GraphQL](<https://graphql.org/learn/pagination/>)

## Побудуйте запит і збережіть його відповідь

![Два конверти відповідей GraphQL містять коректні записи або записи разом із фрагментом помилки.](/blog/uk/article-888d4706-a258-4a12-9d12-cad594ee6f71/cab312f5729a48e0cd40628f62a2aae0c820157de4aa413fa3c27ac74431206b.webp)

На вигляд успішна доставка все одно може містити помилки в тілі відповіді.

У цьому прикладі GraphQL у n8n використайте [вузол HTTP Request](<https://n8n-challenges.app/uk/blog/vprava-z-vuzlom-http-request-u-n8n-marshrutyzatsiya-vidpovidey-i-obmezhennya-opytuvannya>), щоб надіслати JSON POST із query та variables. Документація n8n описує параметри пагінації в тілі POST і вирази для динамічних значень. Конкретні поля нижче належать запропонованому стенду, а не кожному API GraphQL.

Використайте текст запиту query ReadRecords($first: Int!, $after: String) { records(first: $first, after: $after) { nodes { id name } pageInfo { hasNextPage endCursor } } }. Почніть зі значень змінних first = 2 та after = null. Зберігайте повну структуру відповіді, зокрема data й errors.

GraphQL.org розрізняє помилки запиту, за яких data відсутнє, і помилки виконання, які можуть супроводжувати часткові дані. Рекомендації з усунення несправностей радять перевіряти масив errors у тілі відповіді та сумісність зі схемою. У цій вправі фіксуйте будь-який непорожній масив errors як збій, навіть якщо відповідь містить корисні записи.

Якщо ви планували використати вузол GraphQL у n8n, у цій вправі зосередьтеся на HTTP Request, щоб повна структура відповіді та змінні продовження залишалися явними.

## Реалізуйте пагінацію GraphQL у n8n із фіксацією збоїв

![Лотки сторінок GraphQL рухаються вздовж стрічок курсорів, а храповий фіксатор зберігає виявлений збій.](/blog/uk/article-888d4706-a258-4a12-9d12-cad594ee6f71/7573fe190d5d146b5d74c3096efa951c59dd407b19a0fe2c9f086581e00de107.webp)

Цикл зберігає зібрані записи й переносить зафіксовані збої між сторінками.

GraphQL.org описує непрозорі курсори та метадані connection як одну з моделей пагінації; стенд має явно підтримувати саме її. Документація GraphQL від GitHub описує продовження за допомогою endCursor, доки hasNextPage не стане false для відповідних колекцій. Сприймайте курсори як непрозорі значення, а не номери сторінок.

Документація n8n описує [значення пагінації, отримані з відповіді](<https://n8n-challenges.app/uk/blog/pahinatsiya-loop-over-items-u-n8n-nalahodzhennya-otrymannya-danykh-iz-api-po-storinkakh>), власні вирази завершення та явні цикли з вузлом IF. Тут оберіть явний цикл, щоб перевіряти кожну сторінку. Передавайте один керувальний елемент із поточним курсором, уже використаними курсорами, зібраними записами, лічильником сторінок, прапорцем завершення та накопиченими причинами збоїв. Дотримуйтеся запропонованої послідовності.

1. Запитайте сторінку з поточним курсором і збільште лічильник сторінок.
2. Фіксуйте транспортні збої, помилки в тілі відповіді та некоректну структуру даних, не очищаючи попередніх збоїв.
3. Додавайте отримані записи, зберігаючи їхні ідентифікатори для порівняння.
4. Позначайте завершення лише тоді, коли коректне pageInfo явно містить hasNextPage=false.
5. Якщо потрібна наступна сторінка, відхиліть відсутній або вже використаний endCursor; інакше збережіть його та повторіть цикл.
6. Використайте запропонований запобіжний ліміт у три запити; якщо він зупиняє обхід до підтвердження останньої сторінки, зафіксуйте неповноту.

На нашу думку, зафіксований збій має зберігатися до кінця цього запуску вправи; наступна коректна сторінка ніколи не повинна стирати попередню причину блокування запису.

Sources: [Using pagination in the GraphQL API - GitHub Docs](<https://docs.github.com/en/graphql/guides/using-pagination-in-the-graphql-api>), [Pagination | GraphQL](<https://graphql.org/learn/pagination/>), [skills/skills/n8n-loops-official/references/HTTP_PAGINATION.md at main · n8n-io/skills · GitHub](<https://github.com/n8n-io/skills/blob/main/skills/n8n-loops-official/references/HTTP_PAGINATION.md>), [n8n-docs/docs/build/flow-logic/loop.md at main · n8n-io/n8n-docs · GitHub](<https://github.com/n8n-io/n8n-docs/blob/main/docs/build/flow-logic/loop.md>)

## Ухваліть одне рішення про готовність і продемонструйте результат

![Один важіль готовності керує штампом тестової мутації поруч із перевіреними записами та відхиленими фрагментами.](/blog/uk/article-888d4706-a258-4a12-9d12-cad594ee6f71/f2fd9a5f650badd6bb15baf9f42eea019aa54231413a1f0a40ac0f9a2b19962e.webp)

Один керувальний елемент визначає, чи можна виконати тестову мутацію.

Після обходу оцініть один керувальний елемент. Запропонована перевірка допуску вимагає явного завершення, відсутності зафіксованих збоїв, непорожніх обов’язкових полів і точної відповідності очікуваним ідентифікаторам без дублікатів. Документація схем Apollo пояснює, що поля, які допускають null, можуть повертати null, а списки з обмеженням non-null усе одно можуть бути порожніми; отже, готовність за бізнес-вимогами потребує власних правил.

Редакційний розбір із гіпотетичними результатами: перша сторінка повертає A і B з непорожніми іменами, hasNextPage=true та непрозорим endCursor. Накопичений стан: records=[A,B], complete=false і failures=[]. Залиште мутацію заблокованою та запитайте другу сторінку з цим курсором. Припустімо, друга сторінка повертає C з непорожнім ім’ям і hasNextPage=false. За відсутності транспортних збоїв і помилок GraphQL накопичений стан стає records=[A,B,C], complete=true і failures=[]. Ідентифікатори точно відповідають очікуваним і не мають дублікатів, тож єдине рішення про готовність дозволяє одну мутацію в тестовому середовищі.

Для гіпотетичного сценарію зі збоєм припустімо, що одна зі сторінок також містить непорожній масив errors. Негайно зафіксуйте цей збій. Навіть якщо обхід в іншому дає A, B і C з коректними іменами та підтвердженням останньої сторінки, failures залишається непорожнім, і перевірка допуску блокує мутацію.

Спрямуйте результат цього єдиного рішення або до однієї тестової мутації, або до результату блокування з переліком невиконаних передумов. Передайте зібрані ідентифікатори через markReviewed, а потім перевірте також errors і очікувані поля відповіді. Використайте цей контрольний список приймання як перелік свідчень, які потрібно надати.

- [ ] Коректний сценарій: збережіть A, B і C та продемонструйте один виклик мутації.
- [ ] Сценарій із частковими помилками: покажіть збережену помилку та відсутність виклику мутації.
- [ ] Сценарій із відсутнім ім’ям: визначте некоректний запис і заблокуйте мутацію.
- [ ] Сценарій із повтореним курсором: зупиніться із зазначенням причини неповноти.
- [ ] Сценарій із запобіжним лімітом: заблокуйте мутацію, якщо підтвердження останньої сторінки не отримано.
- [ ] Відповідь мутації: вимагайте відсутності помилок, accepted=true і відповідності повернених ідентифікаторів; інакше повідомте про збій.

Запропоноване питання для осмислення: поясніть, чому ані коректних часткових записів, ані прапорця останньої сторінки окремо недостатньо. Специфікація GraphQL за вересень 2025 року розрізняє запити лише для читання та мутації, які записують і отримують дані; ця перевірка на боці клієнта не гарантує, що дані сервера залишаться незмінними між цими операціями.
