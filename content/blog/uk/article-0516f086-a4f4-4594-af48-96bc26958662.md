## Що ви створите: агент рев'ю коду на n8n від PR до коментаря

![Конверт pull request, сувій diff та проштампована бульбашка коментаря, розташовані на робочому столі.](/blog/uk/article-0516f086-a4f4-4594-af48-96bc26958662/b2794c9b8a7ceeb31b24f6177c0d6e4125a96482bee0e85071cf52a9f729f9f1.png)

Ілюстративний вигляд трьох складових, які поєднує агент рев'ю коду на n8n: тригер, diff і коментар.

Це редакційна вправа, а не збірка, яку ми запускали чи перевіряли від початку до кінця: самодостатнє завдання, яке ви можете спробувати виконати самостійно. Мета — спроєктувати агента рев'ю коду на n8n, який стежить за pull request або merge request, читає diff, перевіряє його на відповідність письмовим конвенціям вашої команди та публікує структурований коментар назад у PR чи MR, без ручного копіювання тексту між інструментами.

Вузол AI Agent в n8n не може самостійно аналізувати diff. Офіційна документація n8n зазначає, що вузол потребує щонайменше одного під'єднаного інструмента (tool sub-node), перш ніж він зможе запуститися, тож будь-який дизайн агента рев'ю коду на n8n має давати агенту щось, що він може викликати — чи то інструмент для отримання diff, чи документ із конвенціями, чи обидва разом.

Sources: [AI Agent | Nodes | n8n Docs](<https://docs.n8n.io/integrations/builtin/cluster-nodes/root-nodes/n8n-nodes-langchain.agent>)

## Передумови та вхідні дані, які вам знадобляться

![Планшет із позначеними жетонами для репозиторію, моделі, конвенцій, облікових даних та вебхука, два з яких позначено галочкою.](/blog/uk/article-0516f086-a4f4-4594-af48-96bc26958662/2db34a67e71c8f70fd09986fe42768ae6491d60e59300efd19b2c590dbca4460.png)

Концептуальний чекліст облікових записів, облікових даних та вхідних даних, які ця вправа передбачає перед початком.

Перш ніж щось з'єднувати, підготуйте чотири речі: інстанс n8n (хмарний або self-hosted), обліковий запис GitHub чи GitLab із репозиторієм, на якому можна безпечно тестувати, облікові дані API, обмежені цим репозиторієм, та обліковий запис провайдера ШІ, модель якого ви плануєте викликати з вузла AI Agent.

Щодо облікових даних, власна документація n8n рекомендує персональний токен доступу зі скоупом repo для більшості операцій вузла GitHub, тоді як для облікових даних GitLab документація вказує на потребу в ширшому скоупі api, щоб розблокувати повну функціональність вузла. Оскільки цьому workflow потрібно лише читати diff і публікувати коментарі, ця рекомендація для GitLab передбачає більше доступу, ніж строго необхідно для завдання.

- [ ] Інстанс n8n, хмарний або self-hosted
- [ ] Тестовий репозиторій GitHub або GitLab
- [ ] PAT GitHub зі скоупом repo, або обмежений токен GitLab
- [ ] Обліковий запис провайдера ШІ з моделлю, доступною вашому workflow
- [ ] Письмове джерело конвенцій команди: документ, таблиця або data table

## Побудова workflow: п'ять кроків від вебхука до коментаря

![Конвеєр станцій, що показує рух diff через кроки тригера, отримання, конвенцій, агента та коментаря.](/blog/uk/article-0516f086-a4f4-4594-af48-96bc26958662/6ba5057315d0b5ad4b56131a3a2d5886ba511d4fed5b26778a5dc235d274e774.png)

Концептуальний вигляд процесу п'яти етапів, через які агент рев'ю коду на n8n проводить diff pull request.

Загальна форма workflow рев'ю коду на n8n коротка: тригер, отримання diff, пошук конвенцій, виклик агента та публікація коментаря. Діаграма нижче показує цей порядок; абзаци після неї розкривають важливі рішення на кожному етапі.

![Від pull request до опублікованого рев'ю: 1. Тригер; 2. Отримати diff; 3. Завантажити конвенції; 4. Запустити агента; 5. Опублікувати коментар](/blog/uk/article-0516f086-a4f4-4594-af48-96bc26958662/d23e3627bdfba8ec978dddbc82b5031a9d789011a02cab2160350960acc20602.png)

Власна документація вузла GitHub перелічує операції для pull request, які включають пряме отримання diff чи patch, поряд із подіями GitHub Trigger для звичайної активності pull request, подання рев'ю та коментарів рев'ю. Тригер GitLab аналогічно надає подію merge request, але задокументовані операції вузла застосунку GitLab охоплюють файли, issues, релізи, репозиторії та користувачів, без жодної перелічненої дії merge request для отримання diff чи публікації коментаря. Одна задокументована спільнотна збірка обходить цю прогалину, звертаючись до API GitLab через вузол HTTP Request — саме такий підхід вона використала для свого workflow рев'ю коду на n8n для GitLab.

**Підтримка вузлів GitHub проти GitLab для цього workflow**

| Крок | Вузол застосунку GitHub | Вузол застосунку GitLab |
| --- | --- | --- |
| Отримати diff | Задокументована операція Get Diff / Get Patch | Немає задокументованої операції merge request; єдина задокументована спільнотна збірка, яку ми розглянули, використала HTTP Request |
| Опублікувати коментар | Задокументована операція створення коментаря | Немає задокументованої операції merge request; єдина задокументована спільнотна збірка, яку ми розглянули, використала HTTP Request |
| Подія тригера | Події pull request, review та review-comment | Подія merge request поряд з issues, pipelines та іншою активністю |

Для конвенцій команди одна задокументована спільнотна збірка під'єднує Google Sheet зі стандартами кодування команди як інструмент, до якого AI Agent може звертатися, замість того щоб вставляти правила безпосередньо в текст промпту. Ми вважаємо, що такий підхід на основі інструмента вартий додаткового налаштування: він дозволяє повторно використовувати один workflow для репозиторіїв із різними стандартами, замість форкання промпту щоразу, коли змінюється правило.

Коли агент має і diff, і конвенції, наступне рішення дизайну стосується форми виведення. Якщо попросити модель повернути структурований результат — наприклад, JSON-масив із полями file, line і comment — і розпарсити його за допомогою Structured Output Parser в n8n, крок публікації коментаря отримує передбачувані дані для мапування, що перегукується з тим, як одна задокументована спільнотна збірка формувала свої коментарі рев'ю для GitLab. В окремому блозі спільноти про створення автоматизації рев'ю коду на основі ШІ розробник Harsh Jolapara описує подібну автоматизацію так:

> “Йдеться не про заміну рев'ю людьми — йдеться про їх доповнення за допомогою ШІ, щоб ми рухалися швидше, не ламаючи нічого.”
>
> — Harsh Jolapara, Information & Communication Technology engineer working as a full-stack developer with expertise in AWS cloud, as stated in the article's author bio (переклад)
>
> Оригінал: “This isn’t about replacing human reviews — it’s about augmenting them with AI so we move faster without breaking things.” — Джерело: [How I Automated Code Reviews with AI, n8n, and GitHub (Step-by-Step) | by Harsh Jolapara | Medium](<https://medium.com/@harshj-1703/how-i-automated-code-reviews-with-ai-n8n-and-github-step-by-step-6211fabd1da7>)

Публікація коментаря назад зазвичай є найпростішим викликом вузла: вузол GitHub включає операцію створення коментаря, і одна задокументована спільнотна збірка використовує її для публікації відгуку ШІ одразу після завершення роботи агента; аналог для GitLab знову проходить через вузол HTTP Request у тій єдиній задокументованій спільнотній збірці для GitLab, яку ми розглянули. У будь-якому разі ставтеся до коментаря ШІ як до [чернеткової думки в PR](<https://n8n-challenges.app/uk/blog/human-in-the-loop-v-n8n-dodavannya-kroku-pohodzhennya-do-ai-ahenta>), а не як до умови для злиття.

## Обмеження та критерії завершення

![Два ящики з інструментами, що порівнюють підтримку вузлів GitHub та GitLab для отримання diff і публікації коментарів рев'ю.](/blog/uk/article-0516f086-a4f4-4594-af48-96bc26958662/de0e9ea4eb9c6f4d34b5bf1f252405cee054a8f7ebb76994ba51de72536710ff.png)

Ілюстративне порівняння того, наскільки задокументований вузол застосунку покриває потреби цього workflow на кожній платформі.

Скоуп токена, ліміти швидкості запитів та розмір diff — три обмеження, які найімовірніше дадуться взнаки. Обмежуйте облікові дані мінімально: PAT GitHub зі скоупом repo, або токен GitLab із найвужчим скоупом, який дозволяє ваша платформа, нижче широкого скоупу api, який документація n8n описує як простий варіант за замовчуванням.

Ліміти швидкості запитів відрізняються залежно від платформи. API GitHub очікує, що клієнти чекатимуть до часу, вказаного в заголовку скидання ліміту швидкості, перш ніж повторювати спробу, а GitLab спеціально обмежує створення коментарів у issues та merge requests задокументованим лімітом на GitLab.com, окремо від загальних лімітів API; self-managed або виділені інстанси GitLab встановлюють власні ліміти, які документація згадує, не наводячи конкретної цифри. Ми б [закладали логіку backoff і максимальну кількість повторних спроб](<https://n8n-challenges.app/uk/blog/bezpechni-povtorni-sproby-nevdalykh-http-zapytiv-u-n8n>) із самого початку, а не додавали б їх уже після того, як workflow перевищить ліміт у продакшні.

- Мінімальний скоуп токена для платформи, яку ви використовуєте
- Backoff, коли спрацьовує заголовок скидання ліміту швидкості GitHub
- Розуміння того, що GitLab обмежує створення коментарів окремо від загальних викликів API
- Верхня межа розміру diff, щоб надто великі pull requests не перевантажували контекст агента

Вважайте вправу завершеною, коли справді новий pull чи merge request запускає workflow агента рев'ю коду на n8n, і diff, і конвенції досягають AI Agent, агент повертає структурований результат, який workflow може розпарсити без ручних виправлень, і коментар з'являється в PR чи MR, відображаючи реальний вміст diff.

- [ ] Тригер спрацьовує на реальній події PR/MR
- [ ] Diff отримано і він досягає агента
- [ ] Інструмент конвенцій під'єднано і до нього звертаються
- [ ] Структурований результат парситься без ручних правок
- [ ] Коментар публікується назад у правильний PR/MR

## Рефлексія, усунення несправностей та ескіз пропонованого рішення

Робочий агент рев'ю коду на n8n має відчуватися нудним у найкращому сенсі: він тихо спрацьовує на нових pull requests і залишає один корисний коментар, не більше. Оскільки жоден з туторіалів, на яких базується ця вправа, не документує обробку помилок для невдалого виклику ШІ чи невдалої публікації коментаря, і жодне джерело тут не підтверджує точну схему коментаря, якої очікує вузол кожної платформи, ми б розглядали весь потік як чернетку, яку варто протестувати на репозиторії з низьким трафіком, перш ніж довіряти йому щось важливе. Наше прагматичне рішення: спершу пропустити повністю автоматизовану публікацію і спрямовувати вивід агента в приватний канал протягом тижня, перш ніж дозволити йому коментувати реальні pull requests.

Типові точки збоїв, які варто перевіряти під час тестування, включають надто великий diff, який модель обрізає чи обробляє неправильно, структурований результат, який майже, але не точно відповідає схемі вашого парсера, та виклик публікації коментаря, який мовчки завершується невдачею вже після успішного виклику ШІ.

- [ ] Diff занадто великий для контексту моделі
- [ ] Структурований результат не парситься коректно
- [ ] Виклик публікації коментаря завершується невдачею після успішного виклику ШІ
