## Спершу вирішіть: нативне погодження SAP чи зовнішнє

Процес погодження SAP не обов’язково реалізовувати в n8n. SAP S/4HANA Cloud Public Edition має нативний гнучкий воркфлоу для заявок на закупівлю, а тестовий сценарій best practice від SAP для одного scope item (версія 2608) перевіряє, що сценарний воркфлоу активний для типу документа NB. Будь-який зовнішній дизайн має це враховувати.

Наша рекомендація редакційна, а не задокументоване правило: використовуйте n8n лише для погоджувачів або каналів, до яких SAP не дістається, наприклад зовнішніх погоджувачів чи погодження через чат. На нашу думку, другий механізм погодження поряд із робочим нативним зазвичай створює більше плутанини, ніж зручності.

Є також відкрите питання, про яке варто знати до початку роботи. У липні 2026 року в гілці SAP Community запитували, чи може стандартний API запустити воркфлоу погодження заявки на закупівлю. Єдина відповідь була неперевіреною відповіддю з форуму без прийнятого рішення. Вона радила перевірку через BAdI або утримання заявки у зовнішньому застосунку й попереджала, що SAP не матиме видимості, доки дані не буде передано.

## Пауза й відновлення в n8n

![Чекліст поряд із замком і годинником: захищений URL відновлення вузла Wait з тайм-аутом в n8n](/blog/uk/article-cd6b7a7e-e2d6-42e6-b947-292830b5138f/e9f0ae2acd4c87931ae8c79106f8e5c72272b84036f15c56ab823c29196973cd.webp)

Чекліст поряд із замком і годинником — запобіжники навколо кроку відновлення вузла Wait.

Вузол Wait в n8n призупиняє виконання та вивантажує його дані в базу даних, згідно з документацією n8n. Він може відновитися після інтервалу часу, у заданий час, після виклику вебхука або після надсилання форми. Сторінка документації не вказує версію й не стосується SAP.

У режимі On Webhook Call n8n генерує для кожного виконання URL відновлення, який можна надіслати стороннім сервісам або в листі. Його можна захистити автентифікацією Basic, Header або JWT. Документація попереджає, що часткові виконання змінюють URL відновлення, тому тестуйте в повних виконаннях.

Вузол Wait також може обмежувати час очікування, щоб воркфлоу відновився сам, і може обмежувати викликачів за списком дозволених IP, повертаючи іншим 403. Документація не визначає політику тайм-ауту погодження, тож перші чотири пункти чекліста нижче — наші редакційні пропозиції для процесу погодження SAP; останній — задокументоване попередження n8n.

- [ ] Захистіть URL відновлення автентифікацією Header або JWT
- [ ] Додайте список дозволених IP для викликачів
- [ ] Задайте ліміт очікування із запасним варіантом: ескалація вгору або безпечна зупинка
- [ ] Ніколи не погоджуйте автоматично за тайм-аутом для фінансових об’єктів
- [ ] Тестуйте в повних виконаннях, а не в часткових

На нашу думку, URL відновлення, захищений Header або JWT, плюс список дозволених IP — це мінімум для всього, що стосується фінансів.

Sources: [Wait | Nodes | n8n Docs](<https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.wait>)

## Конфігурація процесу погодження SAP: доступ і запис результату

![Елементи пазла: комунікаційний користувач, система й домовленість для доступу до OData в SAP S/4HANA](/blog/uk/article-cd6b7a7e-e2d6-42e6-b947-292830b5138f/0f2b58257e00dda1f37e4b9e74f59e18eb43599209de1a7379076e20cbd89d96.webp)

Елементи пазла показують, як комунікаційний користувач, система й домовленість поєднуються для доступу до API.

SAP S/4HANA Cloud Public Edition (документація версії 2608) надає API OData V2 і V4 та SOAP, які можна знайти на SAP Business Accelerator Hub. Доступ налаштовується через комунікаційні сценарії та домовленості. Приклад SAP для іншого сценарію, SAP_COM_0837, показує послідовність: комунікаційний користувач, система й домовленість, і зазначає, що неправильний URL кінцевої точки спричиняє помилку автентифікації. Він показує лише шаблон; ролі відрізняються залежно від сценарію.

Методи автентифікації охоплюють Basic, x509, OAuth2 і SAML SSO, але кожен API підтримує різні, тож перевіряйте конкретний API на Hub. В n8n вузол HTTP Request радить використовувати попередньо визначені типи облікових даних, де вони є, із загальними обліковими даними Basic, Header і OAuth2 для інших API. Чи підходять client credentials до вашої домовленості, залежить від самої домовленості.

Перш ніж будувати, переконайтеся, що для вашого об’єкта є випущена операція approve або reject. Перелік 2608 показує Approve і Reject для Purchase Contracts (Version 2) і для Service Entry Sheets (Lean Services), але урізаний текст не вказує, чи це OData. Для заявок на закупівлю він показує API V4 з read, update і validate, а API V2 — як застарілий.

Жодне надане офіційне джерело SAP не показує випущеної операції OData для погодження чи відхилення заявки на закупівлю ззовні SAP, тому ця стаття не стверджує, що вона існує. Нічого тут не тестувалося безпосередньо, а кілька сторінок довідки SAP урізані. Перевірте Hub для свого об’єкта.

## Безпечний запис рішення назад

![Послідовність: отримання токена CSRF, читання ETag і надсилання оновлення OData з n8n](/blog/uk/article-cd6b7a7e-e2d6-42e6-b947-292830b5138f/b46e30474d75271b7cff445f50f0443d6bc65b4f7b628a9d274b509d5f52de67.webp)

Послідовність кроків запису зліва направо: токен, читання, оновлення.

Змінювальні виклики, як-от POST, потребують [токена CSRF](<https://n8n-challenges.app/uk/blog/obrobka-csrf-tokena-v-n8n-pidhotovka-zapysu-v-testovomu-seredovyshchi-sap-gateway>) у S/4HANA Cloud Public Edition (2608). Клієнт отримує його незмінювальним викликом із заголовком X-CSRF-Token зі значенням Fetch, а потім використовує його в змінювальному запиті. Сторінка SAP написана для іншого сервісу, тому специфіка n8n не розглядається.

Оновлення використовують [оптимістичне керування паралелізмом через ETag](<https://n8n-challenges.app/uk/blog/obrobka-sap-odata-etag-redaktsiyna-vprava-v-n8n-pered-povtornoyu-sproboyu>). Клієнт має надіслати раніше отриманий ETag, а невідповідність повертає помилку без змін. Загальний перелік помилок SAP містить 403 Forbidden, 412 Precondition Failed (ресурс змінився, прочитайте знову) і 428 Precondition Required (надішліть заголовок if-match). Чи потребує певний API погодження ETag, не зазначено.

Як редакційна послідовність, кроки нижче накладають ці поведінки на запис результату з n8n.

## Обробка помилок, ідемпотентність і запасний варіант

Демо від спільноти з SAP Inside Track Ankara 2026, опубліковане в репозиторії спільноти на GitHub, показує загальний шаблон: вебхук CAP до n8n, порогова умова IF, надсилання в Telegram із очікуванням відповіді, потім approve або reject, записані назад через дії OData V4. Воно використовувало локальний мок CAP з n8n 2.x, а не S/4HANA, тож демонструє лише шаблон. Автор описує вебхук як fire-and-forget, а дії як ідемпотентні.

Те саме демо зазначає, що SAP не залежить від n8n: замовлення створюються, навіть якщо n8n недоступний, а статус залишається pending, і воркфлоу помилок сповіщає про збої. Жодне офіційне джерело не вказує, як S/4HANA Cloud Public Edition доставляє вихідну подію погодження до n8n, тож цей тригер лишається відкритим питанням.

Як редакційна пропозиція, робіть крок запису повторно запускним. При 412 перечитайте об’єкт і повторіть один раз; при 403 зупиніться й повідомте, а не повторюйте. На нашу думку, [воркфлоу з Error Trigger](<https://n8n-challenges.app/uk/blog/stvory-robochyy-protses-obrobky-pomylok-v-n8n-i-pidyednay-yoho-do-prodakshn-protsesu>) має існувати до першого продуктивного погодження, а не після першого збою.

## Управління та аудит

![Загальний значок технічного користувача поруч із журналом іменних погоджувачів лише з додаванням для погоджень SAP](/blog/uk/article-cd6b7a7e-e2d6-42e6-b947-292830b5138f/b1dd82b733fadc5dadf4a14db15b74b3232033bc8ecfba21b59ea9c97ccf90e1.webp)

Загальний значок поруч із журналом іменних підписів: технічний користувач проти зафіксованого погоджувача.

Технічний користувач — це те, що бачитиме SAP. Блог SAP Community 2025 року про SAP Build Process Automation, що не є OData S/4HANA, повідомляє: виклик API завершення завдання з client credentials показує форму як погоджену загальним користувачем на основі client ID. Сприймайте це як застереження щодо атрибуції при використанні службових облікових даних.

Блог SAP Community 2026 року від SAP AI Solution Architect про агентів із людиною в циклі радить записи аудиту, що фіксують вхідні дані, міркування, рішення, рецензента й уражені об’єкти SAP, які ведуться лише з додаванням. Там також сказано, що запасний варіант «продовжити» за тайм-аутом ніколи не слід використовувати для фінансових проводок. Це дизайнерська думка одного автора для іншого стеку, а не стандарт SAP.

Специфічних вимог SAP до аудиту не надано, тож решта — редакційна: використовуйте окремого комунікаційного користувача на сценарій замість спільного діалогового користувача, а людину-погоджувача фіксуйте в даних виконання n8n і в окремому журналі лише з додаванням.

## Рекомендований дизайн і відкриті питання

Наш запропонований дизайн процесу погодження SAP: переконайтеся, що нативний воркфлоу не підходить, прочитайте об’єкт із SAP, призупиніть у вузлі Wait з автентифікованим URL відновлення й тайм-аутом, потім отримайте токен CSRF, прочитайте ETag і запишіть рішення назад. Спершу протестуйте в непродуктивному тенанті.

Відкриті питання, які треба вирішити у вашому тенанті: чи має ваш об’єкт випущену операцію approve або reject (див. розділ про конфігурацію), який метод автентифікації підтримує цей API і як запит на погодження потрапляє до n8n.
