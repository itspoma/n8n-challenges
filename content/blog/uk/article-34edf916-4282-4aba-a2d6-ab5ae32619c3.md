## Автоматизація офбордингу HR: що має охоплювати воркфлоу

Автоматизацію офбордингу HR в n8n найпростіше проєктувати відносно базового набору контролів. Цей посібник поєднує документацію n8n, текст контролів і сторінки API вендорів, а сама композиція — наш редакційний задум. Нічого з описаного не запускали в екземплярі n8n. Ендпоінти вимкнення облікових записів для Entra, Google, Slack, Okta, GitHub і SAP потрібно перевіряти в документації кожного вендора, а юридичні вимоги чи правила зберігання записів про звільнених різняться залежно від юрисдикції й тут не розглядаються.

Контроль PS-4 з NIST SP 800-53 Rev 5.2.0, відтворений незалежним сайтом CSF Tools, охоплює вимкнення доступу до систем, відкликання облікових даних, повернення майна та збереження доступу до інформації, якою керувала людина. Часовий період кожна організація визначає сама. Одне з посилень згадує автоматизовані механізми, що сповіщають персонал і вимикають доступ, — це підтримує автоматизацію процесу.

Для звільнень з вини працівника те саме керівництво каже, що своєчасні дії є вирішальними, а організації можуть вимикати облікові записи до повідомлення особи. Це впливає на порядок погоджень і сповіщень. Діаграма нижче — наш запропонований потік, а не перевірений стандарт.

## Пауза для погоджень за допомогою вузла Wait

![Конверт зупиняється біля воріт із пісочним годинником — крок погодження з вузлом Wait в n8n](/blog/uk/article-34edf916-4282-4aba-a2d6-ab5ae32619c3/5e5b7b56a014577b562bb4675dacd79e9063dcca215aa54a65bcd16d57ef18d4.webp)

Запуск зупиняється біля воріт погодження й або продовжується, або йде гілкою тайм-ауту.

[Вузол Wait в n8n](<https://n8n-challenges.app/uk/blog/vuzol-n8n-wait-obrobka-povtornykh-sprob-ta-api-z-obmezhennyam-shvydkosti>) може призупиняти воркфлоу до виклику вебхука або надсилання форми, що добре підходить для кроків погодження. Під час паузи він переносить дані виконання в базу даних. Сторінка документації не вказує версію чи редакцію, до якої це належить.

З опцією On Webhook Call кожне виконання отримує унікальну URL-адресу відновлення через $execution.resumeUrl, яку можна вставити в лист чи повідомлення. В автоматизації офбордингу HR один із редакційних способів сповістити власників — надіслати кожному власнику системи повідомлення з URL цього виконання, що відповідає посиленню автоматичних сповіщень у PS-4. Запити на відновлення можуть використовувати автентифікацію Basic, Header або JWT та білий список IP, тож можна обмежити коло тих, хто погоджує. Часткові виконання змінюють URL відновлення, тому тестуйте повними запусками.

Параметр Limit Wait Time відновлює воркфлоу після інтервалу або в заданий час, тож після нього можна поставити вузол IF чи Switch, щоб створити гілку тайм-ауту або ескалації; цей шаблон — наш вибір дизайну, а не задокументований рецепт. Блог самого n8n за січень 2026 року, написаний про ШІ з участю людини, а не про офбординг, радить перевіряти лише в точках незворотних рішень і додавати тайм-аут, ескалацію та журнали аудиту.

Ми вважаємо, що погодження доречні для рішень, що потребують судження, як-от винятки чи передача даних, а рутинне вимкнення облікових записів не має чекати, поки менеджер клацне посилання.

## Відкликання доступу: сесії, токени та облікові записи

![Висмикнутий кабель біля замкнених дверей: відкликання сесій проти вимкнення облікового запису в n8n](/blog/uk/article-34edf916-4282-4aba-a2d6-ab5ae32619c3/4a03b408ebd2f5d6b7ce9faf2a8a6e2af4204c4414e318176f9a4c0584e0608e.webp)

Завершення сесій і вимкнення облікового запису — дві окремі дії.

Відкликання доступу має дві половини для кожної системи: завершення активних сесій чи токенів і вимкнення облікового запису. Таблиця нижче порівнює два задокументовані виклики для сесій і токенів.

revokeSignInSessions у Microsoft Graph v1.0 робить недійсними refresh-токени користувача та cookie браузерних сесій. Потрібен дозвіл User.RevokeSessions.All, а набуття чинності може тривати кілька хвилин. Зовнішні користувачі не охоплюються. Сторінку востаннє оновлено в липні 2025 року.

Метод tokens.delete Directory API в Google Workspace Admin SDK видаляє токени доступу, які користувач видав для одного застосунку. Потрібен scope admin.directory.user.security, і метод працює для окремого client ID, тож для кожного застосунку потрібен окремий виклик.

**Що роблять і чого не роблять два виклики відкликання**

| Виклик API | Дозвіл або scope | Чого не робить |
| --- | --- | --- |
| Microsoft Graph v1.0 revokeSignInSessions | User.RevokeSessions.All | Не вимикає обліковий запис; не охоплює зовнішніх користувачів |
| Google Directory API tokens.delete | admin.directory.user.security | Не призупиняє користувача; не охоплює більше одного застосунку за виклик |

Виклик будь-якого з них із вузла HTTP Request в n8n — наш висновок, а не те, що описують сторінки. Ми б обережно ставилися до позначення звільненого як завершеного лише після виклику відкликання.

Sources: [user: revokeSignInSessions - Microsoft Graph v1.0 | Microsoft Learn](<https://learn.microsoft.com/en-us/graph/api/user-revokesigninsessions?view=graph-rest-1.0>), [Method: tokens.delete](<https://developers.google.com/workspace/admin/directory/reference/rest/v1/tokens/delete?hl=zh-tw>)

## Ведіть журнал аудиту та обробляйте збої

![Папери, що зникають, біля міцної шафи для документів і дзвінка тривоги — журнал аудиту та воркфлоу помилок в n8n](/blog/uk/article-34edf916-4282-4aba-a2d6-ab5ae32619c3/522c5d71da30300ab80a4b97c4a3978d8f107cc6d20d2a76b75331fc08e2a500.webp)

Історія виконань за замовчуванням зникає, тож тривалий запис живе у зовнішньому сховищі.

Для автоматизації офбордингу HR історія виконань n8n — поганий журнал аудиту. Згідно з документацією n8n щодо змінних середовища для self-hosted, завершені виконання за замовчуванням видаляються через 336 годин (14 днів) або при перевищенні 10 000 виконань, а виконання з анотаціями ніколи не видаляються. Збереження виконань також можна налаштувати так, щоб пропускати успішні, тож успішні офбординги не з’являться. Ця документація не вказує обмежень для Cloud.

Натомість записуйте кожне рішення та результат API у зовнішнє сховище. Блог n8n за січень 2026 року радить логувати кожне рішення людини в сховищі даних, називаючи Postgres, Notion і Airtable, і цитує керівника з безпеки (за його власними словами), який очікує, що запис знадобиться під час розбору після інциденту. Червневий туторіал n8n-консалтингової компанії 2026 року поєднує погодження в Slack, вузол Wait і журнал аудиту в PostgreSQL для запитів на доступ; він не про офбординг, тож використовуйте його лише як референс шаблону.

В n8n можна задати воркфлоу помилок, який починається з Error Trigger і запускається, коли виконання завершується збоєм. Вузол Stop And Error примусово викликає збій, щоб цей воркфлоу запустився, наприклад для сповіщення про невдале відкликання. Якщо збій стався у вузлі-тригері, ID виконання та URL відсутні.

На нашу думку, невдале відкликання заслуговує на сповіщення названої людини, а не тихий повтор.

## Перед реальним запуском: доступ, секрети та обробка помилок

![Планшет із відміченими рядками біля невеликого сейфа — передстартові перевірки секретів і ролей в n8n](/blog/uk/article-34edf916-4282-4aba-a2d6-ab5ae32619c3/a7af3d41bdc1ff8e86ff5cde3640e8bc2400295091e3d17a7706d2b6e895bcf1.webp)

Запропонований передстартовий чекліст щодо облікових даних, ролей і шляхів збою.

[n8n RBAC](<https://n8n-challenges.app/uk/blog/n8n-rbac-cheklist-rehulyarnoho-perehlyadu-dostupu>) групує воркфлоу та облікові дані в проєкти з ролями на рівні проєкту. Доступний в n8n Cloud (усі плани) і в self-hosted Registered Community, Business та Enterprise. Переміщення воркфлоу чи облікових даних скасовує наявний спільний доступ. Користувацькі ролі для мінімальних привілеїв доступні лише в n8n Cloud Enterprise і self-hosted Enterprise, тож інші плани покладаються на вбудовані ролі.

Зовнішні сховища секретів, як-от AWS Secrets Manager, Azure Key Vault, GCP Secrets Manager, HashiCorp Vault, 1Password Connect та Infisical, доступні в n8n Cloud Enterprise і self-hosted Enterprise. Секрети розв’язуються лише в полях облікових даних. Сховища з областю проєкту з’явилися в n8n 2.11.0, а поведінка залежить від версії, тож перевірте, що саме ви використовуєте.

Цей передстартовий чекліст для автоматизації офбордингу HR — наша пропозиція, а не перевірений інструмент.

- [ ] Облікові дані обмежені проєктом або зберігаються у зовнішньому сховищі секретів
- [ ] Лише названі адміністратори можуть переглядати чи редагувати воркфлоу
- [ ] Воркфлоу помилок налаштовано, примусовий збій протестовано
- [ ] Гілки тайм-ауту та збою протестовано
- [ ] Пробний запуск виконано на тестовому користувачеві
- [ ] Рішення та результати API потрапляють у зовнішнє сховище
