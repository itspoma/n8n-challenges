## Підготуйте безпечний зразок у Dropbox

У цьому посібнику бінарні дані n8n проходять через чотири вузли: HTTP Request для завантаження, Edit Fields, HTTP Request для надсилання та HTTP Request для перевірочного завантаження. Мета — отримати надісланий документ і порівняти його вміст з оригіналом. Для запропонованої вправи потрібні робоче середовище n8n, обліковий запис Dropbox і наявний текстовий файл із безпечним вмістом.

У налаштуваннях застосунків Dropbox створіть застосунок Scoped access із доступом App folder. Увімкніть files.content.read і files.content.write, застосуйте зміни дозволів і згенеруйте короткостроковий тестовий токен. Dropbox рекомендує OAuth для застосунків у робочому середовищі; його реалізація виходить за межі цього посібника.

У нашому прикладі передбачається, що зразок уже доступний цьому застосунку за шляхом /sample.txt. Виділіть /sample-copy.txt як окремий шлях призначення. Це покроковий посібник на основі документації, а не звіт про власне тестування. В офіційній документації n8n, використаній для цих інструкцій, не зазначено версію чи тарифний план n8n.

## 1. Завантажте бінарні дані n8n у document

Додайте вузол HTTP Request. Для обох операцій Dropbox у цьому посібнику використовуйте HTTPS із хостом content.dropboxapi.com і шляхом кінцевої точки, зазначеним нижче. Налаштуйте завантаження в такому порядку.

1. Установіть Method у POST, а шлях кінцевої точки — /2/files/download.
2. Додайте заголовок Authorization зі значенням Bearer, після якого йдуть пробіл і ваш тестовий токен.
3. Додайте заголовок Dropbox-API-Arg зі значенням {"path":"/sample.txt"}.
4. Установіть Response Format у File, а Put Output in Field — у document.
5. Виконайте вузол і перевірте його бінарні вихідні дані, перш ніж продовжувати.

Очікуваний результат — файл у бінарній властивості document. Ця властивість відокремлена від полів JSON та імені файлу sample.txt. Сам по собі режим відповіді File не підтверджує, що відповідь містить потрібний вам документ.

## 2. Збережіть бінарні дані n8n із попереднього вузла

![Рука змінює блакитний папірець між двома лотками, поки складений документ у рожевому чохлі переходить між ними.](/blog/uk/article-960aebb7-4eb9-49d0-9610-74abb0996424/02ac8e203c205b700a0ac21a30948e45541a62e3630254d500793237917e894f.webp)

Окремі паперові об’єкти ілюструють редагування метаданих JSON зі збереженням бінарного файлу.

Під’єднайте Edit Fields до вузла завантаження. За допомогою Manual Mapping додайте запропоноване поле JSON exerciseLabel зі значенням dropbox-round-trip. Увімкніть Include Binary Data, щоб вхідний файл потрапив у вихідні дані, потім виконайте вузол і перевірте, що document усе ще присутня.

Для роботи з бінарними даними n8n із попереднього вузла наступному вузлу потрібне ім’я бінарної властивості, яку створив попередній: document. На нашу думку, перевірку файлу на цьому переході варто зробити командною звичкою, адже вона чітко визначає, які вхідні дані отримає наступний крок.

## 3. Надішліть файл і завантажте його з місця призначення

![Оригінальний зразок і документ, завантажений із Dropbox, лежать поруч для порівняння вмісту.](/blog/uk/article-960aebb7-4eb9-49d0-9610-74abb0996424/5e23003127f4b5c6d40b0f63437af3970c792527ecb0ae48102638d260f86dd4.webp)

Однакові візерунки на папері ілюструють запропоноване порівняння оригінального й отриманого вмісту.

Під’єднайте ще один вузол HTTP Request після Edit Fields. Операція надсилання Dropbox приймає безпосередній вміст файлу як тіло запиту. Виконайте ці кроки, щоб надіслати бінарні дані n8n і завантажити файл із місця призначення.

1. У вузлі надсилання встановіть Method у POST, а шлях кінцевої точки — /2/files/upload на тому самому хості Dropbox.
2. Додайте заголовок Authorization із токеном Bearer і встановіть Content-Type у application/octet-stream.
3. Установіть Dropbox-API-Arg у {"path":"/sample-copy.txt","mode":"add"}.
4. Увімкніть Send Body, виберіть для Body Content Type значення n8n Binary File і встановіть Input Data Field Name у document.
5. Виконайте надсилання та перевірте повернуті метадані файлу.
6. Під’єднайте перевірочний вузол HTTP Request. Повторіть налаштування завантаження, змінивши Dropbox-API-Arg на {"path":"/sample-copy.txt"}, зі значенням File для Response Format і вихідним полем document.
7. Виконайте перевірочне завантаження та перегляньте фактичний вміст отриманого документа.

Для перевірки успіху радимо порівняти отриманий текст з оригінальним зразком, зокрема пунктуацію та переноси рядків. Також перевірте метадані надісланого файлу щодо місця призначення, але не вважайте підтвердження надсилання доказом однаковості вмісту. На нашу думку, повний цикл передавання завершено лише після перевірки отриманого вмісту.

## 4. Усуньте проблеми з передаванням файлу

Якщо повний цикл передавання не вдається виконати, пройдіть запропоновану послідовність діагностики, щоб знайти, де файл уперше зникає або де запит відрізняється від потрібної конфігурації. Останній рядок стосується адаптації вправи до іншого одержувача.

**Запропонована послідовність діагностики невдалого передавання файлу**

| Точка перевірки | Що перевірити | Наступна дія |
| --- | --- | --- |
| 1. Вихідні дані завантаження | Чи присутня document перед Edit Fields? | Якщо ні, перегляньте налаштування завантаження в кроці 1. |
| 2. Вихідні дані Edit Fields | Чи зникає document між входом і виходом? | Якщо так, перегляньте налаштування збереження в кроці 2. |
| 3. Запит надсилання | Якщо document присутня, у чому відрізняється запит? | Порівняйте вхідну властивість, формат тіла та заголовки з кроком 3. |
| Іншому одержувачу потрібен multipart | Ім’я поля форми одержувача | Використовуйте Form-Data з параметром n8n Binary File і відповідною вхідною властивістю. |

- [ ] Зафіксуйте допустимий максимальний розмір файлу та дозволені формати.
- [ ] Визначте, які конфіденційні дані можуть потрапляти до робочого процесу.
- [ ] Затвердьте шляхи призначення та визначте відповідальних за доступ.
- [ ] Установіть правила зберігання та видалення для вихідних файлів, копій і даних виконання.
- [ ] Призначте відповідальних за впровадження та перевірку цих заходів контролю.

Для n8n на власному хостингу офіційна документація з масштабування зазначає, що бінарні дані за замовчуванням зберігаються в пам’яті, а великі файли можуть спричиняти аварійне завершення роботи. Вона рекомендує N8N_DEFAULT_BINARY_DATA_MODE=filesystem поза режимом черги та database для режиму черги; режим filesystem не підтримується в режимі черги. Ці рекомендації щодо розгортання не визначають універсальної безпечної межі розміру файлу й не є кроком налаштування Cloud.
