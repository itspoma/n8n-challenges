## Редакційна вправа: завдання, передумови та вхідні дані

![Чотири лотки тестових сценаріїв представляють негайне завершення, очікування, порожню відповідь і роботу, яка ніколи не завершується.](/blog/uk/article-df5d06b2-714d-451a-8916-fbf655745d28/65082aafae9e8ead9684b53b34fc2e379c0bf51636469cbe8f07b6acb48cc218.webp)

Чотири лотки представляють спеціально визначені умови тестових сценаріїв, а не універсальні значення кодів відповідей.

Використайте вузол HTTP Request у n8n, щоб дослідити контрольовані відповіді, а потім спроєктуйте процес опитування, який розрізняє завершену роботу, роботу в очікуванні та ескалацію. Це редакційна вправа: запропонований робочий процес не виконували й не перевіряли. Результатами мають бути робочий процес маршрутизації відповідей, схема опитування та матеріали, що пояснюють кожен шлях виходу.

Вам потрібні власне середовище n8n, базові знання API та контрольовані кінцеві точки, надані викладачем. Викладач має надати методи запитів, заголовки, тіла та послідовності відповідей, описані нижче; ця стаття не містить сервера тестових сценаріїв. Використовуйте синтетичні вхідні дані й не залучайте до вправи дані компанії.

Сприймайте ці тестові сценарії як спеціально визначені умови вправи, а не універсальну семантику HTTP. Рекомендації Microsoft щодо шаблону Asynchronous Request-Reply розрізняють початкове підтвердження 202 і запит статусу, який повертає 200, поки робота ще очікує завершення. Визначайте завершення за документованим станом сценарію, а не лише за кодом статусу.

**Рекомендовані контрольовані тестові сценарії, які варто запросити у викладача**

| Тестовий сценарій | Задана послідовність відповідей | Очікуваний результат |
| --- | --- | --- |
| Негайне завершення | 200 зі станом completed | Завершено |
| Асинхронна робота | 202, потім 200 pending, потім 200 completed | Опитування, потім завершення |
| Порожня відповідь | 204 без тіла, що за умовами означає завершення | Завершення без читання тіла результату |
| Робота ніколи не завершується | 202, потім повторювані 200 pending | Ескалація після досягнення ліміту |

На нашу думку, корисна навичка тут — пояснити призначення гілки, перш ніж додавати нові вузли. Схема робочого процесу має робити рішення про зупинку зрозумілими іншому розробнику.

## Дослідіть відповідь вузла HTTP Request у n8n

![Відкритий конверт із відповіддю відокремлює статус, заголовки та тіло для дослідження.](/blog/uk/article-df5d06b2-714d-451a-8916-fbf655745d28/4471e335d7a806edb263a92ceeb67b1bbbe251ed7464742a492b53adc5f58c7d.webp)

Відкритий конверт ілюструє дослідження складових відповіді перед вибором полів маршрутизації.

Увімкніть Include Response Headers and Status. У документації n8n для HTTP Request зазначено, що цей параметр повертає заголовки та код статусу разом із тілом. Перш ніж писати вирази маршрутизації, дослідіть фактичні вихідні дані кожного сценарію та зафіксуйте повернений статус, доступні заголовки й структуру тіла.

Для подальшої маршрутизації використовуйте поля, повернені у цих вихідних даних. Довідник виразів n8n обмежує використання $response.statusCode вузлом HTTP Request; не припускайте, що цей вираз доступний у наступних вузлах. Запропонована нижче послідовність перевірки допомагає відокремити контракт відповіді від припущень щодо шляхів до полів.

1. Виконайте кожен наданий тестовий сценарій і збережіть спостережувану структуру вихідних даних.
2. Знайдіть повернене поле статусу та документоване поле стану в тілі, якщо воно є.
3. Напишіть правило маршрутизації для кожного сценарію, перш ніж з’єднувати гілки.
4. Спрямуйте неочікуваний статус або стан на ескалацію із зазначенням причини.

Зафіксуйте всі заголовки з адресою опитування або затримкою, які надає сценарій, але не використовуйте їх для керування циклом цієї вправи. Опитування на основі заголовків, обробка відсутніх заголовків і розбір затримки потребують окремої специфікації реалізації. Натомість використовуйте задану викладачем кінцеву точку опитування та фіксований інтервал для вправи.

## Спроєктуйте опитування з окремими шляхами виходу

![Доріжка опитування містить пісочний годинник, лічильні намистини, з’їзд завершення та зупинку ескалації.](/blog/uk/article-df5d06b2-714d-451a-8916-fbf655745d28/2672d7f86f4f3b86249646385cf922aa82e1f9dc0829d585b860d8656e500456.webp)

Доріжка пов’язує інтервал очікування й обмежену кількість запитів з окремими шляхами виходу.

Перш ніж проєктувати опитування вузлом HTTP Request у n8n, визначте ліміт. Як умову редакційної вправи дозвольте щонайбільше три запити статусу після початкового підтвердження; це не стандартне налаштування для експлуатації. Зберігайте ідентифікатор операції, кількість виконаних опитувань, ліміт, останню відповідь і причину зупинки. Подайте схему опитування з поясненнями; ця стаття не містить готової до копіювання реалізації циклу.

Офіційний довідник n8n щодо циклів вимагає явної умови завершення та обмеження індексу виконання для опитування в режимі reset і описує підключення виходів Loop Over Items із typeVersion 3. Для цієї редакційної схеми передбачте один вузол ухвалення рішення після відповіді, який виконується один раз для кожної відповіді на запит статусу: його значення $runIndex із відліком від нуля — 0, 1 і 2 — відповідають першому, другому й третьому запитам. Спочатку перевіряйте завершення; інакше передавайте незавершену роботу на ескалацію, коли $runIndex становить щонайменше 2. Перед наступним запитом окрема перевірка доступного залишку має забороняти запит, якщо вже виконано 3 або більше опитувань.

Ці перевірки описують той самий ліміт у три запити, а не два незалежні ліміти. Їхня виконувана конфігурація та збереження стану залишаються поза інструкціями з реалізації цієї вправи. Документація n8n для Wait передбачає інтервал через Wait Amount і Wait Unit; параметр Limit Wait Time, призначений для вебхуків, не є кінцевим терміном циклу опитування.

Скористайтеся наведеною нижче рекомендованою послідовністю рішень. Опрацюйте послідовності відповідей pending, pending, completed і pending, pending, pending, записуючи номер кожного запиту, індекс виконання вузла ухвалення рішення та напрямок переходу.

![Рекомендована послідовність рішень під час опитування: 1. Перевірте залишок запитів; 2. Зачекайте й надішліть запит; 3. Перевірте завершення; 4. Перевірте можливість продовження](/blog/uk/article-df5d06b2-714d-451a-8916-fbf655745d28/41bdfb7ea9db5d61e677de0323480612e30c1e7eb800da3900089635695897ea.webp)

Ми б обмежили першу версію лімітом кількості запитів і фіксованим інтервалом. На нашу думку, зробити ці виходи доступними для перевірки корисніше, ніж додавати обчислення кінцевого терміну до того, як стане зрозумілим контракт станів.

## Критерії завершення та рефлексія

![Учасник перевіряє конверти з відповідями, стан опитування та тестовий сценарій із порожнім тілом за критеріями завершення.](/blog/uk/article-df5d06b2-714d-451a-8916-fbf655745d28/d19c63f6fa1736b167d5410b26065e5baa41b921f9024b37744bfd30c59ecf92.webp)

Дошка перевірки ілюструє перевірку матеріалів тестових сценаріїв і пояснення кожного шляху виходу.

Для вправи з вузлом HTTP Request у n8n подайте робочий процес маршрутизації, збережені вихідні дані тестових сценаріїв і схему опитування з поясненнями. Якщо ви також реалізуєте цикл, продемонструйте, як його ідентифікатор операції та лічильник зберігаються після кожної HTTP-відповіді. Використайте цей рекомендований [контрольний список для перевірки роботи](<https://n8n-challenges.app/uk/blog/cheklist-testuvannya-robochoho-protsesu-n8n-shcho-pereviryty-pered-realnym-vykorystannyam>).

- [ ] Кожен тестовий сценарій дотримується своїх документованих умов маршрутизації.
- [ ] Сценарій із порожнім тілом завершується без читання тіла результату.
- [ ] Відповіді про очікування залишаються відокремленими від відповідей про завершення.
- [ ] Сценарій, який ніколи не завершується, зупиняється після досягнення вибраного ліміту.
- [ ] Ескалація фіксує ідентифікатор операції, останню відповідь і причину зупинки.
- [ ] Схема пояснює завершення на останній дозволеній відповіді.

Ця вправа не визначає виправлення помилок розбору порожнього тіла для конкретного релізу; якщо така помилка виникне, зафіксуйте встановлений реліз, налаштування формату відповіді та саму помилку, а не вважайте неперевірений обхідний спосіб розв’язанням.

Для рефлексії поясніть, чому успішний запит статусу все ще може означати очікування завершення роботи, які поля мають зберегтися після наступного запиту, та обґрунтуйте рішення щодо останньої відповіді. Рекомендований ескіз розв’язання має чотири окремі напрямки: негайне завершення, завершення після опитування, продовження опитування та ескалація.
