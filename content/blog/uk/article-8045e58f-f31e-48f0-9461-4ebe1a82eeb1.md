## n8n Queue Mode vs Normal Mode: що це насправді

![Основний процес n8n передає тригер окремому worker-у, який забирає завдання з черги для виконання.](/blog/uk/article-8045e58f-f31e-48f0-9461-4ebe1a82eeb1/835f20f99a8e710c208cc3dee3dd670cb45dd65dc8e44e7e622ba4706e47b0ef.png)

Основний інстанс лише приймає тригер; окремий worker забирає завдання з черги, щоб виконати його.

Коли інженерні команди порівнюють n8n queue mode і normal mode, різниця починається з того, де фактично виконується workflow. У тому, що документація n8n називає regular mode (далі в цій статті — normal mode), один процес n8n приймає кожен тригер і webhook-викликк, а також виконує відповідний workflow — усе в межах одного event loop. Queue mode розділяє цю роботу: документація n8n стверджує, що queue mode — рекомендований шлях для найкращої масштабованості, оскільки він розділяє прийом і виконання між кількома процесами. Цей розподіл стає найважливішим, коли обмежувальним фактором команди перестає бути код і стає пропускна здатність процесів.

В архітектурі queue mode документація n8n стверджує, що основний інстанс (main instance) лише приймає тригери та webhook-и, тоді як окремий інстанс worker фактично виконує сам workflow. Саме це розділення дозволяє повільному або застряглому workflow виконуватися без блокування інстансу, який слухає нові webhook-викликк або рендерить UI редактора для інших користувачів. У normal mode такої ізоляції немає: прийом і виконання змагаються за один і той самий процес.

![Як queue mode розділяє роботу: 1. Надходить тригер або webhook; 2. Завдання передається в черги; 3. Worker забирає завдання; 4. Worker виконує і повертає результат](/blog/uk/article-8045e58f-f31e-48f0-9461-4ebe1a82eeb1/eaf5d6fcd53128511baa884f776b929eeab2e555ba005d4ffa3c8902d4ab4f12.png)

Два режими також по-різному контролюють конкурентність. Документація n8n про regular mode попереджає, що надто велика кількість одночасних production-виконань може призвести до «thrashing» event loop, погіршуючи продуктивність і відгук усього інстансу. Queue mode, натомість, дозволяє команді встановити конкурентність завдань на одного worker-а окремим флагом, тож навантаження одного worker-а автоматично не стає навантаженням усієї системи. Однак ми би обережно ставилися до того, щоб брати будь-яку конкретну кількість виконань як тригер для перемикання: власна документація n8n описує механізм thrashing event loop, не називаючи конкретний обсяг, з якого він починається, тож сигналом є симптом, а не число.

## Що показує benchmark щодо пропускної здатності, відмов і бінарних даних

![Заблокована одна завантажувальна рампа стоїть поруч зі стабільною черговою рампою, що подає роботу кільком вантажникам паралельно.](/blog/uk/article-8045e58f-f31e-48f0-9461-4ebe1a82eeb1/d178d0544d0875d7615b76102ad7946a8eff9c6fe754e6cfa1535bef28d8bfab.png)

Заблокована одна рампа порівняно зі стабільною черговою рампою ілюструє, як різняться пропускна здатність і відмови під навантаженням.

Власна документація n8n про продуктивність стверджує, що один інстанс може обробляти до 220 виконань workflow за секунду, перш ніж [команді потрібно масштабуватися далі](<https://n8n-challenges.app/uk/blog/n8n-queue-mode-redis-koly-vykhodyty-z-rezhymu-odnoho-instansu>), і що багатоінстансні конфігурації покладаються на queue mode для такого масштабування. Це формулювання вже частково відповідає на питання n8n queue mode проти normal mode: normal mode не обов'язково повільний, але має стелю, пов'язану з одним процесом, а queue mode — це документований спосіб вийти за її межі.

У [benchmark масштабованості n8n 2025 року](<https://blog.n8n.io/the-n8n-scalability-benchmark/>) зафіксовано, що на інстансі c5.large увімкнення queue mode підняло пропускну здатність Single Webhook до 72 запитів за секунду порівняно з тим самим обладнанням у normal mode.

**Пропускна здатність Single Webhook за рівнем обладнання в benchmark масштабованості n8n 2025 року**

| Рівень обладнання | Пропускна здатність Single Webhook (queue mode) | Джерело |
| --- | --- | --- |
| c5.large | 72 запити за секунду | benchmark масштабованості n8n 2025 року |
| c5.4xlarge | 162 запити за секунду | benchmark n8n 2025 року на потужнішому обладнанні |

На більшому інстансі c5.4xlarge [benchmark n8n 2025 року на потужнішому обладнанні](<https://blog.n8n.io/the-n8n-scalability-benchmark/>) зафіксував стабільні 162 запити за секунду в queue mode під навантажувальним тестом K6 з поступовим зростанням до 200 віртуальних користувачів. Документація n8n подає обидва результати як власний benchmark на конкретних типах інстансів, а не як гарантію для будь-якого навантаження.

На меншому рівні обладнання той самий benchmark показав, що queue mode також знизив затримку нижче трьох секунд і усунув відмови, які normal mode показував після досягнення навантаження 200 віртуальних користувачів. Наша прагматична позиція полягає в тому, що опублікована цифра, подібна до цієї, — це відправна точка, а не число для планування: ми би запустили власний фреймворк benchmarking n8n на реальних типах workflow і обладнанні команди, перш ніж визначати розмір production-потужності, оскільки синтетичне webhook-навантаження не показує, як поведеться workflow, повний логіки розгалужень або великих payload.

Бінарні дані змінюють розрахунок. Документація n8n стверджує, що queue mode не підтримує зберігання бінарних даних на локальній файловій системі, а її посібник з конфігурації бінарних даних прямо вказує перемкнути стандартний режим зберігання бінарних даних на зберігання в базі даних, щойно команда переходить на queue mode, оскільки режим файлової системи там не підтримується. Команда, яка передає великі файли або великі webhook-відповіді через свої workflow, має запланувати цю зміну зберігання до перемикання, а не після.

## Висока доступність, обмеження за планом і що залишається незмінним

![Заблокований другий робочий стіл стоїть поруч з ідентичним обладнаним столом, символізуючи обмежену можливість високої доступності.](/blog/uk/article-8045e58f-f31e-48f0-9461-4ebe1a82eeb1/272077c10b2daa33890826e7761fdb199e3bcd0a62aa4b6bc7f8fe38c0bc46aa.png)

Заблокований другий робочий стіл символізує опцію multi-main високої доступності, доступну лише на обмежених планах.

Запуск більш ніж одного основного процесу для високої доступності — це можливість, доступна лише в queue mode, за документацією n8n, і вона обмежена self-hosted Enterprise. Команда на community або не-Enterprise self-hosted ліцензії все ще може [запускати worker-и](<https://n8n-challenges.app/uk/blog/vprava-n8n-queue-mode-z-docker-compose-dovedit-shcho-zavdannya-vykonav-vorker>), але не multi-main конфігурацію, яка усуває основний процес як єдину точку відмови.

У n8n Cloud сам queue mode обмежений планом Enterprise, і документація n8n стверджує, що його потрібно увімкнути, звернувшись безпосередньо до n8n, а не через самостійні налаштування; конкурентність там так само встановлюється на рівні worker-а — та сама логіка, що й у self-hosted queue mode.

**Normal mode проти queue mode за однаковими критеріями**

| Критерій | Normal mode | Queue mode |
| --- | --- | --- |
| Контроль конкурентності | Обмеження на весь інстанс; надто багато одночасних виконань може призвести до thrashing event loop | Флаг конкурентності на одного worker-а, встановлюється окремо від обмеження на весь інстанс |
| Ізоляція виконання | Прийом і виконання використовують один процес | Основний інстанс лише приймає тригери та webhook-и; окремий worker виконує |
| Зберігання бінарних даних | Підтримується зберігання у файловій системі | Зберігання у файловій системі не підтримується; стандарт потрібно перемкнути на зберігання в базі даних |
| Висока доступність (multi-main) | Не документовано як застосовне | Доступно, обмежено self-hosted Enterprise |
| Доступність у n8n Cloud | Стандартний режим виконання | Обмежено планом Enterprise; увімкнення через безпосереднє звернення до n8n |

Деякі речі не змінюються, коли команда перемикається. n8n за замовчуванням увімкнює очищення даних виконання (execution-data pruning) як у normal mode, так і в queue mode — це операційне налаштування не пов'язане з тим, який режим працює. Налаштування очищення та зберігання команди переживають перемикання незмінними, що на одну річ менше для перепроєктування.

## Сигнали, що настав час перемикатися, і чеклист для цього

Разом узяті, найчіткіший сигнал для оцінки n8n queue mode проти normal mode — це документоване попередження про event loop у поєднанні з реальною потребою масштабуватися на більш ніж один інстанс, а не конкретна кількість виконань. Ми оптимістично налаштовані щодо того, що команди, які перемикаються, коли ці сигнали з'являються, здебільшого беруть на себе операційні витрати, а не перепроєктування: самі workflow не змінюються, лише те, де і як вони виконуються.

Перш ніж [виділяти інфраструктуру](<https://n8n-challenges.app/uk/blog/rezhym-cherhy-n8n-na-hostinger-vps-vprava-z-byudzhetnoho-rozhortannya>), варто пройти перемикання по порядку.

- [ ] Перевірте, чи попередження про event loop уже проявляється як погіршення відгуку, а не просто як висока кількість виконань.
- [ ] Визначте, чи горизонтальне масштабування на більш ніж один інстанс дійсно потрібне, оскільки це документована причина, через яку багатоінстансні конфігурації вимагають queue mode.
- [ ] Перевірте workflow, які обробляють великі бінарні дані або webhook-відповіді, перед їх перенесенням, оскільки queue mode потребує зберігання в базі даних замість файлової системи.
- [ ] Перевірте, чи потрібна висока доступність або queue mode в хмарі (Cloud-hosted), і підтвердьте це з огляду на обмеження Enterprise-only для обох.
- [ ] Запустіть власний фреймворк benchmarking n8n на реальних типах workflow та обладнанні, а не покладайтесь лише на опубліковані цифри benchmark.
- [ ] Перегляньте налаштування очищення та зберігання даних виконання, оскільки вони переносяться незмінними, і їх варто налаштувати правильно в будь-якому разі.

Документація n8n не називає єдиного порогу обсягу виконань, який би зобов'язував перемикатися, тож рішення залишається суб'єктивною оцінкою, побудованою на цих сигналах, а не фіксованим правилом.

Sources: [Control concurrency | Deploy | n8n Docs](<https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/control-concurrency>), [Measure performance | Deploy | n8n Docs](<https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/measure-performance>)
