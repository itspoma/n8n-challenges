## Мета й передумови

Дослідження роботи токена оновлення OAuth у n8n починається з правильно підключених облікових даних. Цей посібник допоможе підготувати робочий процес із HTTP Request поза виробничим середовищем для отримання списку файлів Google Drive і пояснить, як класифікувати збої авторизації.

Вам знадобляться робочий простір n8n, доступ до налаштувань проєкту Google Cloud і обліковий запис Google для авторизації. Як редакційний запобіжний захід ми радимо використовувати окремий тестовий обліковий запис і власний клієнт OAuth. Документація не вказує версію чи редакцію n8n для цих інструкцій із налаштування.

На нашу думку, чітке розмежування налаштування й перевірки робить цю підготовчу вправу кориснішою.

## 1. Підготуйте налаштування авторизації Google

![Два шаблони замкової щілини показують суміщені та зміщені отвори поруч із рожевим ключем.](/blog/uk/article-44b9c2b2-b1d2-44e5-b0c8-aa373765e936/ccdfdd05ac3c360a24d346b5eaa984914fbe01a44199a4b2e6fe34dcf0320900.webp)

Суміщені та зміщені замкові щілини ілюструють вимогу Google щодо точного збігу URI перенаправлення.

Документація n8n із налаштування Google та документація Google щодо OAuth для вебсерверів визначають наведену нижче послідовність підготовки. Скопіюйте URI перенаправлення з налаштувань облікових даних n8n, а не складайте його самостійно.

1. Створіть або виберіть проєкт Google Cloud для підключення.
2. Увімкніть Google Drive API та налаштуйте екран згоди OAuth.
3. Створіть клієнт OAuth типу Web application.
4. Зареєструйте URI перенаправлення, показаний у n8n, точно, включно зі схемою, регістром і кінцевою скісною рискою.
5. Якщо застосунок має статус Testing, додайте потрібний обліковий запис Google як тестового користувача.

Для цієї вправи ми пропонуємо область доступу drive.file, яку n8n зазначає серед підтримуваних областей для облікових даних Google OAuth2 generic. Посібник Google з авторизації Drive описує цю область як доступ до файлів, створених за допомогою застосунку, відкритих у ньому або наданих йому для спільного доступу. Вона не надає переліку всіх файлів Drive облікового запису.

## 2. Перевірте підключення облікових даних для токена оновлення OAuth2 у n8n

![Замкнена капсула з’єднана рожевим кабелем із порожнім блоком із роз’ємом.](/blog/uk/article-44b9c2b2-b1d2-44e5-b0c8-aa373765e936/420f84c55ea3ab83efd98242ae358e395d5ebd93b9de454b77caf98b2b46eae9.webp)

Замкнена капсула та підключений блок ілюструють приєднання збережених облікових даних OAuth до вузла HTTP Request.

Використайте для цього підключення облікові дані Google OAuth2 generic у n8n. Введіть ідентифікатор клієнта Google та секрет клієнта, а для області доступу вкажіть drive.file від Google: використайте HTTPS із хостом www.googleapis.com і шляхом /auth/drive.file. Виконайте Sign in with Google, а потім збережіть налаштування. Ці облікові дані підтримують лише області доступу, перелічені n8n; вони не є взаємозамінними з необмеженими універсальними обліковими даними OAuth2.

Налаштуйте вузол HTTP Request за наведеними нижче кроками. На нашу думку, явний вибір облікових даних — кращий початок, ніж спроби виправити автентифікацію додаванням заголовків.

1. Установіть для HTTP Request метод GET. Використайте HTTPS із хостом www.googleapis.com і шляхом /drive/v3/files.
2. Залиште тіло запиту порожнім.
3. У полі Authentication виберіть Predefined Credential Type, як тип облікових даних укажіть Google OAuth2 API та явно виберіть збережені облікові дані Google OAuth2 generic.
4. Зберігайте секрети в облікових даних, а не в полях запиту. Не замінюйте їх на Header Auth із токеном доступу: це обходить механізм оновлення OAuth.

## 3. Підготуйте перевірку за розкладом і визначте її межі

![Рожевий механічний таймер стоїть поруч із лотком для файлів і напівпрозорою блакитною перегородкою.](/blog/uk/article-44b9c2b2-b1d2-44e5-b0c8-aa373765e936/5a1948637fa88e917460be3bf4ca614962373f3410a77dec5161891748d9ee32.webp)

Таймер, лоток для файлів і перегородка ілюструють вправу з отримання списку файлів Google Drive за розкладом.

Додайте Schedule Trigger, налаштуйте його Trigger Rules і Trigger Interval, а потім збережіть та опублікуйте підготовлений робочий процес. Це базові інструкції з налаштування розкладу; вони не визначають прив’язку до конкретного часу чи поведінку щодо пропущених запусків.

Визначте очікуваний результат API, перш ніж розглядати це як вправу з оновлення токена: довідка Google щодо files.list описує успішну відповідь із масивом files. Порожній масив може відповідати доступу drive.file. Цитовані перекладені довідкові матеріали Drive попереджають про можливі помилки перекладу.

Стаття n8n про автентифікацію API за 2026 рік описує автоматичне оновлення токенів доступу OAuth2 для API, що дотримуються стандартної поведінки OAuth2. Під час перевірки токена оновлення OAuth у n8n сам по собі успішний запит за розкладом не дає змоги відрізнити оновлення від повторного використання ще чинного токена доступу. Ця вправа готує конфігурацію, але не перевіряє оновлення. Як редакційну рекомендацію пропонуємо записувати категорії результатів без конфіденційних даних, наприклад «авторизацію відхилено» або «список отримано».

## 4. Діагностуйте збої в правильному порядку

![З’єднувач, замкові щілини, ворота й запечатана капсула лежать поруч із рукою, яка кладе зелену деталь у формі позначки.](/blog/uk/article-44b9c2b2-b1d2-44e5-b0c8-aa373765e936/c5cfa7a608963d1d52a15f7e2f3cc87941885f7d23c3ecc5136e155c44bad884.webp)

З’єднувач, замкові щілини, ворота доступу й запечатана капсула ілюструють рівні, які слід перевіряти під час діагностики збоїв OAuth.

Якщо виникла проблема з токеном оновлення OAuth у n8n, [перевірте ці рівні, перш ніж змінювати бізнес-логіку робочого процесу](<https://n8n-challenges.app/uk/blog/nalahodzhuyte-vorkflou-n8n-persh-nizh-zvynuvachuvaty-intehratsiyu>). Наведені нижче задокументовані причини Google — це відправні точки для діагностики, а не вичерпне пояснення збоїв авторизації.

**Перевірки для відновлення облікових даних і авторизації**

| Рівень | Ознака | Виправлення |
| --- | --- | --- |
| Підключення вузла | Для Authentication установлено none | Виберіть автентифікацію OAuth і облікові дані |
| Перенаправлення | redirect_uri_mismatch | Забезпечте точний збіг із зареєстрованим URI перенаправлення |
| Згода | Відмовлено в доступі в режимі Testing | Додайте потрібного тестового користувача |
| Клієнт | invalid_client | Повторно введіть відповідні ідентифікатор і секрет клієнта |

Приклад Google для вебсервера запитує офлайн-доступ, щоб отримати токен оновлення, і попереджає, що він повертається лише під час першої авторизації. Це не доводить, що ваші облікові дані n8n містять такий токен. Вихідний код n8n у гілці master, не прив’язаний до конкретної версії, вказує на необхідність повторного підключення, коли строк дії токена доступу минув, а токен оновлення відсутній; установлені версії можуть показувати інше формулювання.

Документація Google щодо OAuth за 2026 рік зазначає, що зовнішні застосунки зі статусом Testing отримують токени оновлення зі строком дії сім днів, крім випадків, коли області доступу обмежені зазначеними Google областями ідентифікації. Відкликання доступу та політики організації також можуть спричинити збій оновлення. Ми радимо не визначати причину лише за часом, що минув.
