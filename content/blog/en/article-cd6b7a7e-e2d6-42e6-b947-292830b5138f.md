## Decide first: SAP-native or external approval

An SAP approval workflow does not have to live in n8n. SAP S/4HANA Cloud Public Edition has a native flexible workflow for purchase requisitions, and SAP's best-practice test script for one scope item (version 2608) checks that a scenario-based workflow is active for document type NB. Any external design has to account for that.

Our recommendation is editorial, not a documented rule: use n8n only for approvers or channels SAP cannot reach, such as external approvers or chat-based approval. In our view, adding a second approval engine next to a working native one usually creates more confusion than convenience.

There is also an open question to know about before you build. A July 2026 SAP Community thread asked whether a standard API can trigger the purchase requisition approval workflow. The only reply was an unvetted forum answer with no accepted solution. It suggested a BAdI check or holding the requisition in an external app, and warned that SAP would have no visibility until the data is pushed.

## Pause and resume in n8n

![Checklist beside a padlock and clock showing a protected Wait node resume URL with timeout in n8n](/blog/en/article-cd6b7a7e-e2d6-42e6-b947-292830b5138f/e9f0ae2acd4c87931ae8c79106f8e5c72272b84036f15c56ab823c29196973cd.webp)

A checklist beside a padlock and clock, showing the safeguards around the Wait node resume step.

[The n8n Wait node](<https://n8n-challenges.app/en/blog/the-n8n-wait-node-handling-retries-and-rate-limited-apis>) pauses an execution and offloads its execution data to the database, according to the n8n docs. It can resume after a time interval, at a set time, on a webhook call, or on a form submission. The docs page does not state a version and does not cover SAP.

In the On Webhook Call mode, n8n generates a per-execution resume URL that you can send to a third-party service or an email. It can be protected with Basic, Header or JWT auth. The docs warn that partial executions change the resume URL, so test in full executions.

The Wait node can also limit wait time so the workflow resumes by itself, and it can restrict callers by IP allowlist, returning 403 to others. The docs do not prescribe an approval-timeout policy, so the first four checklist items below are our editorial suggestions for a SAP approval workflow; the last is a documented n8n warning.

- [ ] Protect the resume URL with Header or JWT auth
- [ ] Add an IP allowlist for callers
- [ ] Set a wait limit with an escalate-up or safe-halt fallback
- [ ] Never auto-approve on timeout for financial objects
- [ ] Test in full executions, not partial ones

In our view, a Header or JWT-protected resume URL plus an IP allowlist is the minimum for anything that touches finance.

Sources: [Wait | Nodes | n8n Docs](<https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.wait>)

## SAP approval workflow configuration: access and write-back

![Interlocking pieces for communication user, system and arrangement used for SAP S/4HANA OData access](/blog/en/article-cd6b7a7e-e2d6-42e6-b947-292830b5138f/0f2b58257e00dda1f37e4b9e74f59e18eb43599209de1a7379076e20cbd89d96.webp)

Interlocking pieces showing how communication user, system and arrangement fit together for API access.

SAP S/4HANA Cloud Public Edition (version 2608 docs) provides OData V2 and V4 and SOAP APIs, discoverable on SAP Business Accelerator Hub. Access is set up through communication scenarios and arrangements. An SAP example for another scenario, SAP_COM_0837, shows the sequence of communication user, system and arrangement, and notes that a wrong endpoint URL causes authentication failure. It shows the pattern only; roles differ per scenario.

Authentication methods include Basic, x509, OAuth2 and SAML SSO, but each API supports different ones, so check the specific API on the Hub. In n8n, the HTTP Request node recommends predefined credential types where they exist, with generic Basic, Header and OAuth2 credentials for other APIs. Whether client credentials suit your arrangement depends on the arrangement.

Before building, confirm that your object has a released approve or reject operation. The 2608 listing shows Approve and Reject for Purchase Contracts (Version 2) and for Service Entry Sheets (Lean Services), but the truncated text does not say whether these are OData. For purchase requisitions it shows a V4 API with read, update and validate, and the V2 API as deprecated.

No supplied official SAP source shows a released OData operation to approve or reject a purchase requisition from outside SAP, so this article does not claim one. Nothing here was tested firsthand, and several SAP help pages are truncated. Check the Hub for your own object.

## Write the decision back safely

![Sequence of fetching a CSRF token, reading an ETag and sending an OData update from n8n](/blog/en/article-cd6b7a7e-e2d6-42e6-b947-292830b5138f/b46e30474d75271b7cff445f50f0443d6bc65b4f7b628a9d274b509d5f52de67.webp)

A left-to-right sequence of the write-back steps: token, read, update.

Modifying calls such as POST [need a CSRF token](<https://n8n-challenges.app/en/blog/n8n-csrf-token-handling-prepare-a-sap-gateway-sandbox-write>) on S/4HANA Cloud Public Edition (2608). The client fetches it with a non-modifying call that sends the X-CSRF-Token header set to Fetch, then reuses it on the modifying request. SAP's page is written for another service, so n8n-specific handling is not covered.

Updates use [optimistic concurrency with ETags](<https://n8n-challenges.app/en/blog/sap-odata-etag-handling-an-editorial-n8n-exercise-before-retrying>). The client must send the previously received ETag, and a mismatch returns an error and no change. SAP's general error list includes 403 Forbidden, 412 Precondition Failed (the resource changed, read again) and 428 Precondition Required (send an if-match header). Whether a given approval API needs an ETag is not stated.

## Error handling, idempotency and fallback

A community demo from SAP Inside Track Ankara 2026, published in a community GitHub repository, shows the general pattern: a CAP webhook to n8n, an IF threshold, Telegram send-and-wait, then approve or reject written back through OData V4 actions. It used a local CAP mock with n8n 2.x, not S/4HANA, so it demonstrates the pattern only. The author describes the webhook as fire-and-forget and the actions as idempotent.

The same demo notes that SAP does not depend on n8n: orders are created even if n8n is down, with status staying pending, and an error workflow alerts on failures. No official source states how S/4HANA Cloud Public Edition delivers an outbound approval event to n8n, so that trigger remains an open item.

As an editorial suggestion, keep the write-back step re-runnable. On 412, re-read the object and retry once; on 403, stop and alert rather than retry. In our view, an Error Trigger workflow should exist before the first production approval, not after the first failure.

Sources: [GitHub - gzmilgar/sap_n8n: SAP CAP + n8n live demo: order approval loop with Telegram human-in-the-loop and an AI agent over OData (SAP Inside Track Ankara 2026) · GitHub](<https://github.com/gzmilgar/sap_n8n>), [APIs on SAP Business Accelerator Hub | SAP Help Portal](<https://help.sap.com/docs/SAP_S4HANA_CLOUD/0f69f8fb28ac4bf48d2b57b9637e81fa/1e60f14bdc224c2c975c8fa8bcfd7f3f.html>)

## Governance and audit

![Generic technical user badge compared with an append-only ledger of named approvers for SAP approvals](/blog/en/article-cd6b7a7e-e2d6-42e6-b947-292830b5138f/b1dd82b733fadc5dadf4a14db15b74b3232033bc8ecfba21b59ea9c97ccf90e1.webp)

A generic badge set against a ledger of named signatures, contrasting a technical user with a recorded human approver.

The technical user is what SAP will see. An SAP Community blog from 2025 on SAP Build Process Automation, which is not S/4HANA OData, reports that calling a task-completion API with client credentials shows the form as approved by a generic user based on the client ID. Treat it as a caution about attribution when you use service credentials.

A 2026 SAP Community blog by an SAP AI Solution Architect on human-in-the-loop agents recommends audit entries that record inputs, reasoning, decision, reviewer and affected SAP objects, kept append-only. It also says a timeout fallback of proceed should never be used for financial postings. This is one author's design opinion for another stack, not an SAP standard.

No SAP-specific audit requirements were supplied, so the rest is editorial: use a dedicated communication user per scenario rather than a shared dialog user, and record the human approver in n8n execution data and in a separate append-only log.

Sources: [How to Approve/Reject Task via API in SAP Build Pr... - SAP Community](<https://community.sap.com/t5/technology-blog-posts-by-sap/how-to-approve-reject-task-via-api-in-sap-build-process-automation/ba-p/14012313>), [Human-in-the-Loop SAP Agents: Approval, Escalation... - SAP Community](<https://community.sap.com/t5/artificial-intelligence-blogs-posts/human-in-the-loop-sap-agents-approval-escalation-and-audit-series-2-part-5/ba-p/14372994>)

## Recommended design and open items

Our suggested SAP approval workflow design: confirm the native workflow does not fit, read the object from SAP, pause in the Wait node with an authenticated resume URL and a timeout, then fetch the CSRF token, read the ETag and write the decision back. Test it in a non-production tenant first.

Open items to settle on your tenant: whether your object has a released approve or reject operation (see the configuration section), which authentication method that API supports, and how the approval request reaches n8n.
