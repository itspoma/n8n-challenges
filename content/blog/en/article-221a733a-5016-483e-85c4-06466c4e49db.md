## Your API contract testing task and boundaries

This editorial exercise uses API contract testing to answer a narrow question: does a controlled response contain the fields your proposed write needs? Build three Code nodes named Mock response, Check contract and Simulated write. Your task is to let compatible responses reach a write marker and stop incompatible responses before it.

Prerequisites are an editable n8n development workflow and basic JavaScript. n8n documents generating mock data with Code or Edit Fields nodes. Use synthetic data only: no credentials, external API requests or real writes. The supplied documentation specifies no n8n version or edition, so it does not establish universal runtime or plan compatibility.

The fixtures, algorithm and expected results below are proposed learning material, not an executed or validated workflow. These are handwritten JavaScript assertions, not JSON Schema or a provider-verified consumer-driven contract. HTTP status handling, regression infrastructure, rollback and production deployment are outside this exercise.

## Prepare an API contract testing example

![Success and incompatible response fixtures shown as matching and mismatched objects in specimen boxes.](/blog/en/article-221a733a-5016-483e-85c4-06466c4e49db/a137f5b94d56ab303f88e885329ee2c28347ed75a4efc813fd548e57411be293.webp)

The contrasting specimen boxes represent compatible and incompatible synthetic response fixtures.

Use an editorial envelope containing fixtureName and body. In Mock response, return one fixture per run as an array containing an object whose json property holds that envelope. n8n requires object-valued json inside its array-of-items structure; a correct wrapper alone does not validate the embedded response.

The proposed success contract requires body to be a non-null, non-array object with its own id string and amount number. Allow unrelated extra fields and do not coerce values. We think a useful practice contract should express what the consumer needs, rather than freeze every field the provider happens to return.

Use these suggested fixtures. Give each its row name as fixtureName; the table shows the body value and proposed outcome.

**Editorial fixtures and expected outcomes, not observed results**

| Fixture | body | Expected outcome |
| --- | --- | --- |
| baseline | {"id":"order-a","amount":12} | Write marker |
| extra-field | {"id":"order-a","amount":12,"note":"ok"} | Write marker |
| missing-id | {"amount":12} | Contract error: id |
| string-amount | {"id":"order-a","amount":"12"} | Contract error: amount |
| null-body | null | Contract error: body |
| array-body | [] | Contract error: body |
| upstream-error | {"error":{"code":"RATE_LIMITED","message":"Try later"}} | Upstream error |
| missing-code | {"error":{"message":"Try later"}} | Contract error: error.code |
| wrong-message | {"error":{"code":"RATE_LIMITED","message":12}} | Contract error: error.message |

## Build the contract check before the marker

![Mock response, contract check and simulated write represented by three physical stations.](/blog/en/article-221a733a-5016-483e-85c4-06466c4e49db/fd6af1075c872ef3736fd006162989a4dcf2f134d87b0742c87e15fe11ca4f5f.webp)

The three stations represent the proposed mock, validation and marker sequence.

Set Check contract to Run Once for All Items and read const items = $input.all(). n8n documents this mode and input accessor. Implement the following suggested algorithm, examining every item before returning anything.

1. Loop over items, reading each item's json.fixtureName and json.body.
2. Reject body when it is null, typeof body is not "object", or Array.isArray(body) is true.
3. If Object.hasOwn(body, "error"), require error to be a non-null, non-array object. Require its own code and message properties to have typeof "string".
4. For malformed error objects, throw new Error with the fixture name, "Contract error" and the failed field. For a valid error shape, throw an "Upstream error" containing the fixture name and error.code.
5. Otherwise require Object.hasOwn(body, "id") and typeof body.id === "string"; require Object.hasOwn(body, "amount") and typeof body.amount === "number". Throw a descriptive contract error for either failure.
6. Only after the entire loop finishes, return items. Do not return accepted items from inside the loop.

Object.hasOwn() distinguishes an own property from an absent or inherited one; presence still needs a value check. JavaScript typeof reports both null and arrays as objects, so guard against them explicitly. Confirm Object.hasOwn() is available in your runtime.

Set the validator's On Error option to Stop Workflow: n8n documents that it prevents further node execution after an error. Continue instead proceeds with the last valid data. Stopping does not undo earlier writes, which is why this exercise places its marker after validation.

## Run separately and record completion evidence

![A single response fixture enters a testing jig beside a notebook for recording execution observations.](/blog/en/article-221a733a-5016-483e-85c4-06466c4e49db/4b203c78ea9da1e82fe2c7aedb722e900d7af2e351751532dafe3d23a0fe7131.webp)

Testing one fixture at a time makes its diagnostic and marker observation easier to record.

In Simulated write, use $input.all().map(item => ({json: {wouldWrite: true, id: item.json.body.id}})) as the returned value. This marker is solely an exercise artifact. Run the complete sequence separately for every fixture and record the observed diagnostic and whether the marker node executed.

Use the checklist below as suggested completion criteria for API contract testing. In our view, the decisive observation is whether execution reaches the marker after rejection; a readable error message alone is insufficient.

- [ ] Complete an observation record for every fixture, including its diagnostic and whether Simulated write executed.
- [ ] Compare every recorded outcome against the fixture table.
- [ ] Confirm from each rejected fixture's current execution that it never reached Simulated write.

If an unexpected marker appears, inspect the validator's On Error setting and whether it throws before returning. If Code output fails, inspect the array wrapper and object-valued json. If null or arrays pass, revisit the body guards rather than relying on typeof alone.

## Reflect on what passing mocks establishes

For this API contract testing exercise, the suggested solution is a full-input validation pass followed by a separate marker node. Reflect on why an added field is allowed, why a well-formed upstream error still blocks the marker, and which required fields your actual consumer would need.

Passing these mocks cannot prove that a live provider still conforms. Martin Fowler's 2011 article Contract Test distinguishes testing against a double from checking whether the external service matches it. Treat your recorded results as evidence about these fixtures and this workflow configuration.
