## The n8n per-user credential theft announcement

![A colleague’s workflow branches toward an editor’s error workflow beside a credential drawer.](/blog/en/article-42b73df4-e99a-4736-ba20-5ac7258fb568/14ada6f9248fd0c32a800ceb5e71011b58d458a3d023b91f99dbc2e9dd81ac13.webp)

Two branching tracks connect workflows with different owners beside a credential drawer.

The n8n per-user credential theft advisory published on October 14, 2026 describes a vulnerability involving an error workflow inheriting another user’s identity. The official announcement, GHSA-pcr3-v5vr-qppf, identifies fixed versions and recommends upgrading.

The exposure described involves a project editor pointing a colleague’s workflow at an error workflow the editor owns. When the colleague’s workflow failed, the inherited user identity could allow the editor to resolve the colleague’s per-user credential secrets. This describes a possible attack path; the advisory does not report observed theft, exploitation prevalence or affected customer counts.

In our view, the important permission boundary here is who can [choose the error workflow](<https://n8n-challenges.app/en/blog/build-an-n8n-error-workflow-and-attach-it-to-a-production-workflow>) for someone else’s automation. Teams should treat that decision as a security concern alongside the recovery logic itself.

Sources: [Per-User Credential Theft via Error-Workflow Execution Context Inheritance · Advisory · n8n-io/n8n · GitHub](<https://github.com/n8n-io/n8n/security/advisories/GHSA-pcr3-v5vr-qppf>)

## What changed in n8n execution context inheritance

![Two recovery trays contrast an identity badge traveling with data and a badge kept outside the tray.](/blog/en/article-42b73df4-e99a-4736-ba20-5ac7258fb568/133876719d8e30f9ac1b1db24b03c4d569631be03f60e9b3d11d5176bbd7fd9c.webp)

The trays illustrate the distinction between identity information and other execution fields.

For the affected error-workflow execution path, the announcement says the error workflow now receives only non-identity fields. That is the stated change to n8n execution context inheritance. The advisory does not enumerate those fields or describe compatibility effects.

The n8n per-user credential theft announcement identifies n8n 2.42.2 and 2.41.5 as containing the fix and instructs users to upgrade to one of those versions or later. Its affected-version fields separately list versions below 2.42.2 and below 2.41.5, without explaining branch selection.

Our editorial suggestion is to have the instance owner identify the installed version and release branch before [planning the upgrade](<https://n8n-challenges.app/en/blog/n8n-current-version-when-and-how-should-a-self-hosted-team-upgrade>). The announcement provides no installation-specific upgrade procedure, so this article does not supply deployment commands.

## n8n error workflow security: upgrade and temporary measures

![An administrator fits a replacement gate into an n8n workflow track beside removable barriers.](/blog/en/article-42b73df4-e99a-4736-ba20-5ac7258fb568/4a5f044c09a5d9066d83f866c240cc663e58892f6ecf6fc5e5560abc2d739afb.webp)

A replacement gate and removable barriers illustrate upgrading alongside temporary restrictions.

For the n8n per-user credential theft risk covered by this announcement, upgrading is the recommended action. If upgrading is delayed, the advisory tells administrators to consider the temporary measures below. They do not fully remediate the risk.

- [ ] Consider restricting instance access to fully trusted users.
- [ ] Consider removing untrusted project editors.
- [ ] Check active workflows’ settings.errorWorkflow values.
- [ ] Consider disabling dynamic credentials if they are unnecessary.

We would prioritize assigning responsibility for the upgrade over treating temporary restrictions as a finished fix. That is our practical recommendation, separate from the announcement’s listed measures.

Sources: [Per-User Credential Theft via Error-Workflow Execution Context Inheritance · Advisory · n8n-io/n8n · GitHub](<https://github.com/n8n-io/n8n/security/advisories/GHSA-pcr3-v5vr-qppf>)

## What the announcement leaves unstated

The announcement does not state which editions or hosted plans are affected, or whether hosted instances were patched automatically. Its publication date does not establish when exploitation began or when patches first became available.

It also does not provide credential-rotation instructions, [incident-response procedures](<https://n8n-challenges.app/en/blog/n8n-security-breach-checklist-what-to-check-and-lock-down-first>), a detailed audit procedure or a verification test. Those details cannot be inferred from the announced fix.
