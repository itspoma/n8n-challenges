## What the n8n SQL Injection Microsoft SQL Node Advisory States (September 30, 2026)

GitHub's official security advisory database published a new n8n SQL injection Microsoft SQL node entry on September 30, 2026, tracked as GHSA-5qpp-pqww-h7fp. The listing states that the vulnerability sits in n8n's Microsoft SQL node and results from expression interpolation into the query field, and GitHub rates the severity as High. The entry credits a contributor named Matsuuu with the report.

This advisory page functions as a listing entry rather than a full write-up: it names the title, the GHSA identifier, the publish date, the severity rating and the reporting contributor. The detailed advisory body describing exact impact, exploitation conditions or proof-of-concept steps is not present in what we could retrieve, so this article cannot summarize content that simply isn't there.

Sources: [Security Advisories · n8n-io/n8n · GitHub](<https://github.com/n8n-io/n8n/security/advisories>)

## Background: What Expression Interpolation Into the Query Field Means

![n8n SQL injection Microsoft SQL node data flowing from unchecked form input to a query field.](/blog/en/article-e2f3fd41-e7c8-4273-b880-b45105ad25ee/02c121158ac56e717c9f621fd92c330e5142a7f621b2cc61101153a590ed9e7d.png)

A conceptual view of how an unfiltered expression can carry outside input into a SQL query field.

n8n's own documentation describes the Microsoft SQL node as a way to run SQL queries and to insert, update or delete rows in Microsoft SQL databases from inside a workflow.

In n8n, an expression lets someone building a workflow insert a dynamic value, such as data from a webhook, a form or a previous node, into a field instead of typing a fixed value. When a query field accepts an expression and the resolved value is interpolated directly into the SQL text sent to the database, unescaped input can change the structure of that query. This explanation is the article's own general description of that mechanism, commonly called an n8n expression interpolation vulnerability, and is not detail drawn from the advisory body itself. The GHSA-5qpp-pqww-h7fp title names this exact mechanism for the Microsoft SQL node.

Sources: [Security Advisories · n8n-io/n8n · GitHub](<https://github.com/n8n-io/n8n/security/advisories>), [Microsoft SQL | Nodes | n8n Docs](<https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.microsoftsql>)

## What Readers Should Do Now

The suggestions below are this article's own editorial judgment, not steps stated by the advisory itself.

- [ ] Treat any workflow that feeds expression-built input into the Microsoft SQL node's query field as potentially exposed until n8n publishes fuller advisory details
- [ ] Tighten who can create or edit workflows, as a general precaution while affected versions and a workaround remain unpublished
- [ ] Search existing workflows for expressions that carry webhook, form or API response data straight into the Microsoft SQL node's query field
- [ ] Bookmark the GHSA-5qpp-pqww-h7fp page and revisit it for the affected-version list, patched release and any workaround n8n adds
- [ ] If your team lacks capacity to track advisories like this promptly, have someone independently review your n8n instance for this and similar injection risks

Anyone who finds or suspects a related issue can report it through n8n's Vulnerability Disclosure Program, described on the project's official security overview page, though that reporting channel doesn't itself confirm details of this specific advisory.

## How This Fits With n8n's Other Recent SQL Injection Advisories

This isn't the first Microsoft SQL node vulnerability n8n has disclosed in 2026. An earlier advisory, published February 25, 2026, described a different SQL injection issue affecting the Microsoft SQL, MySQL and PostgreSQL nodes, caused by unescaped identifier values such as table or column names rather than by query-field expression interpolation.

For that earlier issue, n8n described temporarily disabling the affected nodes through an [environment variable](<https://n8n-challenges.app/en/blog/n8n-environment-variables-and-credentials-shared-instance-checklist>) as a stopgap while a patch was prepared, not as a permanent fix.

That February 2026 issue later received a formal CVE entry, in the U.S. National Vulnerability Database, months after its GitHub advisory first went live. No CVE status is stated for the September 30, 2026 advisory in the sources we could retrieve, so the two should not be treated as the same finding.
