## Define the SAP OData pagination goal and prerequisites

![A service cabinet, keyring and notebook represent prerequisites for Business One Orders extraction.](/blog/en/article-1ed33368-4e7c-4f60-b9a0-cb53f5188840/248f76c0990c78a001873c281d22baa9b389faa4282a58c2b6b03c3ee6d32742.webp)

Begin with an identified deployment and authenticated access.

This tutorial scopes SAP OData pagination to read-only Orders extraction from an existing SAP Business One 10.0 Service Layer deployment. The goal is to [follow continuation links within explicit request bounds](<https://n8n-challenges.app/en/blog/n8n-loop-over-items-pagination-debugging-paginated-api-pulls>), then check rows and document keys before downstream processing. The supplied documentation supports the individual controls, but not a complete runnable workflow across authentication, relative-link resolution, completion settings and downstream blocking; those details require deployment-specific verification.

Record your actual Business One patch level, hosting arrangement, Service Layer endpoint and n8n HTTP Request node version. SAP's Business One 10.0 reference identifies OData V3 as deprecated from FP 2405 and retains OData V4 guidance. SAP demonstrates Orders retrieval through /b1s/v2/Orders.

Start with an approved, authenticated read already working in n8n. SAP documents HTTPS and session continuity through SessionID and ROUTEID cookies; n8n requires the authentication method expected by the target service. This tutorial assumes that continuity is already established for successive requests.

## Choose the query and inspect one Orders response

![Matching filter stencils cover order records and count tokens for the extraction query.](/blog/en/article-1ed33368-4e7c-4f60-b9a0-cb53f5188840/9a80eedaa7c6b0f852290d94cd3a51321daf2e16d4f2000aaa523d8ec8e3913b.webp)

Use the same filter for the Orders extraction and its source count.

For this SAP OData pagination example, use an editorial extraction contract: one approved Orders filter, DocEntry plus the fields needed downstream, ordering by DocEntry, and a separate count request with the identical filter. SAP documents $select, $orderby and collection counts through /Orders/$count.

Follow these preparation steps before enabling repeated requests. DocEntry is identified as a unique document key in SAP Business One 10.0 DI API documentation; SAP's Service Layer lesson separately demonstrates addressing an order by that key. Confirm its presence in your actual Orders response.

1. Write down the extraction filter and reuse it unchanged for the data and count requests.
2. Select DocEntry and the required downstream fields; order the extraction by DocEntry.
3. Fetch one approved Orders page and inspect its value array and continuation annotation.
4. Record the matching source count and the observed response shape for reconciliation.

Inspect the continuation annotation rather than copying its spelling from an example. SAP's protocol-specific guidance names @odata.nextLink for V4 and odata.nextLink for V3, while its retrieval lesson uses inconsistent terminology. We think inspecting the returned payload is a better starting point than adapting a familiar pagination template.

## Configure bounded next-link pagination

![Page bundles and continuation ribbons meet a stop block beside an hourglass for bounded pagination.](/blog/en/article-1ed33368-4e7c-4f60-b9a0-cb53f5188840/a51203bd4ca2753477b38ec7a83210ba83462ebd7e56ff49be6a5c14b963c96d.webp)

A request ceiling bounds work even when another page remains.

In HTTP Request, enable Pagination and choose Response Contains Next URL. Supply a Next URL expression that reads the continuation field observed in your response. Preserve the server-provided continuation query parameters. If the link is relative, verify its resolution against your deployment before proceeding; the supplied documentation does not establish handling for both root-relative and service-relative links.

For a populated final page without a continuation annotation, n8n's reference recommends custom completion based on that field being absent. The same reference gives conflicting guidance about automatic termination on falsy next URLs. Verify the completion setting in your installed node version rather than treating an empty next URL as sufficient.

Set explicit bounds using the controls below. Choose their values with the SAP service owner. Our practical preference is to stop and investigate a capped run rather than release its partial output.

**Documented request controls and their limits**

| Control | Purpose | Limit |
| --- | --- | --- |
| limitPagesFetched and maxRequests | Enable a hard request cap | Does not prove completion |
| requestInterval | Delay between requests | Not documented as a completion check |
| Timeout | Bound waiting for response headers | Not a total workflow deadline |

Preserve page-level evidence before splitting: whether a continuation remains, which continuation values were seen, and whether the configured ceiling was reached.

## Reconcile orders and troubleshoot before release

![Record slips, unique key tokens and count beads sit before a release gate for order reconciliation.](/blog/en/article-1ed33368-4e7c-4f60-b9a0-cb53f5188840/9a5fafc0f9ae0a923e984cb65510539763aa98ae93d81ba0d6566e6bffa13014.webp)

Compare rows, unique keys and the matching source count before releasing orders.

After preserving pagination evidence, [use Split Out with Field to Split Out set to value to separate each page's order array](<https://n8n-challenges.app/en/blog/transform-nested-json-into-simple-records-in-n8n>). Wrapped responses need this explicit handling. n8n's Code node supports JavaScript and Run Once for All Items, making it a possible location for custom reconciliation logic; the supplied documentation does not establish the complete collection, empty-result and blocking implementation.

Use this suggested editorial acceptance rule for SAP OData paging: release only when pagination completed, every row has DocEntry, retrieved rows equal distinct DocEntry values, and both equal the matching source count. Matching these checks does not establish a transactionally consistent snapshot. We regard reconciliation as a release condition, not a completeness guarantee.

The following are suggested troubleshooting checks, not tested outcomes. For an empty extraction, require explicit pagination completion and a matching zero source count before accepting it.

- [ ] Normal completion: confirm the final response has no continuation annotation.
- [ ] Unexpected missing annotation: compare the actual payload with the selected OData protocol before accepting completion.
- [ ] Ceiling reached: inspect the final continuation and configured request cap; for repeated continuation, compare successive returned links.
- [ ] Authentication failure: have the deployment owner verify session continuity across requests.
- [ ] Missing or duplicate DocEntry values: inspect the collected rows.
- [ ] Count mismatch: check filter equality and investigate source changes during extraction.
