## How to use this n8n workflow review checklist

This n8n workflow review checklist is for the moment a teammate says their workflow is ready and asks you to look before it goes live. It covers five areas: error handling, failure-path testing, credentials, naming and monitoring. It finishes with a sign-off step.

Here is our editorial rule for what done means: a check counts only when you have seen it yourself in the workflow. The author telling you it is done does not count. For example, open Workflow Settings and look at which error workflow is selected.

Each item in this n8n workflow review checklist is tagged as either an n8n feature fact or a team convention. None of these are mandatory standards. Only the error workflow, Error Trigger and Stop And Error items come from the official n8n documentation; everything else is practitioner advice. No source measures whether reviews reduce incidents, so any benefit described is the authors' own view. Treat the conventions as a starting point that your team adapts.

Sources: [Handle errors gracefully | Build | n8n Docs](<https://docs.n8n.io/build/flow-logic/handle-errors-gracefully>)

## Error handling and failure-path testing

![A finger tips a pink domino in a pastel domino run that ends at a small bell beside a name tag](/blog/en/article-c2f9353a-306d-4b60-aa33-df3f830d1b47/83d313d7a7f5f2e0bd277cc45773e6fc8b4823a1fd6f826bd97be6f328ebf9fb.png)

Conceptual illustration of forcing a failure with Stop And Error to test the alert path.

Start with what happens when something breaks. A practitioner post by Ciphernutz on DEV Community says that by default a failed node stops the execution and marks it as an error, and nobody is alerted unless someone has set that up. That silent failure is what this section tries to prevent.

The feature fact: according to the n8n documentation, [you set an error workflow for each workflow in Workflow Settings](<https://n8n-challenges.app/en/blog/build-an-n8n-error-workflow-and-attach-it-to-a-production-workflow>). It runs when an execution fails and must start with the Error Trigger node. The docs page does not say which version or plan this applies to. The documented Stop And Error node forces an execution to fail under conditions you choose, and that failure triggers the error workflow. Using it to test the alert path is our suggestion, not a test method the docs describe.

**Forcing a failure to test the alert path**

1. **Add Stop And Error**: Put the node on a test branch with a condition you control.
2. **Run the workflow**: Trigger the condition so the execution fails on purpose.
3. **Error workflow fires**: The linked workflow starts from its Error Trigger node.
4. **Confirm the alert**: Check that the named owner actually received it.
5. **Remove the test**: Take the forced failure out before go-live.

The conventions: Till Freitag's 2026 pre-go-live checklist includes confirming the global error workflow is linked. Ciphernutz recommends [turning on Retry on Fail for every external HTTP call](<https://n8n-challenges.app/en/blog/retrying-failed-n8n-http-requests-safely>). HatchWorks' 2026 production checklist says to test failure paths on purpose with bad input, expired credentials and API timeouts, not only the happy path.

- [ ] Error workflow selected in Workflow Settings (feature fact)
- [ ] Error workflow starts with the Error Trigger node (feature fact)
- [ ] One failure forced with Stop And Error, and the alert arrived (suggestion)
- [ ] Retry on Fail on for external HTTP calls (convention)
- [ ] Bad input sent and the result checked (convention)
- [ ] Expired credential tried (convention)
- [ ] API timeout simulated and the behaviour checked (convention)

## Credentials and naming

![Two key rings with blue and pink tags kept apart by a divider, next to small boxes with handwritten labels](/blog/en/article-c2f9353a-306d-4b60-aa33-df3f830d1b47/c9f483f87bb98b8945d95d896c239ac0efe60d38439207b8372a62d8adaa755d.png)

Conceptual illustration of separate staging and production credentials and descriptive names.

Next, check what the workflow connects to and whether the next person can read it. Both items are team conventions from Till Freitag's 2026 best-practices article, which is based on the author's own experience rather than a study. n8n does not require either of them.

On credentials, the article recommends keeping staging and production credentials separate. When you review, open each node that uses a credential and check it points to the credential meant for production, not one someone used while building.

On naming, it recommends naming nodes after what they do, not after their node type. A suggested example: a node called Fetch open orders tells a reviewer more than one called HTTP Request2. Our suggestion: apply the same idea to the workflow name so the list of workflows stays easy to scan.

**Suggested naming examples (editorial, not a standard)**

| Default-style name | Descriptive name |
| --- | --- |
| HTTP Request2 | Fetch open orders |
| IF | Is order valid? |
| Edit Fields | Map order to invoice fields |

Sources: [n8n Best Practices – 10 Rules for… – Till Freitag](<https://till-freitag.com/en/blog/n8n-best-practices-guide-en>)

## Monitoring and sign-off

An alert only helps if someone owns it. HatchWorks' 2026 checklist says failure alerts should go to a named channel with a named owner. HatchWorks' checklist goes on to cover [more observability practices](<https://n8n-challenges.app/en/blog/self-hosted-n8n-production-readiness-checklist>), which this article does not include.

Then close the n8n workflow review checklist. Our editorial recommendation is to write down the result and who owns the workflow, so responsibility passes clearly from the builder to whoever runs it. Formal code-review processes, n8n's version history, RBAC and SSO are outside the scope of this checklist.

- [ ] Alerts go to a named channel (convention)
- [ ] A named person owns those alerts (convention)
- [ ] Review result recorded: approved or changes needed (suggestion)
- [ ] Workflow owner recorded and handed over (suggestion)
