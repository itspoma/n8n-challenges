## Inventory your n8n data redaction controls

Start your n8n data redaction review by identifying which controls your deployment supports. n8n documents execution redaction for Enterprise on Cloud and self-hosted deployments: workflow controls require n8n 2.16.0 or later, and instance enforcement requires n8n 2.26.0 or later. The checklist below is suggested operating guidance, not a compliance standard or a report of firsthand testing.

Workflow sharing is documented for all Cloud plans and self-hosted Business and Enterprise. Creators and editors can view executions, while instance owners and admins can view all workflows; [project membership also affects access](<https://n8n-challenges.app/en/blog/rbac-meaning-in-n8n-when-a-small-team-needs-it>). Complete this inventory before choosing test accounts.

- [ ] Record deployment type, plan and installed n8n version.
- [ ] List workflow collaborators and relevant project memberships.
- [ ] Identify ordinary viewers and accounts with privileged access.
- [ ] Record which documented redaction controls apply.

## Prepare synthetic markers and a visibility matrix

The paired stations illustrate the suggested comparison between ordinary and privileged execution viewers.

We think a conspicuous fake secret is a better starting point than a realistic customer record. Use these suggested test inputs: a synthetic email, a token-like string, a nested marker and a harmless attachment. Keep destinations controlled and avoid real credentials or personal information.

Create the following test matrix and inspect saved records through Overview > Executions or an accessible project. n8n provides Success and Failed status filters. For each category, compare an ordinary collaborator with a privileged account, recording marker visibility in node inputs, outputs and error details.

## Verify Enterprise redaction and reveal access

Use the applicable workflow controls and instance enforcement identified in your inventory. Configure production and manual redaction independently in workflow Settings. Changing them requires the applicable enable or disable permission scopes. Where instance enforcement applies, owners and admins can enforce a floor through Settings > Security; workflow controls cannot weaken that floor.

Repeat your n8n data redaction matrix. In eligible Enterprise executions, node JSON, binary payloads and error details are hidden, while status, timing, node names, error type and HTTP status code remain available. Users with execution:reveal can temporarily reveal data; owners and admins have this scope by default. Dynamic-credential executions cannot be revealed.

- [ ] Record production and manual redaction settings separately.
- [ ] Verify ordinary-viewer results against the baseline.
- [ ] Check privileged reveal separately where supported.
- [ ] Verify reveal and enforcement audit events reach the intended log-streaming destination.
- [ ] Confirm useful execution metadata remains visible.

## Minimize payloads and choose what gets saved

![Hands select necessary workflow fields while keeping an attachment pouch separate for the n8n binary inclusion decision.](/blog/en/article-334e89c7-c6c4-460f-9e8d-43218e70dc0e/6f413a34c574d8a1e3be8e85249e0f0436044b3e68269ce5a3a2a0a8a9475e48.webp)

Selecting fields and handling attachments separately illustrates the payload decisions to review before passing data onward.

n8n’s Help Center guidance, updated in 2026, recommends reducing payloads early and provides separate saving choices for successful production, failed production and manual executions. Edit Fields offers Keep Only Set Fields to discard unused input fields, with a separate option for binary inclusion. Reducing a later node’s output does not establish that earlier execution records are clean.

Our practical preference is to decide which fields a workflow needs before deciding [how much execution history to keep](<https://n8n-challenges.app/en/blog/n8n-execution-data-retention-a-self-hosted-ops-checklist>). Use these suggested checks to document both decisions; disabling saving reduces persisted history but does not necessarily reduce runtime memory.

- [ ] Define the fields needed at each handoff.
- [ ] Review Keep Only Set Fields and binary inclusion.
- [ ] Inspect earlier nodes for synthetic markers.
- [ ] Choose saving settings for each run category independently.
- [ ] Explain every missing test record using its saving setting.

## Check boundaries beyond the execution viewer

n8n data redaction does not encrypt or change stored execution data. Viewer checks therefore cannot establish database protection or deletion. This review also does not implement backup deletion, a complete retention policy or regulatory compliance.

As separate suggested checks, search for synthetic markers in Code-node logs and controlled webhook responses, and inspect what reaches controlled outbound destinations. Record each observation without assuming viewer redaction covers that path. n8n’s Help Center guidance recommends avoiding sensitive information in logs and execution metadata.

## Preserve diagnostics and record completion

n8n’s Help Center guidance recommends retaining failed executions when their details are needed for debugging. Before disabling failed-execution saving, document how the team will investigate failures using approved context, such as status, timing, node identity and non-sensitive correlation values. Reproduce failures only against controlled destinations.

Use the following suggested completion criteria to turn observations into an owned decision.

- [ ] Save the completed test matrix and account roles.
- [ ] Record selected controls and unresolved exposure paths.
- [ ] Approve the diagnostic fields and failure-investigation approach.
- [ ] Assign an owner to each unresolved item.
