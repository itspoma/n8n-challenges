## Your n8n CSV import task and prerequisites

![A disposable storage drawer, paper file and sender represent the CSV exercise prerequisites.](/blog/en/article-e6f97419-45b2-4076-99ab-31b22f41ceaa/bd9b75d15864c1dd6f22af4d67c43cc5596d5875b5d5696e21a574ac2e611fc9.webp)

A separate destination and synthetic input define the exercise workspace.

This editorial exercise asks you to design an n8n CSV import that keeps identifiers intact, accounts for rejected records and verifies stored results. The proposed workflow and completion criteria have not been executed or validated. Your task is complete when every input record has one classification and the stored records match the accepted records.

Prepare an n8n workspace, a CSV-capable HTTP sender and an empty, disposable Data Table. Create String columns named customer_id, name and email. n8n documents typed Data Table columns, including String. Data Tables are project-scoped storage for light to moderate use; these sources establish no universal minimum version or plan entitlement for this complete exercise.

Use synthetic records only. We think a disposable destination makes this practice more useful: it lets learners focus on explaining every record before deciding how a shared import should behave.

## Receive the n8n CSV file and inspect identifiers

![A magnifying glass spans two matching bead strings for the CSV identifier check.](/blog/en/article-e6f97419-45b2-4076-99ab-31b22f41ceaa/3679949fa32b03ed38b128d83fa0bc8b634c1493253f418d6926db74460fd9b5.webp)

Compare identifiers immediately after parsing before allowing records to proceed.

Create a CSV with the headers and literal values below, representing each Empty cell as an empty CSV field. This suggested fixture contains five data records; the header is excluded from the count. Treat customer_id as an exact identifier, and require all three fields to contain non-whitespace text. Email-format validation is outside this exercise.

**Suggested synthetic CSV fixture; Empty means an empty field.**

| customer_id | name | email |
| --- | --- | --- |
| 00127 | Ada | ada@example.invalid |
| 00420 | Ben | ben@example.invalid |
| 00127 | Ada repeat | repeat@example.invalid |
| 00009 | Empty | missing@example.invalid |
| Empty | Cy | cy@example.invalid |

Configure a Webhook to receive binary input, then connect Extract From File using CSV extraction. Match the Webhook's receiving binary property to the extractor's input field. For the test URL, select Listen for test event before sending your n8n CSV file; production uses a distinct URL and requires publishing.

Inspect the parsed customer_id values immediately against the original CSV. The cited CSV extraction documentation does not establish whether CSV extraction preserves numeric-looking identifiers or which parser setting guarantees it. Stop if 00127 becomes 127. A String destination or later conversion cannot restore lost characters; resolve ingestion before proceeding.

## Classify records and reconcile before loading

![Record slips occupy separate trays for accepted, invalid and duplicate CSV records.](/blog/en/article-e6f97419-45b2-4076-99ab-31b22f41ceaa/981488a066cf0fa3a7eba1be279598229e9f4cd7d990a97cb0b9923d19d30293.webp)

The three trays represent mutually exclusive classifications retained for reconciliation.

After the identifier check passes, use Edit Fields for explicit mapping and discard unused fields if appropriate. n8n documents custom JavaScript in the Code node and conditional routing with If. The following suggested algorithm for your n8n CSV import is an editorial design for you to implement and verify.

Keep accepted, invalid and duplicate arrays plus a summary in one Code output item. Preserve original field values and a source-record index, and attach rejection reasons. Follow this order so each record belongs to exactly one category; account for [n8n's documented item-linking requirements](<https://n8n-challenges.app/en/blog/tracing-n8n-item-linking-errors-why-item-fails-and-how-to-fix-it>) when input and output item counts differ.

1. Initialize empty category arrays and a set of accepted customer_id values.
2. Inspect each record in source order; classify missing required values as invalid first.
3. For a valid record, classify an already-seen customer_id as duplicate; otherwise accept it and remember its identifier.
4. Calculate category counts and return the arrays and summary together, even when accepted is empty.

For the fixture, the expected editorial result is five input records: two accepted, two invalid and one duplicate. Before Insert, use If to evaluate input count = accepted count + invalid count + duplicate count. Route a mismatch to Stop And Error; only the matching branch may proceed toward insertion. Test an additional all-invalid fixture: retain its rejection arrays and summary, and skip insertion when accepted is empty.

Remove Duplicates documents current-input deduplication across selected fields following its n8n 1.64.0 overhaul; earlier versions need their corresponding documentation. It documents removal rather than a rejected-duplicate output. In our view, explicit classification is the better learning choice here because the exercise asks you to explain rejected records.

## Complete the n8n Data Table import and reflect

![A hand compares tokens from an open drawer and a reference tray for the Data Table readback check.](/blog/en/article-e6f97419-45b2-4076-99ab-31b22f41ceaa/1f2691d23f778abc347487e5b1694f9a9dfb569085cab264b47edf62fd9c57af.webp)

Readback checks compare the destination with the accepted records.

For this n8n Data Table import, CSV records must pass the pre-load gate before you send only accepted records to Insert and map each column manually. Read back the destination with Return All while other writers remain paused; n8n warns that concurrent changes can cause omissions or repeats during paginated reads. Compare the stored count and exact identifier values with the accepted array, then check name and email values.

If your n8n CSV import produces missing rows or a count mismatch, inspect the saved classifications, insertion inputs and readback settings before rerunning. The operations reference notes version-dependent behavior, warns that plain Insert can duplicate records on reruns and describes empty outputs when filtering removes every item. An empty branch alone is insufficient completion evidence.

After loading, use a separate If check to compare the readback count and field values with the accepted records, routing any mismatch to Stop And Error. Failure does not establish rollback of earlier writes. Production locking, transaction guarantees and partial-write recovery are outside this isolated exercise. Finish by recording the following suggested reflection decisions.

- [ ] Save the fixture, classifications, summary and readback comparison as completion evidence.
- [ ] Name the owner who approves required fields and duplicate-key rules.
- [ ] Choose append-only, skip-existing or update-existing behavior before adapting the workflow.
- [ ] Explain how you would investigate partial writes before authorizing another run.
