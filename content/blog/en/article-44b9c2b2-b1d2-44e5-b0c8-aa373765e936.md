## Goal and prerequisites

An n8n OAuth refresh token investigation starts with a correctly connected credential. This tutorial prepares a non-production HTTP Request workflow for a Google Drive listing and explains how to classify authorization failures.

Have an n8n workspace, access to Google Cloud project settings, and a Google account available for authorization. As editorial precautions, we suggest a dedicated test account and custom OAuth client. The documentation does not specify an n8n release or edition for these setup instructions.

We think keeping the boundary between configuration and verification explicit makes this a more useful preparation exercise.

## 1. Prepare Google's authorization settings

![Two keyway templates show aligned and misaligned openings beside a pink key.](/blog/en/article-44b9c2b2-b1d2-44e5-b0c8-aa373765e936/ccdfdd05ac3c360a24d346b5eaa984914fbe01a44199a4b2e6fe34dcf0320900.webp)

Aligned and misaligned keyways illustrate Google's requirement for an exact redirect URI match.

n8n's Google setup documentation and Google's web-server OAuth documentation establish the preparation sequence below. Copy the redirect URI from your n8n credential configuration rather than reconstructing it.

1. Create or select the Google Cloud project for the connection.
2. Enable the Google Drive API and configure the OAuth consent screen.
3. Create a Web application OAuth client.
4. Register the redirect URI shown by n8n exactly, including scheme, case and trailing slash.
5. If the app is in Testing, add the intended Google account as a test user.

For this exercise, our suggested scope is drive.file, which n8n lists among the supported scopes for its Google OAuth2 generic credential. Google's Drive authorization guide describes this scope as access to files created by, opened with, or shared with the app. It does not provide an inventory of the account's entire Drive.

## 2. Check n8n OAuth2 refresh token credential wiring

![A locked capsule is joined by a pink cable to a blank block with a socket.](/blog/en/article-44b9c2b2-b1d2-44e5-b0c8-aa373765e936/420f84c55ea3ab83efd98242ae358e395d5ebd93b9de454b77caf98b2b46eae9.webp)

A locked capsule and connected block illustrate attaching the saved OAuth credential to the HTTP Request node.

Use n8n's Google OAuth2 generic credential for this connection. Enter the Google client ID and client secret, and set the scope to Google's drive.file scope: use HTTPS with host www.googleapis.com and path /auth/drive.file. Complete Sign in with Google, then save. This credential supports only the scopes listed by n8n; it is not interchangeable with unrestricted generic OAuth2.

Configure the HTTP Request node using the following steps. In our view, explicit credential selection is a better starting point than trying to repair authentication by adding headers.

1. Set the HTTP Request method to GET. Use HTTPS with host www.googleapis.com and path /drive/v3/files.
2. Leave the request body empty.
3. Set Authentication to Predefined Credential Type, choose Google OAuth2 API as the credential type, and explicitly select the Google OAuth2 generic credential you saved.
4. Keep secrets inside credentials rather than request fields. Do not substitute Header Auth containing an access token: that bypasses OAuth refresh handling.

## 3. Prepare a scheduled check and define its limits

![A pink mechanical timer stands beside a file tray and a translucent blue partition.](/blog/en/article-44b9c2b2-b1d2-44e5-b0c8-aa373765e936/5a1948637fa88e917460be3bf4ca614962373f3410a77dec5161891748d9ee32.webp)

A timer, file tray and partition illustrate the scheduled Google Drive listing exercise.

Add a Schedule Trigger, configure its Trigger Rules and Trigger Interval, then save and publish the prepared workflow. These are basic scheduling instructions; they do not establish clock alignment or catch-up behavior.

Define the expected API result before treating this as a renewal exercise: Google's files.list reference documents a successful response containing a files array. An empty array can be consistent with drive.file access. The cited translated Drive references warn of possible translation errors.

n8n's 2026 API authentication article describes automatic OAuth2 access-token refresh for APIs following standard OAuth2 behavior. For an n8n OAuth refresh token check, a successful scheduled request alone cannot distinguish renewal from reuse of a still-valid access token. This exercise prepares configuration without verifying renewal. As an editorial suggestion, record sanitized outcome categories such as authorization rejected or listing returned.

## 4. Diagnose failures in the right order

![A connector, keyways, gate and sealed capsule sit beside a hand placing a green check-shaped piece.](/blog/en/article-44b9c2b2-b1d2-44e5-b0c8-aa373765e936/c5cfa7a608963d1d52a15f7e2f3cc87941885f7d23c3ecc5136e155c44bad884.webp)

A connector, keyways, permission gate and sealed capsule illustrate the layers to inspect when diagnosing OAuth failures.

For an n8n OAuth refresh token problem, [work through these layers before changing the workflow's business logic](<https://n8n-challenges.app/en/blog/debug-n8n-workflows-before-blaming-the-integration>). The documented Google causes below are diagnostic starting points, not an exhaustive explanation of authorization failures.

**Credential and authorization recovery checks**

| Layer | Signal | Correction |
| --- | --- | --- |
| Node wiring | Authentication set to none | Select OAuth authentication and the credential |
| Redirect | redirect_uri_mismatch | Match the registered redirect URI exactly |
| Consent | Testing access denied | Add the intended test user |
| Client | invalid_client | Re-enter matching client ID and secret |

Google's web-server example requests offline access to obtain a refresh token and warns that it is returned only on first authorization. This does not prove that your n8n credential contains one. The unpinned n8n master source instructs reconnection when an expired access token has no refresh token available; installed releases may expose different wording.

Google's 2026 OAuth documentation states that external apps in Testing receive refresh tokens expiring after seven days, except when scopes are limited to its specified identity scopes. Revocation and organizational policies can also cause refresh failure. We'd avoid diagnosing the cause from elapsed time alone.
