## Editorial exercise: define your response contract

This n8n Respond to Webhook exercise asks you to build a POST endpoint with explicit JSON responses for three outcomes. It is an editorial assignment based on documented capabilities; the proposed solution and expected results have not been executed or validated.

You need an accessible n8n environment, workflow-editing access and curl 7.82.0 or later, which supports --json for sending POST requests. Use synthetic data and the test webhook while developing. The supplied n8n documentation is mostly undated and not pinned to a release, so check settings against your installation.

Use the following editorial response contract. Inputs must be syntactically valid JSON objects; malformed JSON, authentication failures and infrastructure failures are outside this assignment.

**Proposed inputs and required caller-visible responses**

| Case | JSON input | Status | JSON response |
| --- | --- | --- | --- |
| Success | {"name":"Ada"} | 200 | {"ok":true,"message":"Hello, Ada"} |
| Invalid input | {} | 400 | {"ok":false,"error":{"code":"INVALID_INPUT"}} |
| Handled failure | {"name":"Ada","simulateFailure":true} | 500 | {"ok":false,"error":{"code":"PROCESSING_FAILED"}} |

## Suggested solution: validate, then process

![A validation gate and processing crank separate invalid input from a handled processing failure.](/blog/en/article-0e8d8264-b0c6-434d-a512-92584356f57f/cce0d31830d2a3fe2c1bd76a29f9b6644938f1acb63e75b7615d713d16871858.webp)

The objects distinguish validation from processing and its separate failure path.

Set the Webhook method to POST and its response mode to Using 'Respond to Webhook' Node. Connect it to a JavaScript Code node. The supplied moving-master Webhook implementation exposes the request payload under body; this is not a guarantee for every installed release, so [inspect your Webhook output](<https://n8n-challenges.app/en/blog/tracing-a-missing-n8n-webhook-field>) before using that path.

For the validation Code node, use Run Once for All Items and this proposed JavaScript: const b = $input.first().json.body; const valid = b !== null && typeof b === 'object' && !Array.isArray(b) && typeof b.name === 'string' && b.name.trim().length > 0; return [{ json: { valid, name: valid ? b.name.trim() : '', simulateFailure: valid && b.simulateFailure === true } }];

Add an IF node that tests whether valid is true. Send false to the invalid-input response. Send true to a processing Code node, also running once for all items, with this proposed JavaScript: const d = $input.first().json; if (d.simulateFailure) throw new Error('Exercise failure'); return [{ json: { ok: true, message: 'Hello, ' + d.name } }];

Configure the processing node to continue using its separate error output, represented as continueErrorOutput in the supplied reference. Wire its normal output to the success response and its error output to the failure response. This handles that node's failure, not whole-workflow timeouts, crashes outside nodes or failures elsewhere without wired error outputs. We think separating validation from processing makes the response contract easier to reason about.

## Configure n8n Respond to Webhook JSON bodies

![Three envelopes represent n8n Respond to Webhook JSON responses for success, invalid input and handled failure.](/blog/en/article-0e8d8264-b0c6-434d-a512-92584356f57f/3a9516433ef546fc1ce7de6444cb61553f3dabec81bee1b3e97024b2e63e083c.webp)

Each envelope represents a separate response body and status configured in the exercise.

Create three terminal n8n Respond to Webhook nodes. In each, select JSON under Respond With and set Response Code explicitly using the corresponding opening contract row. The table below adds the body configuration detail; the success expression reads the processing node's current JSON item.

**Suggested body configuration for the opening contract**

| Response node | Response Body configuration |
| --- | --- |
| Success | Expression: {{ $json }} |
| Invalid input | Fixed JSON from the invalid-input contract row |
| Handled failure | Fixed JSON from the handled-failure contract row |

Keep the failure body fixed rather than exposing exception details. In our view, callers should receive a stable public error contract, while internal diagnostics belong in the team's debugging process.

## Test each caller-visible result

![Hands compare three webhook replies with expected-result templates during response testing.](/blog/en/article-0e8d8264-b0c6-434d-a512-92584356f57f/292d30aea603a013d461e3604cf398fa6345bed0675ec04fc2228fdd964f81fd.webp)

Comparing replies with expectations represents the manual checks learners are asked to perform.

Select Listen for test event before sending a request, rearming the listener before subsequent requests as needed. In these proposed commands, replace TEST_URL with the node's test URL. curl --json does not validate your JSON; -i includes response headers alongside the body.

1. Send success input: curl -i --json '{"name":"Ada"}' 'TEST_URL'
2. Send invalid fields: curl -i --json '{}' 'TEST_URL'
3. Send controlled failure: curl -i --json '{"name":"Ada","simulateFailure":true}' 'TEST_URL'

For each request, record the HTTP status, headers, JSON body and executed response branch. Compare the results with the assignment contract; manually inspecting them does not establish automated coverage or JSON validity.

## n8n Respond to Webhook not working? Trace the branch

If the caller receives something unexpected, use this [suggested diagnostic checklist](<https://n8n-challenges.app/en/blog/n8n-webhook-not-working-a-step-by-step-debugging-checklist>). A workflow that finishes without executing n8n Respond to Webhook returns n8n's standard message with status 200; that fallback fails this exercise's explicit response contract.

- [ ] Confirm POST, the selected test URL and the listening state.
- [ ] Confirm the Webhook delegates its response to Respond to Webhook.
- [ ] Inspect the Code output's array and json object structure.
- [ ] Follow the IF outputs to their intended destinations.
- [ ] Check both the processing error setting and its error-output connection.
- [ ] Inspect each response node's JSON body and explicit status.

Completion means all three inputs reach their intended response nodes and match the required statuses and bodies. For reflection, explain why invalid fields and a processing exception deserve separate outcomes, and why acknowledging a request early cannot promise completed processing.

Keep this exercise synchronous and short. n8n Cloud documents a 524 response when an incoming webhook receives no response within 100 seconds; other infrastructure and callers may impose different deadlines. Treat that limit as a boundary, not a timing target.
