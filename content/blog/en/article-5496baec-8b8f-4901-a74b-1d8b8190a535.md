## Your n8n Compare Datasets exercise

This editorial exercise uses n8n Compare Datasets to reconcile an invented CRM export with a destination snapshot. Your task is to explain every classification and write a proposed-action list, without updating a destination. The n8n Team’s comparison template provides the starting pattern: manually run a workflow that compares generated datasets using a shared field.

Prerequisites are access to an n8n environment with Compare Datasets and basic node-editing skills. Use synthetic records only; production credentials are unnecessary for this task. [CSV ingestion](<https://n8n-challenges.app/en/blog/n8n-csv-import-an-exercise-in-validation-and-reconciliation>), live CRM connectors and automated duplicate detection are outside its scope.

The controls described here come from n8n’s undated master-branch implementation, including Compare Datasets node version 2.3; it does not identify an installed n8n release. Inspect your installed node version before following those controls. This editorial exercise has not been executed or validated; its expected classifications are proposed acceptance criteria.

## Prepare the synthetic inputs and inspect keys

![CRM record folders show distinct, duplicated and missing matching keys before comparison.](/blog/en/article-5496baec-8b8f-4901-a74b-1d8b8190a535/e455f7677d3637ef630d613101876ed2a3863710afc4612ad68577b94a7f1b0e.webp)

Folder tabs illustrate the manual key-quality checks required before this exercise’s comparison.

Use Input A for the CRM export and Input B for the destination snapshot. Create separate items with the fields crm_id, name and email, keeping all values as strings. This table supplies the invented teaching inputs; “Absent” means omit that record from that input.

**Invented CRM and destination records for the exercise**

| crm_id | name | Input A email | Input B email |
| --- | --- | --- | --- |
| C-101 | Ada | ada@example.invalid | ada@example.invalid |
| C-102 | Bo | bo.new@example.invalid | bo.old@example.invalid |
| C-103 | Cy | cy@example.invalid | Absent |
| C-104 | Dee | Absent | dee@example.invalid |

Before comparison, manually list the crm_id values on each side. For this exercise, require nonempty keys, consistent key types and uniqueness within each input. Then make a separate duplicate-key variant by copying A’s C-102 record and changing its email. Identify the repeated key and remove the extra record before continuing; do not treat Compare Datasets as a duplicate detector.

We think deciding what identifies a record deserves more attention than deciding which fields changed. A comparison is only useful when the team can explain why two records belong together.

## Configure matching and retain both versions

The n8n Compare Datasets node pairs records through configured matching fields, then compares their remaining fields in n8n’s undated master-branch implementation, including node version 2.3. Use the following suggested setup for this exercise.

1. Connect the synthetic CRM items to A and the destination items to B.
2. Match crm_id on A to crm_id on B.
3. Select Include Both Versions so you can inspect the changed pair.
4. Keep Fuzzy Compare disabled and leave Fields to Skip Comparing empty. Record a reason if you later exclude a field.
5. Connect the four outputs to review-only NoOp nodes, following the warehouse-audit template’s inspection pattern.

For node version 2.3, Fuzzy Compare tolerates small type differences, such as a number and its string representation. That does not establish text similarity, case normalization or whitespace cleanup. The same implementation exposes Multiple Matches controls; those controls do not establish that duplicate keys are safe.

## Review outputs and investigate unexpected classifications

The n8n Team’s SQL comparison template describes four categories: only in A, only in B, the same and different. Apply those categories to your synthetic CRM exercise using the proposed expectations below. The action labels are editorial suggestions, not synchronization rules.

**Proposed classifications and review actions**

| Record | Expected category | Proposed action |
| --- | --- | --- |
| C-101 | Same | No-action candidate |
| C-102 | Different | Review email change |
| C-103 | Only in A | Proposed addition |
| C-104 | Only in B | Destination-only review |

If you find n8n Compare Datasets not working as expected, first inspect A/B orientation, matching-field names, missing or duplicate keys, key types and unintended comparison fields. Change one synthetic input at a time and record its classification rather than assuming undocumented edge-case behavior.

In our view, a destination-only record should prompt a question before it prompts an action. We would leave deletion decisions outside this exercise.

## Complete the exercise and reflect

Lucas Peyrin’s warehouse-audit template supports inspecting comparison categories through NoOp nodes; that review pattern does not establish production synchronization correctness. Use this editorial completion checklist.

- [ ] Account for every supplied record and explain its category.
- [ ] Inspect both versions of C-102 and identify the email difference.
- [ ] Include your key-inspection notes.
- [ ] Write a proposed-action list, including unresolved review items.
- [ ] Confirm that no destination-write nodes are connected.

For reflection, consider these suggested design questions: Which system has authority over each field? What policy would authorize deletion? Who must approve proposed changes before production updates? Your answers define further design work; this exercise stops at review.
