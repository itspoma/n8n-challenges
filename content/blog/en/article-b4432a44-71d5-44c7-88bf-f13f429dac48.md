## Your n8n lookup table exercise

Build an n8n lookup table that prepares a payload only when an incoming label has exactly one reference row, an approved code and an unexpired mapping. This is an editorial exercise based on documented capabilities: its fixtures, algorithm and expected results are proposals, with no supplied execution or validation.

Use synthetic data in your own n8n environment. You need Data Tables, permission to create a table, and familiarity with JavaScript Code nodes and IF branching. n8n documents Data Tables for workflow lookups and [CSV import](<https://n8n-challenges.app/en/blog/n8n-csv-import-an-exercise-in-validation-and-reconciliation>), but the supplied documentation establishes no minimum version or plan; check that your environment exposes the feature. Tables are project-scoped and intended for light to moderate storage.

Finish at separate eligible-payload and review outputs. HTTP configuration, authentication, actual writes and destination enforcement are outside scope. Completion means every input identifier appears exactly once, with the expected disposition below.

## Suggested solution: preserve ambiguity before checking expiry

![One hand lifts a token over a partly hidden token; a second tray holds two exposed tokens beside an hourglass.](/blog/en/article-b4432a44-71d5-44c7-88bf-f13f429dac48/9d07c5c2fbcda847630d75e2925524fb9d933e7ad682cbeed9a39cab9a0ad8d9.webp)

Keeping duplicate mappings visible preserves the ambiguity that selecting a first match would hide.

Use this suggested serial arrangement: Incoming records → Get reference rows → Build index → Evaluate. Make Incoming records a Code node returning one item whose json contains a records array with all seven identifier-and-label objects. Get reference rows retrieves every row with a nonempty label and Return All enabled. n8n's Code guidance supports joining reference data to another dataset and returning workflow items as an array of { json: ... } objects.

Run Build index once for all items. Group $input.all() rows by exact label in a JavaScript Map named index, retaining arrays of complete reference rows, and return [{ json: { byLabel: Object.fromEntries(index) } }]. Economy's array must contain both rows. Run Evaluate once for all items: read the index from $input.first().json.byLabel and the original records from $('Incoming records').first().json.records. For each record, retrieve candidates with byLabel[record.label] ?? []. Iterate that records array, not the reference rows, so Unknown also receives a result. These worked examples show the proposed workflow items.

**Editorial worked evaluations and proposed workflow items**

| Input | Evaluation | Result item |
| --- | --- | --- |
| r1: Express | One match; EXP approved; expiry later than evaluation time | {"json":{"identifier":"r1","label":"Express","eligibility":true,"reason":"eligible","payload":{"identifier":"r1","apiCode":"EXP"}}} |
| r2: Economy | Two matches; reject before code or expiry checks | {"json":{"identifier":"r2","label":"Economy","eligibility":false,"reason":"ambiguous"}} |

For dates, n8n documents that values pass between nodes as strings and require parsing. In JavaScript, use Luxon DateTime.fromISO with an explicit UTC zone, inspect isValid, and compare toMillis() values. Luxon 3.7.2 documentation lists validity inspection and timestamp conversion; it does not establish the version bundled with your installation. [Explicit UTC timestamps](<https://n8n-challenges.app/en/blog/n8n-date-formatting-a-pre-write-exercise>) avoid relying on workflow timezone interpretation.

We think ambiguity deserves its own rejection reason: selecting a convenient row hides the decision the learner needs to inspect. Follow this proposed validation order.

1. Group reference rows by exact label into arrays, preserving every duplicate. A JavaScript Map can hold each label and its array.
2. For each incoming record, retrieve its matches. Emit missing for zero matches and ambiguous for more than one; stop evaluating that record.
3. For the single match, require a string apiCode whose trimmed value is nonempty and whose original value belongs to the declared approved-code set. Otherwise emit invalid_code.
4. Parse expiresAt. Emit invalid_expiry when parsing is invalid; otherwise emit expired when its timestamp is less than or equal to the evaluation timestamp.
5. Emit one { json: result } item per input. Keep its identifier and label, eligibility and reason. Add payload containing the identifier and mapped apiCode only when eligible; otherwise omit payload and apiCode.

## Route results and inspect completion

Configure IF to send eligibility equal to true to the payload output and everything else to review. Suyash Raj's 2026 commercial implementation guide describes IF branching for valid and invalid records. Set node errors to Stop Workflow, which n8n documents as halting execution. Business rejections still require the explicit rules above.

Use Execute step to inspect lookup and validation outputs separately. Compare results against these editorial acceptance checks.

- [ ] Express alone reaches the eligible output with payload.apiCode equal to EXP.
- [ ] Economy, Legacy, Broken and Unknown reach review with ambiguous, expired, invalid_expiry and missing respectively.
- [ ] Blank and Boundary reach review with invalid_code and expired respectively.
- [ ] All seven identifiers occur exactly once across both outputs; rejected items contain no payload or apiCode.
- [ ] The retrieved reference output retains both Economy rows, and no route bypasses validation.

## Reflect on the mapping decision

If results differ, inspect retrieved row counts, duplicate grouping, exact label spelling and parsed expiry values. Keep normalization out unless you explicitly apply the same rule to both datasets.

Explain what would happen if one Economy row expired but the other remained current. Under this exercise's rules, counting duplicates comes first, so the mapping remains ambiguous. Then explain why choosing the first match or supplying a default code would violate the contract.

In our view, an n8n lookup table should expose unresolved choices before a payload leaves the gate. This exercise does not establish atomicity with a later API write or protect against reference changes after lookup.
