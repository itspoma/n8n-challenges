## Before You Start: What This n8n Security Breach Checklist Assumes

If you suspect an n8n security breach, the order you act in matters as much as what you do. This checklist walks through what to check and lock down first, synthesized from n8n's own documentation and from third-party incident-response writing into one ordered sequence.

It assumes you still have administrative access to the instance, that you can reach the server or cloud workspace directly, and that you're responding to a specific suspicion rather than running a general audit of n8n security concerns, since not every n8n security breach looks the same. Some steps below depend on which n8n edition or plan you run; each is named where it applies.

Sources: [Rotate encryption keys | Deploy | n8n Docs](<https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/rotate-encryption-keys>)

## Step 1 — Contain: Cut Off Outside Access First

![A padlock closes over a server rack gate, showing an n8n instance being sealed off from outside access.](/blog/en/article-49768a92-7a4a-492b-a88b-d78f56571e55/95024825ea60286dd5fe9e0a4fba289fba07f9fd62d9d8c8422b00abff1ff3ae.png)

Disabling outside access is the first move before any investigation begins.

Before auditing anything, cut off outside access. n8n's own documentation describes disabling the public API as a way to stop others from using the n8n public REST API, and taking that step first keeps an attacker from reaching the instance again while you investigate. Treat the instance as still exposed until you've confirmed otherwise.

In our view, debating root cause before access is cut off just extends the window an attacker has; contain first, diagnose second.

- [ ] Disable the public API
- [ ] Take the instance off the public internet or behind a VPN
- [ ] Pause or disable any public-facing webhooks
- [ ] Revoke any shared admin session you can't account for
- [ ] Record the time containment started for your incident notes

Sources: [Security | Deploy | n8n Docs](<https://docs.n8n.io/deploy/host-n8n/configure-n8n/security>)

## Step 2 — Rotate n8n's Own Secrets (Encryption Key, Tokens, Sessions)

Once outside access is cut, rotate n8n's own secrets before trusting anything already logged in. On self-hosted n8n, the [encryption key](<https://n8n-challenges.app/en/blog/n8n-environment-variables-and-credentials-shared-instance-checklist>) can be rotated, but n8n's documentation notes this feature isn't available on n8n Cloud and instructs administrators to take a full database backup before enabling it, since rotation is a one-way migration.

**Encryption key rotation availability by deployment**

| Deployment | Availability | Note |
| --- | --- | --- |
| Self-hosted n8n | Available | Back up the database first; rotation is a one-way migration, per n8n's documentation. |
| n8n Cloud | Not available | n8n's documentation states this feature isn't offered on Cloud. |

Beyond the encryption key, Gridinsoft's 2026 incident-response guidance, reporting GitGuardian's research, instructs responders to revoke every exposed n8n API or MCP token and to rotate connected secrets at their source rather than only at the n8n level.

Sources: [Rotate encryption keys | Deploy | n8n Docs](<https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/rotate-encryption-keys>), [Leaked n8n API Tokens: 321 Live Instances Exposed](<https://blog.gridinsoft.com/leaked-n8n-api-tokens/>)

## Step 3 — Lock Down and Review User Accounts

![Two desks contrast moving files forward versus shredding them, showing options for a removed n8n account.](/blog/en/article-49768a92-7a4a-492b-a88b-d78f56571e55/f271795a13a84b53c01e2d97e1333bda67c76e084333bd63f704772f65ce12d4.png)

Copying a removed user's items forward versus deleting them outright: two different paths after lockdown.

n8n defines three built-in instance roles, [Owner, Admin and Member](<https://n8n-challenges.app/en/blog/rbac-meaning-in-n8n-when-a-small-team-needs-it>), with Admin available on n8n Cloud Pro, Enterprise, and self-hosted Enterprise, per n8n's documentation. Review who holds each role and remove access for anyone you can't immediately account for.

If you need to remove a suspected-compromised user, n8n's deletion flow lets an admin choose whether to copy that user's workflow data and credentials to a new user or permanently delete them, according to n8n's documentation. We'd default to permanently deleting a suspected-compromised user's workflows and credentials rather than copying them forward, unless you've already confirmed those items are clean.

Sources: [Manage users and access | Administer | n8n Docs](<https://docs.n8n.io/administer/manage-users-and-access>), [Add and remove users | Administer | n8n Docs](<https://docs.n8n.io/administer/manage-users-and-access/add-and-remove-users>)

## Step 4 — Audit Workflows, Executions and Webhook Exposure

![A magnifying glass inspects a cluster of pipe junctions, representing an audit of n8n workflows and webhooks.](/blog/en/article-49768a92-7a4a-492b-a88b-d78f56571e55/9b25bc524492434399af1dee1751d25126c212f16c308340ef161b2096f26f7a.png)

An audit pass moves across the whole workflow network, flagging the junctions that need attention.

n8n's documentation lists [running a security audit](<https://n8n-challenges.app/en/blog/n8n-security-checklist-for-a-shared-self-hosted-instance>) among the controls for securing a self-hosted instance. GitGuardian's 2026 blog research recommends running the authenticated audit endpoint on a schedule and forwarding results to a SIEM, and describes the audit response, in its own analysis, as able to flag high-risk nodes, nodes with filesystem access, unprotected webhooks and unused credentials.

Beyond the automated audit, Gridinsoft's 2026 guidance, reporting GitGuardian's research, instructs responders to compare workflow changes for unfamiliar nodes, new webhooks or changed destinations. n8n's N8N_SECURITY_AUDIT_DAYS_ABANDONED_WORKFLOW variable defaults to flagging a workflow as abandoned after 90 days without execution, which is one more place a stale, forgotten workflow can hide a change.

![Workflow audit pass: 1. Run the audit; 2. Compare recent changes; 3. Check abandoned workflows; 4. Close each flagged item](/blog/en/article-49768a92-7a4a-492b-a88b-d78f56571e55/7a7290e64570507928f14220709d2680deab15cfc871207bb5a69bfac27c50c8.png)

## Step 5 — Patch and Harden the Instance

Only patch after containment and secret rotation, so a patched-but-still-compromised instance isn't mistaken for a closed incident. Cyera Research Labs' January 2026 disclosure of CVE-2026-21858 recommends updating n8n to version 1.121.0 or later, and [Cyera Research Labs' own 2026 estimate](<https://www.cyera.com/research/ni8mare-unauthenticated-remote-code-execution-in-n8n-cve-2026-21858>) put the exposure at an estimated 100,000 servers globally when it published the finding on January 7, 2026. On patch turnaround specifically, Cyera's researcher Dor Attias commented in that same disclosure on how quickly n8n responded once the vulnerability was reported, a pace that matters because the value of a fix depends on how fast a team can apply it after containment.

> “They maintain a strong security posture across the product and respond incredibly fast when it comes to addressing reported vulnerabilities.”
>
> — Dor Attias, Research Labs, Cyera · Source: [Ni8mare - Unauthenticated Remote Code Execution in n8n (CVE-2026-21858)](<https://www.cyera.com/research/ni8mare-unauthenticated-remote-code-execution-in-n8n-cve-2026-21858>)

Harden what's left afterward: n8n's N8N_BLOCK_ENV_ACCESS_IN_NODE variable controls whether users can reach environment variables through expressions and the Code node, and is worth checking during the same pass.

Sources: [Ni8mare - Unauthenticated Remote Code Execution in n8n (CVE-2026-21858)](<https://www.cyera.com/research/ni8mare-unauthenticated-remote-code-execution-in-n8n-cve-2026-21858>), [Security | Deploy | n8n Docs](<https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/security>)

## Step 6 — Rotate Every Downstream Credential n8n Could Reach

![A row of old keys being swapped for new ones across cloud, database and folder shapes, showing credential rotation.](/blog/en/article-49768a92-7a4a-492b-a88b-d78f56571e55/891d0310b2ef7b8a57b2e050f12cadce85f423600202e2fa8d4b3f335f259f31.png)

Rotating downstream credentials means replacing the key at every system the workflow could reach, not just one.

Revoking the n8n-level token doesn't undo actions already taken through connected systems. Gridinsoft's 2026 guidance, reporting GitGuardian's research, instructs responders to map which credentials were reachable through the affected workflows, then rotate those connected secrets at their source.

![Downstream credential rotation: 1. Map reachable credentials; 2. Rotate at the source; 3. Reissue n8n credentials; 4. Confirm workflows still run](/blog/en/article-49768a92-7a4a-492b-a88b-d78f56571e55/c9810680e084aebe963d34c87cdabe5fe66f396cd31f3b10aea03862b39dff77.png)

We think treating full downstream rotation as a non-negotiable last step, not an optional extra, is the difference between closing an incident and just hiding it.

Sources: [Leaked n8n API Tokens: 321 Live Instances Exposed](<https://blog.gridinsoft.com/leaked-n8n-api-tokens/>)

## Step 7 — Decide the Incident Is Closed

Treat the incident as closed only once every item below is true.

- [ ] A fresh security audit comes back clean
- [ ] The instance is running a patched version
- [ ] Every downstream credential the affected workflows could reach has been rotated
- [ ] Ongoing monitoring, including a repeated security audit, is back in place

Sources: [Security | Deploy | n8n Docs](<https://docs.n8n.io/deploy/host-n8n/configure-n8n/security>), [Ni8mare - Unauthenticated Remote Code Execution in n8n (CVE-2026-21858)](<https://www.cyera.com/research/ni8mare-unauthenticated-remote-code-execution-in-n8n-cve-2026-21858>)

## Limitations and What This Checklist Does Not Cover

This order is an editorial synthesis across n8n's own documentation and third-party incident-response writing, not a single published runbook from n8n. GitGuardian and Cyera Research Labs are both vendor security-research blogs with a commercial interest in their findings and products, and Gridinsoft's guidance reports GitGuardian's research secondhand rather than firsthand.

Figures like Cyera's server estimate describe conditions at the time of that disclosure, not n8n's current installed base or current vulnerability status. If your team is weighing broader n8n security issues beyond one suspected n8n security breach, or comparing how n8n handles n8n security concerns against other platforms, treat this checklist as one input, not a complete program. It's also not documented here whether n8n Cloud customers have a self-service incident-response path equivalent to the self-hosted controls above.
