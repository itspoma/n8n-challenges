## Scope your n8n MCP issues before changing settings

![A debugging kit groups the configuration details for an n8n MCP Server Trigger check.](/blog/en/article-d716b9ac-1d5f-4090-b264-527ace65062d/a5d2aea976fe990bae209e3bc3dfe0c8f22bdde7aa548d16ede4fec33b3874c8.webp)

A compartmented debugging kit represents the configuration details to record before troubleshooting.

Is n8n MCP not working in your workflow? Separate connection, tool discovery and tool execution. This checklist targets the [MCP Server Trigger](<https://n8n-challenges.app/en/blog/n8n-mcp-vs-api-choosing-how-an-ai-agent-calls-a-tool>), which exposes tools from one workflow; instance-level MCP setup belongs to a different configuration.

The checks and completion criteria below are our suggested troubleshooting framework, not mandatory MCP standards or a tested procedure. These checks do not establish compatibility across n8n and client releases; verify them against your installed versions. Start by recording the configuration so later changes have a clear baseline.

- [ ] Record the installed n8n and client versions.
- [ ] Record the deployment and whether a reverse proxy is involved.
- [ ] Identify the MCP Server Trigger workflow and selected endpoint type.
- [ ] Record the intended transport and authentication mode without copying secrets.

We think the most useful debugging habit is to name the failing boundary before changing settings. A missing tool and an incorrect tool result deserve different investigations.

## Check endpoint readiness, transport and authentication

![Temporary and mounted sockets represent test and production endpoints for the n8n MCP Server Trigger.](/blog/en/article-d716b9ac-1d5f-4090-b264-527ace65062d/48c990c623b1c7c8758c0ea0d82b83a8edebcfd09301ccc1eeced520b5fd0952.webp)

Temporary and mounted sockets illustrate test and production endpoint readiness; a coupling and key represent transport and authentication.

For an inactive workflow, n8n registers the MCP Server Trigger test URL when you select Listen for Test Event or Execute workflow. Publishing registers the production URL.

The trigger supports SSE and streamable HTTP, but not direct stdio. A gateway that bridges a stdio client is a separate configuration. Authentication choices are None, Bearer auth and Header auth; authenticated access is our recommendation for this team check, rather than a universal platform requirement.

With n8n MCP not working at connection time, investigate each boundary separately instead of treating every failure as evidence of an invalid token. For reverse-proxy deployments, the buffering check below reflects n8n's documented requirement, not a complete proxy configuration. Use the following suggested completion checks.

- [ ] Use the test URL while listening, or the production URL after publishing.
- [ ] Select SSE or streamable HTTP explicitly in the client.
- [ ] Match the client's authentication configuration to the trigger.
- [ ] If a reverse proxy is present, check buffering for the MCP endpoint.
- [ ] Mark this stage complete when the client connects through the intended configuration.

## Check discovery with a minimal read-only tool

![One connected diagnostic tool becomes visible through an n8n MCP discovery check.](/blog/en/article-d716b9ac-1d5f-4090-b264-527ace65062d/5b2705a19e112b32e82d1f7517e2a34eb37e34e408eb63b6937c18a79d784aef.webp)

A single tool in a toolbox appears through a connected viewing aperture, illustrating discovery of the minimal diagnostic tool.

Our suggested fixture is a diagnostic workflow containing the MCP Server Trigger and a connected JavaScript Code Tool returning a fixed string, for example return 'mcp-check-ok';. Exclude external APIs and write operations. n8n's Code Tool implementation on the repository's master branch describes output as a single string; this example is untested and must be checked against your installed release.

n8nlogic's March 2026 vendor guide describes the trigger as executing connected tool nodes rather than a conventional linear workflow. Use that wiring explanation as a troubleshooting lead: inspect the diagnostic tool's connection before changing its code.

The regular n8n MCP Client node automatically fetches the external server's selectable tools. Configure it for your endpoint and inspect that list. Discovery is complete when the diagnostic tool appears; visibility does not establish that the tool executes successfully.

In our view, a deliberately boring fixture is the right starting point. We would remove business logic until the connection and tool boundary are understandable.

## Check the call, then repeat the same evidence

![A diagnostic tool returns a bead that is compared with the expected result and stored with an execution record.](/blog/en/article-d716b9ac-1d5f-4090-b264-527ace65062d/e0e1d2b5fd3e9d7534ce013ea9aa9042cc7f2a7ca03ca7d0e70155aff0bad9c7.webp)

Matching beads in an evidence tray illustrate comparing actual and expected output, with a clipped slip representing the execution record.

Is n8n MCP not working even after discovery succeeds? Call the selected tool with inputs matching its discovered schema. The n8n MCP Client supports manually entered parameters or a JSON object. For this suggested fixture, completion means the response contains mcp-check-ok and you can inspect the corresponding execution.

[Inspect production runs through executions](<https://n8n-challenges.app/en/blog/n8n-event-logs-an-exercise-to-trace-a-workflow-failure>) rather than live canvas output. The executions view can filter accessible runs by workflow, status and start time; access depends on workflow permissions, and deleting a workflow deletes its execution history. A Success status alone does not establish correct output.

Use this suggested handoff checklist after each configuration change. It checks the constant-response boundary, not application-specific APIs, downstream permissions or business data correctness, and it provides no reliability guarantee.

- [ ] Repeat discovery and the same tool call.
- [ ] Record the endpoint type, transport, tool name and redacted inputs.
- [ ] Record expected output, actual output and timestamp.
- [ ] Attach an accessible execution reference.
- [ ] Separate connection failures, missing tools, returned errors and incorrect output.
- [ ] Hand over the remaining failing boundary and the last configuration change.
