## Editorial exercise: define the contact contract

![Two input slots, a wooden processing jig and four output compartments sit beside a blank contact contract.](/blog/en/article-1f0cea8d-ef76-4846-9d40-98d633521388/c203fd1be60b41e0f9dac41b8cdc2906002189124b1ca1768652819a6ba856f8.webp)

The exercise proposes two input fields and a consistent four-field return.

Practise n8n Execute Sub-workflow by building a reusable contact normalizer and a separate development caller. Your task is to define their shared contract, implement it, and collect actual outputs or errors for four suggested test cases. This is an editorial exercise, not an executed or validated solution.

Use your own development n8n environment, synthetic contacts and no external services. You should already know how to add nodes and map fields. Keep the exercise manually constructed and synchronous; production publishing, permissions, paused executions, error-workflow routing and automatic extraction of existing nodes are outside its scope.

Use the following proposed contract. Require nonblank email and name values; trim both and lowercase the email. For this exercise only, accept an email if it contains an @ with text on both sides and no whitespace. This is deliberately limited, not comprehensive email validation.

**Suggested input and output contract**

| Direction | Field | Type | Rule |
| --- | --- | --- | --- |
| Input | email | String | Required; normalize and check |
| Input | name | String | Required; trim |
| Output | success | Boolean | True only when valid |
| Output | email | String | Normalized value, or empty on failure |
| Output | name | String | Trimmed value, or empty on failure |
| Output | error | String | Empty on success; reason on failure |

We think writing the return contract before building nodes makes this exercise more useful: it gives every check a concrete target.

## Build the child with n8n Execute Sub-workflow Trigger

![Contact slips pass through an entrance gate and trimming jig toward a four-compartment return tray.](/blog/en/article-1f0cea8d-ef76-4846-9d40-98d633521388/5e08d2069908e1cc64d053ab2bd10c06a0971d4ad1c14508fcf6d9a837b7834f.webp)

The suggested child moves from typed inputs through validation to an explicit return.

Start the child with n8n Execute Sub-workflow Trigger and declare email and name as string inputs. n8n documents this trigger as the child's first node; declared typed inputs become parameters the caller can populate.

For the suggested implementation, connect a [Code node](<https://n8n-challenges.app/en/blog/n8n-code-node-javascript-debugging-tutorial>) for per-item validation and normalization, then an Edit Fields node named Return. The sequence below defines the proposed logic. n8n returns the child's last node output, and its guidance recommends a final Set / Edit Fields node to expose the return contract; that does not automatically enforce a complete output schema.

1. Check for null, missing values and non-string values before calling string methods.
2. Trim both strings, lowercase email, then check for blank values and the exercise's email rule.
3. On failure, produce success false, empty email and name strings, and an explanatory error string.
4. On success, produce success true, normalized email, trimmed name and an empty error string.
5. Configure Return to expose only success, email, name and error.

For expected validation failures, retain the same field names and types. This follows n8n's recommendation to use a consistent return shape with a success flag and error field.

## Build the development caller

![A hand places contact slips in a dispatch tray beside a raised flag, empty receiving tray and separate processing box.](/blog/en/article-1f0cea8d-ef76-4846-9d40-98d633521388/4830529ac488969e4f450c6c8a2dc2e1c0479f15feb3acf725e165e48c96fca8.webp)

The development caller supplies controlled inputs and waits for the child to finish.

Create a separate caller with Manual Trigger, synthetic fixtures and n8n Execute Sub-workflow. n8n documents Code and Edit Fields as ways to generate custom test datasets. In Execute Sub-workflow, select Database / From list, choose the child and map its declared inputs.

Enable Wait for Sub-Workflow Completion and initially disable Attempt to convert types. Waiting lets the parent proceed after the child finishes; it does not validate returned data. Start with the mode that passes all input items into one execution. Neither mode guarantees your intended output count.

The mapped fields are absent when the child uses Accept all data, so use explicit typed inputs here. You may pin development fixtures for repeatability, but pinning is unavailable in production executions; these checks cannot establish production behavior.

## Check four cases through the caller

![Four test trays hold a fitted contact slip, an empty recess, a round peg beside a rectangular slot and several aligned slips.](/blog/en/article-1f0cea8d-ef76-4846-9d40-98d633521388/1d557c5ad57b4569276f329a6d1b960b442913b30070f10963342ffc470e517c.webp)

These suggested fixtures probe different parts of the workflow contract.

Run these suggested fixtures through the caller boundary and record what actually happens. The expected values below are exercise targets, not reported test results.

**Suggested fixtures and checks**

| Case | Input | Target or observation |
| --- | --- | --- |
| Valid | email: ' ALICE@EXAMPLE.COM '; name: ' Alice ' | true; alice@example.com; Alice; empty error |
| Missing name | Valid email; name mapping removed | false; empty email/name; explanatory error |
| Wrong type | email: 12345; name: Alice | Record caller rejection or child result |
| Multiple items | Two distinct valid contacts | Target two normalized results in both execution modes |

n8n documents that removing the requested name mapping sends null.

In his vendor walkthrough from 2026, Jahanzaib Ahmed reports that his Docker test on n8n 2.43.4 rejected numeric email at the parent with conversion disabled; enabling conversion passed it to child validation as a string. This is his reported result, not independently verified behavior across installations. Repeat both settings yourself; under the proposed email rule, the string 12345 should fail validation. Do not assume a caller rejection becomes a child-generated failure row.

## Review mismatches and finish the exercise

If the result differs from your contract, inspect the declared inputs and caller mappings first, then null handling and conversion settings. For missing return data, inspect the execution mode, waiting setting and the child's final node output. Compare field names, types and item counts at the caller.

We'd keep boundary rejection and business-validation failure separate in the review: each tells you something different about where the contract failed.

Complete the exercise with the evidence below. For reflection, explain why a rejected call might have no child return object, and how conversion changes what your validation receives.

- [ ] Supply the written contract and both workflow designs.
- [ ] Supply the recorded caller outputs or errors for all required checks.
- [ ] Explain every mismatch against the proposed contract.
