## The Real GitHub Advisory We Found: OAuth Credential Redirection in the MCP Python SDK

![A key travels toward an unlabeled doorway instead of the correct authorization server, depicting credential redirection.](/blog/en/article-8f925793-d4f2-46d9-8af1-dd66e913b29c/fe7691407396370f334ed7ba8a203fa793ab5eaf60ff6d4ef679e5926afb5adf.png)

A key travels toward an unlabeled doorway instead of the correct authorization server, illustrating how the advisory describes credentials being redirected.

GitHub published this advisory, titled "OAuth client could send credentials to an authorization server chosen by the MCP server," on September 28, 2026, for the mcp package distributed on PyPI by the Model Context Protocol Python SDK maintainers. The advisory states that affected versions of the SDK's OAuth client support did not validate the authorization server's declared identity on every discovery path, and did not bind stored or pre-provisioned client credentials to the authorization server they belong to. It says a malicious or compromised MCP server could use this gap to redirect those credentials, including a client secret, authorization code or PKCE verifier, to a token endpoint of its own choosing.

According to the advisory, this affects applications using the SDK as an MCP client over HTTP through OAuthClientProvider, ClientCredentialsOAuthProvider, PrivateKeyJWTOAuthProvider, or the deprecated 1.x RFC7523OAuthClientProvider, when that client might connect to an MCP server it does not fully trust while holding credentials for a real authorization server. The advisory states that versions 1.9.1 through 1.29.1 lacked the check on every path, while 2.0.0 through 2.1.1 lacked it only on a legacy fallback path. It adds that MCP servers built with the SDK, stdio-based clients, and clients that attach their own tokens or headers are not affected.

The advisory's fix is to upgrade to version 2.2.0 or later on the 2.x line, or 1.30.0 or later on the 1.x line. It notes that upgrading alone does not fully close the gap for the two credential-based providers: a team must also pass an explicit issuer value, since without one the client still follows whichever authorization server the connected MCP server advertises. The advisory calls this a deprecation warning for now, becoming a required setting in a future 3.0 release.

**Affected and patched MCP Python SDK versions, per the advisory**

| SDK line | Affected versions | Patched version | Gap described by the advisory |
| --- | --- | --- | --- |
| 2.x | >=2.0.0a1, <2.2.0 | 2.2.0 | Missing issuer check on paths where the server published no protected resource metadata |
| 1.x | >=1.9.1, <1.30.0 | 1.30.0 | No issuer check or credential binding on any discovery path |

For remediation, the advisory tells teams to clear any OAuth client registration stored before upgrading, since a registration saved without an issuer stays unbound, a condition it says covers everything the 1.x line stored before version 1.30.0. It also states that a client which may have connected to an untrusted MCP server before the fix should have its client secret rotated and its tokens revoked at the authorization server. On versions before the fix, the advisory says there is no workaround besides only connecting OAuth-enabled clients to MCP servers already trusted.

For background only, the same maintainers' own release notes for SDK version 2.2.0, published September 7, 2026, describe the matching code change as checking the authorization server's declared issuer on every discovery path, including a legacy path that previously skipped the check. We use that release note here only to explain the kind of code change the advisory's remediation steps assume, not as a separate source of facts about the vulnerability itself.

The advisory does not mention n8n, any n8n edition, or n8n Cloud; it names only the mcp Python package, and it does not state a CVE identifier or whether other products bundle this SDK. We report only what it does not address here, since that is a stated limitation rather than something another source can fill in. This remains the closest verified official document to the MCP workflow validation interpreter vulnerability originally requested, not a confirmed match for it. In our view, a security update is only actionable once its scope is this precisely bounded, which is exactly what makes a specific advisory more useful than a vague warning.

## What n8n Teams Should Do Now, and What the Advisory Leaves Open

![A hand checks items on a list beside a padlock, showing suggested follow-up steps for n8n teams.](/blog/en/article-8f925793-d4f2-46d9-8af1-dd66e913b29c/499d2911c0e48448a618b8d6b8a02e521093d8673982e0bc1f2f0a95eabe555a.png)

Suggested checks for teams evaluating whether their MCP tooling depends on the affected SDK, separate from the advisory's own text.

Since the advisory is silent on n8n, the rest of this section offers our own editorial suggestions for teams that connect n8n to external MCP tooling.

We'd suggest, separate from anything the advisory recommends, that any team [connecting n8n to external MCP servers through AI chat clients](<https://n8n-challenges.app/en/blog/n8n-mcp-client-setup-connect-claude-or-chatgpt-safely>) check whether their MCP tooling depends on this SDK's OAuth client code, and if so, confirm which version is running before assuming the fix does not apply.

Until a team confirms its own exposure, suggested checks:

- [ ] Check whether any MCP client code in your stack imports the mcp Python package, and note its pinned version
- [ ] If it uses OAuthClientProvider, ClientCredentialsOAuthProvider or PrivateKeyJWTOAuthProvider, confirm an explicit issuer value is set after upgrading
- [ ] Rotate OAuth client secrets and revoke tokens for any client that may have connected to an untrusted MCP server
- [ ] Watch the modelcontextprotocol/python-sdk security advisories directly for future updates to this SDK
