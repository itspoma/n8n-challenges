## Prerequisites and goal

This n8n API retry tutorial uses the HTTP Request node to fetch a paginated GET response, retry temporary failures, and write records using a stable identifier. Before configuring it, gather the API URL, authentication details, pagination rules, page-size limit, response fields, and record identifier. The supplied documentation does not define those API-specific values, so use placeholders until you check the API documentation or a sample response.

## 1. Inspect the first response

![The HTTP Request response is inspected for its fields and pagination rule.](/blog/en/article-34bbbd28-2034-49ef-a65d-35b1679060f3/531b94163c854628736a0f5352700d9dbf8c949828dae26e8d0ac29f4e7074ec.webp)

The first HTTP Request response reveals which pagination rule to configure.

Add an HTTP Request node and set its method to GET. Make one request without pagination, then inspect the returned body, headers, and status code. n8n’s documentation says APIs differ in their pagination rules, so identify whether this API supplies a next-page URL or expects a parameter to change on each request before configuring the node.

1. Set the request URL and authentication using the API’s documented requirements.
2. Run one request without pagination.
3. Record the response fields, page size, and either the next-page URL or page parameter.

Sources: [HTTP Request | Nodes | n8n Docs](<https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.httprequest>)

## 2. Configure pagination and n8n API retry

![The HTTP Request pagination and retry steps move from page selection to bounded recovery.](/blog/en/article-34bbbd28-2034-49ef-a65d-35b1679060f3/dd0f2518f547795c33cb2201a5baaad1e8589455e6260dd454a3fd8478646be0.webp)

Pagination, finite retries, and a stopping point form the request setup sequence.

In the HTTP Request node, enable [Pagination](<https://n8n-challenges.app/en/blog/n8n-loop-over-items-pagination-debugging-paginated-api-pulls>) and choose the mode that matches the API: update a parameter on each request or use a next-page URL from the response. Use the API’s documented expression and stopping condition. n8n exposes $pageCount and $response for expressions, but those variables do not tell you how this API numbers pages or represents its next link.

[For retries](<https://n8n-challenges.app/en/blog/retrying-failed-n8n-http-requests-safely>), set a finite Retry On Fail limit and a wait appropriate to the API. n8n documents Retry On Fail as rerunning a node after failure; its HTTP Request guidance describes Max Tries and Wait Between Tries as retry controls. Microsoft Learn identifies 429 and 5xx responses as typical retry candidates, most 4xx responses as unlikely to be fixed by retrying, and recommends respecting Retry-After when supplied. These are general HTTP guidelines; follow the target API’s rules.

We think the safest default is to keep pagination and retry settings explicit and bounded, then adjust them to the API’s documented behavior instead of treating every error as temporary.

## 3. Upsert records by a stable identifier

![The Data Table upsert updates a matching record or creates a new one.](/blog/en/article-34bbbd28-2034-49ef-a65d-35b1679060f3/5fe2b278a62b33b2f433608c2e36966bb9322cfa7df62732686cf77032dbf379.webp)

Matching identifiers direct an upsert to update an existing record or create a new one.

After fetching records, write them to a Data Table with an upsert operation and matching conditions based on the API’s stable record identifier. n8n documents that an upsert updates a matching row or creates one when no match exists. Verify the matching conditions before relying on this to prevent duplicate rows; the documentation does not guarantee uniqueness.

- [ ] Choose a stable identifier from the API response.
- [ ] Configure the upsert matching conditions to use that identifier.
- [ ] Verify that an existing record is updated and a new record is created when no match exists.

Sources: [Data Table | Nodes | n8n Docs](<https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.datatable>)

## 4. Check results and troubleshoot

![An n8n execution review shows repeated processing and an error workflow alert.](/blog/en/article-34bbbd28-2034-49ef-a65d-35b1679060f3/e4c6ca43f309fce62cc5095183a5f36bd68b57b730b87a4681b94b50551c3ead.webp)

Execution review checks for repeated side effects and captures workflow failures.

Review the execution output for fetched pages, returned items, and error status. If you retry a failed workflow, inspect whether the failed node already performed side effects: n8n documents that workflow retries reprocess every item at that node, which can repeat earlier effects. An error workflow can start with Error Trigger and be assigned in workflow settings to handle failed executions; it does not itself provide an automatic replay strategy.
