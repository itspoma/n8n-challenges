## Your n8n data validation task and boundaries

This editorial exercise asks you to build n8n data validation that sends accepted company records toward a write boundary and keeps rejected records available for correction. Use synthetic inputs, preserve each original record and explain every rejection. The proposed workflow and expected results have not been executed or validated.

You need an n8n environment with JavaScript Code node support, basic JavaScript knowledge and access to node outputs. n8n documents custom JavaScript steps and a default Run Once for All Items mode; the supplied documentation establishes no specific edition or version. Check Object.hasOwn() support in your runtime if you use an older installation.

Stop at an inspection point representing the intended write boundary. Destination configuration and actual create or update operations are outside scope. We think making rejection reasons reviewable is as important as producing an accepted payload.

The specimen trays distinguish missing, empty and wrong-type inputs used in the editorial exercise.

Use this editorial contract: companyName and contactEmail must exist, contain non-null strings and remain non-empty after trimming. contactEmail must also pass n8n's documented isEmail() format check. These are exercise rules, not universal company-record requirements. The email check does not establish mailbox existence, ownership or deliverability; its accepted grammar is not specified in the supplied source.

## Suggested solution: inspect fields and retain reasons

For n8n nodes, data validation in this exercise separates field inspection from routing. Start with a JavaScript Code node in Run Once for All Items mode. Read $input.all() and process every item, whose ordinary data sits under json. Return one json-wrapped result per input containing caseId, original, normalized, validationErrors and isValid; keep validation metadata outside the original record.

Follow this suggested algorithm for each required field. Object.hasOwn() [distinguishes an absent property from a present one](<https://n8n-challenges.app/en/blog/n8n-expressions-exercise-prepare-updates-without-losing-valid-values>), including one containing null or undefined. Check null separately because JavaScript's typeof reports it as an object. Check string type before trim(), which returns a new string without changing the original.

1. If the field is not an own property, append its missing reason and stop checking that field.
2. If its value is null or undefined, append empty and stop checking that field.
3. If its type is not string, append invalid_type and stop checking that field.
4. Trim the string into normalized; if it is empty, append empty.
5. Continue with the other required field so simultaneous failures remain visible.

Treat email format as a separate n8n expression check using normalized.contactEmail.isEmail(), reached only for a non-empty string. Carry its result into a final JavaScript step that appends contactEmail: invalid_email when false, then sets isValid from validationErrors.length === 0. This avoids assuming that n8n expression helpers are ordinary JavaScript methods.

n8n's 2026 Production AI Playbook illustrates validationErrors and an isValid flag for AI output; this exercise adapts that pattern to company records. In our view, one precise reason per failed field is more useful here than cascading several errors from the same missing value.

## Route records and check completion

Use an If node to compare isValid with Boolean true. n8n documents conditional splitting through comparison operations. Connect the true branch to the inspection point and the false branch to review; do not reconnect review to the write path. The following checklist defines the proposed completion criteria for your n8n data validation exercise.

- [ ] Every caseId appears exactly once across the two branches with its expected decision.
- [ ] Rejected records retain their originals and all expected field reasons.
- [ ] Accepted records have no validation errors; C10 has normalized companyName = Acme.
- [ ] No rejected caseId reaches the write boundary.

Inspect both branch outputs and execution history. n8n's 2026 API Contract Testing article recommends retaining execution history as validation evidence. This dry run demonstrates routing only; establishing that an external destination received no writes requires a separate sandbox destination check.

For unexpected decisions, inspect field spelling, null handling, type checks before trim(), Boolean versus string comparisons, caseId preservation and branch connections. Suggested reflection: why does a present null differ from an absent key, and what evidence would justify changing one rejection rule?
