## Editorial exercise: define your n8n RSS feed digest

Build an n8n RSS feed workflow that discovers entries, stores a digest before sending it and remembers delivery state between sequential runs. This is an editorial exercise using documented capabilities; the proposed workflow has not been executed or validated.

You need an n8n environment with the nodes described below, a reachable public feed, project Data Table access, provider-configured SMTP credentials and a test recipient. n8n documents RSS Read for reading a publication URL and Send Email for SMTP delivery. Some providers require additional SMTP setup or an app password.

Confirm node availability before starting: the supplied documentation generally specifies no version, edition or plan. Keep this exercise to one feed and sequential runs; concurrent processing, atomic uniqueness, transactional delivery and production-scale operation are excluded.

## Prepare stable keys and separate state

![Separate drawers represent the RSS entries table and deliveries table linked by digest identity.](/blog/en/article-30fc70ff-d411-4b8b-916e-548a26735e06/05fbced54c87eaa7703c52f0fc221bbe77963b239a0c8bc98c6d7cbfbcc116ff.webp)

Two storage drawers represent the suggested separation between entry records and delivery payloads.

n8n documents Data Tables as persistent project storage and supports conditional row retrieval, insertion and updates. They suit light to moderate storage; project members can access project tables by default, and direct Code-node access is unsupported. The following schemas and fixtures are editorial suggestions.

Create an entries table with feedKey, entryKey, title, link and digestId. Treat feedKey plus entryKey as the identity, enforced through [sequential lookup and insertion](<https://n8n-challenges.app/en/blog/build-an-idempotent-n8n-webhook-that-skips-retried-requests>). Create a deliveries table with digestId, entryKeys, renderedBody, status and lastError. We think separating discovery from delivery makes the retry decision easier to inspect.

Choose a stable identifier available in your feed, with an explicit fallback policy; reject entries without an acceptable key. Do not use array position or publication time alone. Use these fictional fixtures, where each letter retains the same title and link across runs.

**Suggested fictional entry fixtures**

| feedKey | entryKey | title | link |
| --- | --- | --- | --- |
| practice-feed | A | Alpha update | Stable article link A |
| practice-feed | B | Beta update | Stable article link B |
| practice-feed | C | Gamma update | Stable article link C |

## Suggested solution: schedule, persist and send

For scheduling, the vendor FlowKit's 2026 guide describes Schedule Trigger followed by RSS Read, and cautions that returned feed fields vary. This design uses that scheduled pattern rather than an n8n RSS Feed Trigger node. Exact scheduling configuration, timezone settings and publication controls are outside this exercise.

Follow this suggested sequence. Data Table operations support the state transitions, Aggregate can collect item data into one list, and Send Email supplies SMTP delivery. Aggregation itself neither formats nor sends the message.

For this n8n RSS feed exercise, our suggested routing design uses separate scheduled discovery and delivery workflows, run sequentially without overlap. Start the delivery workflow directly from its own Schedule Trigger and query pending deliveries, without passing through RSS Read or depending on discovery output. This editorial choice keeps stored deliveries reachable when the feed fetch fails or discovery produces no items.

1. Connect Schedule Trigger to RSS Read and map the feed's available fields to the fixture shape.
2. Look up each compound entry key. Enable Always Output Data on the empty Get lookup, branch explicitly and insert only undiscovered entries; keep branch output shapes consistent.
3. Retrieve entries without a digestId. Use Aggregate's All Item Data option to retain feedKey, entryKey, title and link together in each list item, then render a plain-text email body.
4. Persist a pending delivery with its digestId, entry keys and renderedBody; associate those entries with that digestId before sending.
5. In the separate scheduled delivery workflow, query deliveries whose status is pending. Stop without sending if none exist; otherwise use each delivery's stored payload.
6. Configure Send Email with your SMTP credential, the Send operation, an authorized sender address, your test recipient, a subject such as Practice RSS digest, and Text format. Map its message body to the pending delivery's stored renderedBody.
7. After successful Send Email completion, update that digestId's delivery to sent. Route send failures through the error output, retaining pending status and recording lastError.

## Test sequential repeat runs and inspect failures

![Reordered RSS entries sit beside a pending email envelope after a failed send.](/blog/en/article-30fc70ff-d411-4b8b-916e-548a26735e06/db411cd13c4188971aa5ba4cdf5f59db6f8ce349097a15dc6119a6841681daa8.webp)

Reordered entries and a failed send test different parts of the proposed state model.

Run the following suggested checks and record actual results. Here, sent means successful Send Email node completion, not confirmed inbox receipt. A stored pending payload should remain available even if its entries disappear from the feed.

**Editorial completion criteria, to verify rather than assume**

| Test input | Required observation |
| --- | --- |
| First run: A/B | One digest containing A and B |
| Next run: B/A | No additional delivery |
| Next run: B/C/A | Next digest contains only C |
| Fixture with no acceptable identity key | Rejected without inserting an entry or sending it |
| New entry; intentionally fail SMTP | Queryable pending delivery and recorded error |
| Restore credentials; omit entry from feed | Later attempt uses the stored payload |
| Intentionally fail RSS Read with a delivery pending | Inspect the fetch error route; existing state remains unchanged |
| After failed fetch, run delivery workflow independently | Existing pending delivery remains retryable from its stored payload |

For missing entries, inspect empty Get output, branch shapes and stored keys. Always Output Data belongs on the lookup here; n8n warns that using it on IF nodes can create infinite loops. Use Continue using error output for explicit failure routing; Continue instead passes the last valid data.

[Assign an error workflow](<https://n8n-challenges.app/en/blog/build-an-n8n-error-workflow-and-attach-it-to-a-production-workflow>) for otherwise unhandled failures. n8n's guidance says handled node errors do not automatically trigger it. Programmatic error-workflow assignment is documented for n8n 2.29.0+; older instances use workflow settings.

## Reflect on uncertain delivery and assign owners

Suggested reflection: SMTP accepts the message, but the sent-state update fails. Explain why retrying could duplicate mail, then document who decides whether to resend or reconcile the record. The supplied sources establish neither exactly-once SMTP delivery nor atomic coordination between sending and state updates.

In our view, an uncertain send needs a named decision-maker before unattended use. Complete this editorial handover checklist alongside your recorded test results.

- [ ] Name a feed owner for source URLs and the stable-key policy.
- [ ] Name a workflow owner for stored state and SMTP credentials.
- [ ] Name a responder and backup for pending deliveries and missed updates.
