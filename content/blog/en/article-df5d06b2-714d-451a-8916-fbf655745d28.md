## Editorial exercise: task, prerequisites and inputs

![Four fixture trays represent immediate completion, pending work, an empty response and work that never completes.](/blog/en/article-df5d06b2-714d-451a-8916-fbf655745d28/65082aafae9e8ead9684b53b34fc2e379c0bf51636469cbe8f07b6acb48cc218.webp)

The four trays represent the authored fixture contracts, rather than universal meanings of response codes.

Use the n8n HTTP Request node to inspect controlled responses, then design a polling flow that distinguishes completed work, pending work and escalation. This is an editorial exercise: the proposed workflow has not been executed or validated. Its deliverables are a response-routing workflow, a polling design and evidence explaining every exit path.

You need your own n8n environment, basic API knowledge and instructor-provided controlled endpoints. The instructor must supply the request methods, headers, bodies and response sequences described below; this article does not provide a fixture server. Use synthetic inputs and keep company data out of the exercise.

Treat these fixtures as authored exercise contracts, not universal HTTP semantics. Microsoft’s Asynchronous Request-Reply guidance distinguishes an initial 202 acknowledgement from a status request that returns 200 while work remains pending. Define completion from the fixture’s documented state, rather than its status code alone.

**Suggested controlled fixtures to request from the instructor**

| Fixture | Authored response sequence | Expected outcome |
| --- | --- | --- |
| Immediate completion | 200 with state completed | Completed |
| Asynchronous work | 202, then 200 pending, then 200 completed | Poll, then complete |
| Empty response | 204 with no body, defined as complete | Complete without reading a result body |
| Never completes | 202, then repeated 200 pending | Escalate at the ceiling |

We think the useful skill here is explaining why a branch exists before adding more nodes. A workflow diagram should make its stopping decisions understandable to another developer.

## Inspect the n8n HTTP Request node response

![An opened response envelope separates status, headers and body for inspection.](/blog/en/article-df5d06b2-714d-451a-8916-fbf655745d28/4471e335d7a806edb263a92ceeb67b1bbbe251ed7464742a492b53adc5f58c7d.webp)

The opened envelope illustrates inspecting the response components before choosing routing fields.

Enable Include Response Headers and Status. n8n’s HTTP Request documentation says this returns the headers and status code alongside the body. Inspect the actual output for each fixture before writing routing expressions, recording the returned status, available headers and body shape.

For downstream routing, use the fields returned in that output. n8n’s expression reference limits $response.statusCode to the HTTP Request node; do not assume that expression is available in later nodes. The suggested inspection sequence below keeps the response contract separate from assumptions about field paths.

1. Run each supplied fixture and save the observed output shape.
2. Identify the returned status field and any documented body-state field.
3. Write a routing rule for every fixture before connecting branches.
4. Route an unexpected status or state to escalation with a reason.

Record any polling-location or delay headers the fixture provides, but do not make them control this exercise’s loop. Header-driven polling, missing-header handling and delay parsing need their own implementation specification. Use an instructor-specified polling endpoint and a fixed exercise interval instead.

## Design polling with separate exit paths

![A polling track uses an hourglass, counting beads, a completion ramp and an escalation stop.](/blog/en/article-df5d06b2-714d-451a-8916-fbf655745d28/2672d7f86f4f3b86249646385cf922aa82e1f9dc0829d585b860d8656e500456.webp)

The track connects a waiting interval and finite request allowance to separate exit paths.

For the n8n HTTP Request node polling design, define a ceiling before starting. As an editorial constraint, allow at most three status requests after the initial acknowledgement; this is not an operating default. Preserve an operation identifier, polls made, ceiling, last response and stop reason. Submit an annotated polling design; this article does not provide a copyable loop implementation.

n8n’s official looping reference requires explicit termination and a run-index ceiling for reset-mode polling, and describes Loop Over Items typeVersion 3 output wiring. For this editorial design, specify one post-response decision node evaluated once per status response: its zero-based $runIndex values 0, 1 and 2 correspond to requests one, two and three. Check completion first; otherwise, escalate pending work when $runIndex is at least 2. Before requesting again, the separate allowance check must reject polls made of 3 or more.

These checks describe the same three-request allowance, not two independent budgets. Their executable configuration and state preservation remain outside this exercise’s implementation instructions. [n8n’s Wait](<https://n8n-challenges.app/en/blog/the-n8n-wait-node-handling-retries-and-rate-limited-apis>) documentation supports an interval through Wait Amount and Wait Unit; its webhook-specific Limit Wait Time is not a polling-loop deadline.

Use the following suggested decision sequence. Work through responses pending, pending, completed and pending, pending, pending, recording each request number, decision-node run index and destination.

![Suggested polling decision sequence: 1. Check allowance; 2. Wait and request; 3. Check completion; 4. Check continuation](/blog/en/article-df5d06b2-714d-451a-8916-fbf655745d28/41bdfb7ea9db5d61e677de0323480612e30c1e7eb800da3900089635695897ea.webp)

We’d keep the first version limited to a request-count ceiling and fixed interval. In our view, making those exits inspectable is more useful than adding deadline arithmetic before the state contract is clear.

## Completion criteria and reflection

![A learner reviews response envelopes, polling state and an empty-body fixture against completion checks.](/blog/en/article-df5d06b2-714d-451a-8916-fbf655745d28/d19c63f6fa1736b167d5410b26065e5baa41b921f9024b37744bfd30c59ecf92.webp)

The review board illustrates checking fixture evidence and explaining each exit path.

For the n8n HTTP Request node exercise, submit the routing workflow, saved fixture outputs and annotated polling design. If you also implement the loop, demonstrate how its operation identifier and counter survive each HTTP response. Use this suggested checklist to review the submission.

- [ ] Each fixture follows its documented routing contract.
- [ ] The empty-body fixture completes without reading a result body.
- [ ] Pending responses remain distinct from completed responses.
- [ ] The never-completing fixture stops at the chosen ceiling.
- [ ] Escalation records the operation identifier, last response and stop reason.
- [ ] The design explains completion on the final permitted response.

This exercise does not specify a release-specific fix for empty-body parsing failures; if one occurs, record the installed release, response-format setting and failure rather than treating an unverified workaround as the solution.

For reflection, explain why a successful status request can still represent pending work, which fields must survive the next request, and justify your final-response decision. A suggested solution sketch has four distinct destinations: immediate completion, completion after polling, continued polling and escalation.
