## The exercise: SAP order status without duplicate updates

This is an editorial exercise. Nothing here was executed or validated, and the steps are a suggested design, not a tested recipe. The task: poll SAP order status on a schedule, map the status codes, and write only real changes to another system.

Choose one interface. S/4HANA Cloud Public Edition documents a Sales Order OData V2 API (documentation version 2608). SAP Business One has a separate Service Layer. They are different interfaces, so do not mix them in one workflow.

Prerequisites are a sandbox SAP system, an n8n instance and a target system you may write to safely. Completion means a rerun with no changes produces zero writes. The editorial inputs are listed next.

The editorial constraints follow the inputs. The sources do not cover the target system's write API or idempotency options, so check those yourself. Likewise, no official source supplied here lists the S/4HANA status fields and codes, so confirm them in your own metadata.

- Editorial inputs: SAP base URL and credentials for your sandbox
- Last-sync mark (timestamp) stored between runs
- Target system endpoint you may write to safely
- Status lookup table kept in an n8n Data Table

- Editorial constraints: poll only, no push
- No duplicate writes to the target system
- No SAP-n8n connector assumed to be available
- One SAP interface per workflow, never mixed

## Steps 1 to 3: schedule, read changed orders and page

Start with a Schedule Trigger. The workflow must be saved and published, and the timezone follows the workflow setting or the instance default. By default, missed runs after downtime are discarded. An option to run the most recent missed execution exists from n8n 2.36 and needs the durable scheduler, default from n8n 2.45.0. We think a stored high-water mark is the safer design than trusting every run to happen.

For S/4HANA Cloud Public Edition, a community Q&A (2020, updated 2024) reports that LastChangeDate misses status changes, so LastChangeDateTime is needed. The poster also says a datetimeoffset literal worked only without a space. That is one user's report and may differ by release, so verify it.

For Business One, the Service Layer's official documentation lists $filter, $select, $orderby, $top, $skip and $count. As an editorial suggestion, filter /Orders on an update field and confirm its name in your metadata, since the sources do not name one. [Its paging defaults to 20 records and returns a next link](<https://n8n-challenges.app/en/blog/sap-odata-pagination-in-n8n-bound-and-reconcile-business-one-orders>), adjustable with a Prefer header.

In the HTTP Request node, pagination can use a response that contains a next URL, or a parameter updated per request with $pageCount. The annotation name differs by OData version, so check the response shape.

**Suggested read strategy per interface (editorial, unvalidated)**

| Aspect | S/4HANA Cloud Public Edition | Business One Service Layer |
| --- | --- | --- |
| Change filter | LastChangeDateTime (community report) | Update field on /Orders; confirm in metadata |
| Paging | Unknown; check your response shape | Default 20 per page, next link returned |
| Push alternative | Not covered here | Webhooks chapter exists; details not captured |

## Step 4: map SAP order status codes (Business One)

As editorial advice, keep the mapping out of the workflow logic. We'd put it in a [lookup Data Table](<https://n8n-challenges.app/en/blog/n8n-lookup-table-an-exercise-in-gating-api-payloads>) and route any unmapped code to a review path instead of guessing.

For Business One, the ORDR table reference is the closest thing to a SAP order status table in our sources. It lists DocStatus with O for open and C for closed, plus WddStatus for authorization status. The SDK also describes DocumentStatus as a read-only open or closed property. The Service Layer JSON naming can differ from these, so read names from your metadata.

A suggested starter table, shown for Business One only: O maps to Open, C maps to Closed, and anything else goes to review. That includes a code like CRTD if it appears in your own system, because our sources do not explain it, so treat any SAP order status CRTD value as unmapped until you confirm it. This article gives no S/4HANA status codes: our sources list none, so you must source them from your own system's documentation and metadata.

**Suggested Business One starter mapping (editorial, unvalidated)**

| DocStatus value | Mapped status |
| --- | --- |
| O | Open |
| C | Closed |
| Anything else | Send to review |

## Step 5: prevent duplicate updates

![A gate over a conveyor belt that lets only parcels with a changed colour tag pass](/blog/en/article-cd47b6db-03c7-4431-9c3a-104ef51592f1/c7d9db1fa9fe0511fc7ca1e5dd6e8788dd160bda3610ec9f077366aa28a90670.webp)

A gate that passes only changed items, showing the compare-before-write idea from this section.

The Data Table node supports upsert and an if-row-exists check, so it can store the last synced status per order. To keep SAP order status writes free of duplicates, key each row on order ID and compare the incoming mapped status before writing. Data tables default to 200 MiB per instance, and exceeding it causes execution errors on insert or update.

![Suggested exercise flow: 1. Schedule; 2. Read; 3. Page; 4. Map; 5. Compare; 6. Write](/blog/en/article-cd47b6db-03c7-4431-9c3a-104ef51592f1/c4c4451d48cdca4e4e5bd31087e713476a2078935c1ae33d710509f5e4bda71b.webp)

[Remove Duplicates](<https://n8n-challenges.app/en/blog/preventing-duplicate-api-actions-in-n8n-webhooks>) can drop items seen in earlier executions and keeps 10,000 items by default in Value Is New mode. It stores the key, not the last status sent, so a status change on the same order needs a composite key. Use it as a second guard, not the main one.

A community blog on a 1909 on-premise system reported delta tracking that returned changes as delete-plus-new rows. That was a single author's test, so test any delta feed before relying on it.

- [ ] Rerun with no SAP changes: zero writes
- [ ] Change one order status: exactly one write
- [ ] Unmapped code lands in review, not the target
- [ ] Status field names confirmed in your own metadata

## Reflection and suggested solution

Reflect on three questions, offered as suggestions: What happens if a run is missed? What if the target write succeeds but the state update fails? Which SAP order status codes landed in review?

As a bonus for Business One, explore its webhooks as a push alternative, since the guide lists a chapter on them but our sources hold no payload details. Add a stored high-water mark to the Step 5 flow as the suggested baseline.

In our view, polling with a stored state is the pragmatic start; webhooks are worth evaluating once the mapping is stable.
