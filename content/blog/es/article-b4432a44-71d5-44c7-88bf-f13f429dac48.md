## Tu ejercicio de tabla de consulta en n8n

Crea una tabla de consulta en n8n que prepare un payload solo cuando una etiqueta entrante tenga exactamente una fila de referencia, un código aprobado y una correspondencia sin caducar. Este es un ejercicio editorial basado en capacidades documentadas: sus datos de prueba, algoritmo y resultados esperados son propuestas, sin ejecución ni validación aportadas.

Usa datos sintéticos en tu propio entorno de n8n. Necesitas Data Tables, permiso para crear una tabla y familiaridad con los nodos Code de JavaScript y las bifurcaciones IF. n8n documenta Data Tables para consultas desde workflows e [importación de CSV](<https://n8n-challenges.app/es/blog/importacion-de-csv-en-n8n-un-ejercicio-de-validacion-y-conciliacion>), pero la documentación proporcionada no establece una versión ni un plan mínimos; comprueba que tu entorno incluya esta función. Las tablas pertenecen a un proyecto y están pensadas para un almacenamiento ligero o moderado.

Termina con salidas separadas para los payloads aptos y los registros que requieren revisión. La configuración HTTP, la autenticación, las escrituras reales y la aplicación de restricciones en el destino quedan fuera del alcance. Para completar el ejercicio, cada identificador de entrada debe aparecer exactamente una vez, con el resultado esperado que se indica más adelante.

## Solución sugerida: conserva la ambigüedad antes de comprobar la caducidad

![Una mano levanta una ficha sobre otra parcialmente oculta; una segunda bandeja contiene dos fichas visibles junto a un reloj de arena.](/blog/es/article-b4432a44-71d5-44c7-88bf-f13f429dac48/9d07c5c2fbcda847630d75e2925524fb9d933e7ad682cbeed9a39cab9a0ad8d9.webp)

Mantener visibles las correspondencias duplicadas conserva la ambigüedad que ocultaría seleccionar la primera coincidencia.

Usa esta secuencia sugerida: Incoming records → Get reference rows → Build index → Evaluate. Haz que Incoming records sea un nodo Code que devuelva un elemento cuyo json contenga un array records con los siete objetos de identificador y etiqueta. Get reference rows recupera todas las filas con una etiqueta no vacía y Return All activado. La guía de Code de n8n permite combinar datos de referencia con otro conjunto de datos y devolver elementos del workflow como un array de objetos { json: ... }.

Ejecuta Build index una vez para todos los elementos. Agrupa las filas de $input.all() por etiqueta exacta en un Map de JavaScript llamado index, conservando arrays de filas de referencia completas, y devuelve [{ json: { byLabel: Object.fromEntries(index) } }]. El array de Economy debe contener ambas filas. Ejecuta Evaluate una vez para todos los elementos: lee el índice desde $input.first().json.byLabel y los registros originales desde $('Incoming records').first().json.records. Para cada registro, recupera los candidatos con byLabel[record.label] ?? []. Recorre ese array records, en lugar de las filas de referencia, para que Unknown también reciba un resultado. Estos ejemplos resueltos muestran los elementos propuestos del workflow.

**Evaluaciones resueltas del ejercicio editorial y elementos propuestos del workflow**

| Entrada | Evaluación | Elemento de resultado |
| --- | --- | --- |
| r1: Express | Una coincidencia; EXP aprobado; caducidad posterior al momento de evaluación | {"json":{"identifier":"r1","label":"Express","eligibility":true,"reason":"eligible","payload":{"identifier":"r1","apiCode":"EXP"}}} |
| r2: Economy | Dos coincidencias; rechazar antes de comprobar el código o la caducidad | {"json":{"identifier":"r2","label":"Economy","eligibility":false,"reason":"ambiguous"}} |

Para las fechas, n8n documenta que los valores pasan entre nodos como cadenas y requieren análisis. En JavaScript, usa DateTime.fromISO de Luxon con una zona UTC explícita, comprueba isValid y compara los valores de toMillis(). La documentación de Luxon 3.7.2 incluye la comprobación de validez y la conversión de marcas de tiempo; no establece la versión incluida en tu instalación. Las [marcas de tiempo UTC explícitas](<https://n8n-challenges.app/es/blog/formato-de-fechas-en-n8n-un-ejercicio-previo-a-la-escritura>) evitan depender de la interpretación de la zona horaria del workflow.

Creemos que la ambigüedad merece su propio motivo de rechazo: seleccionar una fila conveniente oculta la decisión que quien aprende necesita examinar. Sigue este orden de validación propuesto.

1. Agrupa las filas de referencia por etiqueta exacta en arrays, conservando todos los duplicados. Un Map de JavaScript puede almacenar cada etiqueta y su array.
2. Para cada registro entrante, recupera sus coincidencias. Emite missing si no hay coincidencias y ambiguous si hay más de una; deja de evaluar ese registro.
3. Para la única coincidencia, exige un apiCode de tipo cadena cuyo valor sin espacios al principio y al final no esté vacío y cuyo valor original pertenezca al conjunto declarado de códigos aprobados. En caso contrario, emite invalid_code.
4. Analiza expiresAt. Emite invalid_expiry si el análisis no es válido; en caso contrario, emite expired cuando su marca de tiempo sea menor o igual que la marca de tiempo de evaluación.
5. Emite un elemento { json: result } por entrada. Conserva su identifier y label, eligibility y reason. Añade payload con identifier y el apiCode correspondiente solo cuando sea apto; en caso contrario, omite payload y apiCode.

## Dirige los resultados y comprueba que el ejercicio esté completo

Configura IF para enviar los elementos con eligibility igual a true a la salida de payloads y todos los demás a revisión. La guía de implementación comercial de Suyash Raj de 2026 describe las bifurcaciones IF para registros válidos e inválidos. Configura los errores de los nodos como Stop Workflow, que, según documenta n8n, detiene la ejecución. Los rechazos por reglas de negocio siguen requiriendo las reglas explícitas anteriores.

Usa Execute step para inspeccionar por separado las salidas de consulta y validación. Compara los resultados con estas comprobaciones de aceptación del ejercicio editorial.

- [ ] Solo Express llega a la salida de registros aptos con payload.apiCode igual a EXP.
- [ ] Economy, Legacy, Broken y Unknown llegan a revisión con ambiguous, expired, invalid_expiry y missing, respectivamente.
- [ ] Blank y Boundary llegan a revisión con invalid_code y expired, respectivamente.
- [ ] Los siete identificadores aparecen exactamente una vez entre ambas salidas; los elementos rechazados no contienen payload ni apiCode.
- [ ] La salida de referencia recuperada conserva ambas filas de Economy y ninguna ruta elude la validación.

## Reflexiona sobre la decisión de correspondencia

Si los resultados difieren, inspecciona la cantidad de filas recuperadas, la agrupación de duplicados, la escritura exacta de las etiquetas y los valores de caducidad analizados. No introduzcas normalización salvo que apliques explícitamente la misma regla a ambos conjuntos de datos.

Explica qué ocurriría si una fila de Economy caducara, pero la otra siguiera vigente. Según las reglas de este ejercicio, primero se cuentan los duplicados, por lo que la correspondencia sigue siendo ambigua. Después, explica por qué elegir la primera coincidencia o proporcionar un código predeterminado incumpliría el contrato.

En nuestra opinión, una tabla de consulta en n8n debería mostrar las decisiones pendientes antes de dejar pasar un payload. Este ejercicio no establece atomicidad con una escritura posterior en la API ni protege frente a cambios en los datos de referencia después de la consulta.
