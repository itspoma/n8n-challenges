## Requisitos previos y objetivo

Este tutorial de reintentos de API en n8n usa el nodo HTTP Request para obtener una respuesta GET paginada, reintentar fallos temporales y escribir registros mediante un identificador estable. Antes de configurarlo, reúne la URL de la API, los datos de autenticación, las reglas de paginación, el límite de tamaño de página, los campos de respuesta y el identificador del registro. La documentación proporcionada no define esos valores específicos de la API, así que usa marcadores hasta consultar su documentación o una respuesta de ejemplo.

Sources: [HTTP Request | Nodes | n8n Docs](<https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.httprequest>), [Work with nodes | Build | n8n Docs](<https://docs.n8n.io/build/understand-workflows/workflow-components/work-with-nodes>), [Data Table | Nodes | n8n Docs](<https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.datatable>)

Puedes seguir los pasos de este tutorial de reintentos de API en n8n en un espacio de trabajo nuevo. Este enlace de socio abre la página de registro de n8n.

## 1. Inspecciona la primera respuesta

![Se inspecciona la respuesta de HTTP Request para identificar sus campos y la regla de paginación.](/blog/es/article-34bbbd28-2034-49ef-a65d-35b1679060f3/531b94163c854628736a0f5352700d9dbf8c949828dae26e8d0ac29f4e7074ec.webp)

La primera respuesta de HTTP Request revela qué regla de paginación configurar.

Añade un nodo HTTP Request y configura el método GET. Haz una solicitud sin paginación e inspecciona el cuerpo, los encabezados y el código de estado devueltos. La documentación de n8n indica que las API tienen reglas de paginación distintas; por eso, antes de configurar el nodo, identifica si esta API proporciona una URL para la página siguiente o espera que cambie un parámetro en cada solicitud.

1. Configura la URL de la solicitud y la autenticación según los requisitos documentados de la API.
2. Ejecuta una solicitud sin paginación.
3. Anota los campos de respuesta, el tamaño de página y la URL de la página siguiente o el parámetro de página.

Sources: [HTTP Request | Nodes | n8n Docs](<https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.httprequest>)

## 2. Configura la paginación y los reintentos de API en n8n

![Los pasos de paginación y reintento de HTTP Request avanzan desde elegir la página hasta una recuperación acotada.](/blog/es/article-34bbbd28-2034-49ef-a65d-35b1679060f3/dd0f2518f547795c33cb2201a5baaad1e8589455e6260dd454a3fd8478646be0.webp)

La paginación, los reintentos finitos y un punto de parada forman la secuencia de configuración de la solicitud.

En el nodo HTTP Request, activa Pagination y elige el modo que corresponda a la API: actualizar un parámetro en cada solicitud o usar una URL de página siguiente obtenida de la respuesta. Usa la expresión y la condición de parada documentadas por la API. n8n expone $pageCount y $response para las expresiones, pero esas variables no indican cómo numera las páginas esta API ni cómo representa el enlace siguiente.

Para los reintentos, [define un límite finito de Retry On Fail](<https://n8n-challenges.app/es/blog/reintentar-de-forma-segura-solicitudes-http-fallidas-en-n8n>) y un tiempo de espera adecuado para la API. La documentación de n8n describe Retry On Fail como la repetición de un nodo tras un fallo; sus indicaciones para HTTP Request señalan Max Tries y Wait Between Tries como controles de reintento. Microsoft Learn identifica las respuestas 429 y 5xx como candidatas habituales a reintentos, considera poco probable que repetir resuelva la mayoría de las respuestas 4xx y recomienda respetar Retry-After cuando se envía. Son pautas HTTP generales; sigue las reglas de la API de destino.

Creemos que la opción predeterminada más segura es mantener explícitos y acotados los ajustes de paginación y reintento, y luego adaptarlos al comportamiento documentado de la API en vez de tratar todos los errores como temporales.

## 3. Actualiza o inserta registros con un identificador estable

![La operación upsert de Data Table actualiza un registro coincidente o crea uno nuevo.](/blog/es/article-34bbbd28-2034-49ef-a65d-35b1679060f3/5fe2b278a62b33b2f433608c2e36966bb9322cfa7df62732686cf77032dbf379.webp)

Los identificadores coincidentes indican a upsert si debe actualizar un registro existente o crear uno nuevo.

Tras obtener los registros, escríbelos en una Data Table con una operación upsert y condiciones de coincidencia basadas en el [identificador estable del registro](<https://n8n-challenges.app/es/blog/prevenir-acciones-api-duplicadas-en-webhooks-de-n8n>) de la API. La documentación de n8n indica que upsert actualiza una fila coincidente o crea una si no existe ninguna coincidencia. Verifica las condiciones de coincidencia antes de confiar en que evitan filas duplicadas; la documentación no garantiza la unicidad.

- [ ] Elige un identificador estable de la respuesta de la API.
- [ ] Configura las condiciones de coincidencia de upsert para usar ese identificador.
- [ ] Verifica que se actualice un registro existente y se cree uno nuevo cuando no haya coincidencias.

Sources: [Data Table | Nodes | n8n Docs](<https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.datatable>)

## 4. Comprueba los resultados y resuelve problemas

![La revisión de una ejecución de n8n muestra el procesamiento repetido y una alerta del flujo de error.](/blog/es/article-34bbbd28-2034-49ef-a65d-35b1679060f3/e4c6ca43f309fce62cc5095183a5f36bd68b57b730b87a4681b94b50551c3ead.webp)

La revisión de la ejecución comprueba si se repiten efectos secundarios y registra los fallos del flujo de trabajo.

Revisa el resultado de la ejecución para comprobar las páginas obtenidas, los elementos devueltos y el estado de error. Si vuelves a intentar un flujo fallido, comprueba si el nodo que falló ya produjo efectos secundarios: la documentación de n8n indica que los reintentos del flujo vuelven a procesar cada elemento en ese nodo, lo que puede repetir efectos anteriores. Un flujo de error puede empezar con Error Trigger y asignarse en los ajustes del flujo para gestionar ejecuciones fallidas; por sí solo, no proporciona una estrategia de repetición automática.
