## Delimita los problemas de MCP en n8n antes de cambiar ajustes

![Un kit de depuración agrupa los detalles de configuración para comprobar MCP Server Trigger de n8n.](/blog/es/article-d716b9ac-1d5f-4090-b264-527ace65062d/a5d2aea976fe990bae209e3bc3dfe0c8f22bdde7aa548d16ede4fec33b3874c8.webp)

Un kit de depuración con compartimentos representa los detalles de configuración que conviene registrar antes de diagnosticar problemas.

¿No funciona MCP en n8n en tu flujo de trabajo? Separa la conexión, el descubrimiento de herramientas y su ejecución. Esta lista se centra en [MCP Server Trigger](<https://n8n-challenges.app/es/blog/n8n-mcp-vs-api-como-elige-una-herramienta-un-agente-de-ia>), que expone herramientas de un único flujo; la configuración de MCP a nivel de instancia es distinta.

Las comprobaciones y los criterios de finalización siguientes son nuestra propuesta para diagnosticar problemas, no normas obligatorias de MCP ni un procedimiento probado. Estas comprobaciones no acreditan la compatibilidad entre versiones de n8n y del cliente; contrástalas con tus versiones instaladas. Empieza registrando la configuración para tener una referencia clara al hacer cambios posteriores.

- [ ] Registra las versiones instaladas de n8n y del cliente.
- [ ] Registra el despliegue y si interviene un proxy inverso.
- [ ] Identifica el flujo de MCP Server Trigger y el tipo de endpoint seleccionado.
- [ ] Registra el transporte previsto y el modo de autenticación sin copiar secretos.

Creemos que el hábito más útil al depurar es identificar el límite en el que se produce el fallo antes de cambiar ajustes. Una herramienta que no aparece y un resultado incorrecto requieren investigaciones diferentes.

## Comprueba la disponibilidad del endpoint, el transporte y la autenticación

![Un conector temporal y otro fijo representan los endpoints de prueba y producción de MCP Server Trigger de n8n.](/blog/es/article-d716b9ac-1d5f-4090-b264-527ace65062d/48c990c623b1c7c8758c0ea0d82b83a8edebcfd09301ccc1eeced520b5fd0952.webp)

Los conectores temporal y fijo ilustran la disponibilidad de los endpoints de prueba y producción; un acoplamiento y una llave representan el transporte y la autenticación.

En un flujo inactivo, n8n registra la URL de prueba de MCP Server Trigger cuando seleccionas Listen for Test Event o Execute workflow. Al publicar se registra la URL de producción.

El trigger admite SSE y HTTP transmisible, pero no stdio directo. Una pasarela que conecta un cliente stdio requiere una configuración aparte. Las opciones de autenticación son None, Bearer auth y Header auth; recomendamos el acceso autenticado para esta comprobación en equipo, aunque no es un requisito universal de la plataforma.

Si MCP en n8n falla al conectar, investiga cada límite por separado en lugar de interpretar cualquier fallo como prueba de un token inválido. Para despliegues con proxy inverso, la comprobación del almacenamiento en búfer que aparece a continuación refleja el requisito documentado de n8n, no una configuración completa del proxy. Utiliza los siguientes criterios de comprobación propuestos.

- [ ] Utiliza la URL de prueba mientras el trigger escucha, o la URL de producción después de publicar.
- [ ] Selecciona explícitamente SSE o HTTP transmisible en el cliente.
- [ ] Haz coincidir la configuración de autenticación del cliente con la del trigger.
- [ ] Si hay un proxy inverso, comprueba el almacenamiento en búfer del endpoint MCP.
- [ ] Da esta etapa por completada cuando el cliente se conecte mediante la configuración prevista.

## Comprueba el descubrimiento con una herramienta mínima de solo lectura

![Una herramienta de diagnóstico conectada se hace visible al comprobar el descubrimiento de MCP en n8n.](/blog/es/article-d716b9ac-1d5f-4090-b264-527ace65062d/5b2705a19e112b32e82d1f7517e2a34eb37e34e408eb63b6937c18a79d784aef.webp)

Una única herramienta en una caja aparece a través de una abertura de observación conectada, ilustrando el descubrimiento de la herramienta mínima de diagnóstico.

Proponemos una configuración de prueba: un flujo de diagnóstico con MCP Server Trigger y una herramienta Code Tool de JavaScript conectada que devuelva una cadena fija, por ejemplo return 'mcp-check-ok';. Excluye las API externas y las operaciones de escritura. La implementación de Code Tool de n8n en la rama master del repositorio describe la salida como una única cadena; este ejemplo no está probado y debe verificarse con tu versión instalada.

La guía del proveedor n8nlogic de marzo de 2026 describe el trigger como un ejecutor de nodos de herramientas conectados, en lugar de un flujo lineal convencional. Usa esa explicación de las conexiones como pista para el diagnóstico: inspecciona la conexión de la herramienta de diagnóstico antes de cambiar su código.

El nodo MCP Client estándar de n8n obtiene automáticamente las herramientas seleccionables del servidor externo. Configúralo para tu endpoint e inspecciona esa lista. El descubrimiento se completa cuando aparece la herramienta de diagnóstico; que sea visible no demuestra que se ejecute correctamente.

En nuestra opinión, una configuración de prueba deliberadamente sencilla es el punto de partida adecuado. Eliminaríamos la lógica de negocio hasta comprender la conexión y el límite de la herramienta.

## Comprueba la llamada y vuelve a recoger las mismas evidencias

![Una herramienta de diagnóstico devuelve una cuenta que se compara con el resultado esperado y se guarda junto con un registro de ejecución.](/blog/es/article-d716b9ac-1d5f-4090-b264-527ace65062d/e0e1d2b5fd3e9d7534ce013ea9aa9042cc7f2a7ca03ca7d0e70155aff0bad9c7.webp)

Las cuentas iguales en una bandeja de evidencias ilustran la comparación entre la salida real y la esperada; un papel sujeto con una pinza representa el registro de ejecución.

¿MCP en n8n sigue sin funcionar aunque el descubrimiento haya tenido éxito? Llama a la herramienta seleccionada con entradas que coincidan con su esquema descubierto. MCP Client de n8n admite parámetros introducidos manualmente o un objeto JSON. Para esta configuración de prueba propuesta, completar la comprobación significa que la respuesta contiene mcp-check-ok y que puedes inspeccionar la ejecución correspondiente.

[Inspecciona las ejecuciones de producción](<https://n8n-challenges.app/es/blog/registros-de-eventos-de-n8n-un-ejercicio-para-rastrear-el-fallo-de-un-flujo-de-trabajo>) en la vista de ejecuciones, en lugar de consultar la salida en directo del lienzo. La vista de ejecuciones permite filtrar las ejecuciones accesibles por flujo, estado y hora de inicio; el acceso depende de los permisos del flujo, y eliminar un flujo borra su historial de ejecuciones. El estado Success por sí solo no demuestra que la salida sea correcta.

Utiliza esta lista propuesta para el traspaso de información después de cada cambio de configuración. Comprueba el límite de respuesta constante, no las API específicas de la aplicación, los permisos de los sistemas posteriores ni la corrección de los datos de negocio, y no ofrece ninguna garantía de fiabilidad.

- [ ] Repite el descubrimiento y la misma llamada a la herramienta.
- [ ] Registra el tipo de endpoint, el transporte, el nombre de la herramienta y las entradas con los datos sensibles ocultos.
- [ ] Registra la salida esperada, la salida real y la marca de tiempo.
- [ ] Adjunta una referencia accesible a la ejecución.
- [ ] Distingue entre fallos de conexión, herramientas ausentes, errores devueltos y salidas incorrectas.
- [ ] Comunica el límite que sigue fallando y el último cambio de configuración.
