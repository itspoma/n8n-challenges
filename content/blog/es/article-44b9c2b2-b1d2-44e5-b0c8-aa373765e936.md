## Objetivo y requisitos previos

La investigación de un token de actualización OAuth en n8n empieza con una credencial correctamente conectada. Este tutorial prepara un flujo HTTP Request fuera de producción para obtener un listado de Google Drive y explica cómo clasificar los fallos de autorización.

Necesitas un espacio de trabajo de n8n, acceso a la configuración de un proyecto de Google Cloud y una cuenta de Google disponible para la autorización. Como precauciones editoriales, sugerimos una cuenta de prueba dedicada y un cliente OAuth personalizado. La documentación no especifica una versión ni una edición de n8n para estas instrucciones de configuración.

Creemos que distinguir explícitamente entre configuración y verificación hace que este ejercicio de preparación resulte más útil.

## 1. Prepara la configuración de autorización de Google

![Dos plantillas de bocallave muestran aberturas alineadas y desalineadas junto a una llave rosa.](/blog/es/article-44b9c2b2-b1d2-44e5-b0c8-aa373765e936/ccdfdd05ac3c360a24d346b5eaa984914fbe01a44199a4b2e6fe34dcf0320900.webp)

Las bocallaves alineadas y desalineadas ilustran el requisito de Google de que el URI de redirección coincida exactamente.

La documentación de configuración de Google de n8n y la documentación de OAuth para servidores web de Google establecen la secuencia de preparación que aparece a continuación. Copia el URI de redirección de la configuración de tu credencial de n8n en lugar de reconstruirlo.

1. Crea o selecciona el proyecto de Google Cloud para la conexión.
2. Habilita la Google Drive API y configura la pantalla de consentimiento OAuth.
3. Crea un cliente OAuth de tipo Web application.
4. Registra exactamente el URI de redirección que muestra n8n, incluidos el esquema, las mayúsculas y minúsculas y la barra final.
5. Si la aplicación está en Testing, añade la cuenta de Google que vayas a usar como usuario de prueba.

Para este ejercicio, sugerimos el ámbito drive.file, que n8n incluye entre los ámbitos compatibles con su credencial Google OAuth2 generic. La guía de autorización de Drive de Google describe este ámbito como acceso a los archivos creados por la aplicación, abiertos con ella o compartidos con ella. No proporciona un inventario de todo el Drive de la cuenta.

## 2. Comprueba la conexión de la credencial del token de actualización OAuth2 en n8n

![Un cable rosa une una cápsula cerrada con un bloque sin marcas que tiene una toma.](/blog/es/article-44b9c2b2-b1d2-44e5-b0c8-aa373765e936/420f84c55ea3ab83efd98242ae358e395d5ebd93b9de454b77caf98b2b46eae9.webp)

Una cápsula cerrada y un bloque conectado ilustran cómo vincular la credencial OAuth guardada al nodo HTTP Request.

Usa la credencial Google OAuth2 generic de n8n para esta conexión. Introduce el ID de cliente y el secreto de cliente de Google, y establece el ámbito drive.file de Google: usa HTTPS con el host www.googleapis.com y la ruta /auth/drive.file. Completa Sign in with Google y guarda. Esta credencial solo admite los ámbitos que enumera n8n; no es intercambiable con una credencial OAuth2 genérica sin restricciones.

Configura el nodo HTTP Request siguiendo estos pasos. En nuestra opinión, seleccionar explícitamente la credencial es un mejor punto de partida que intentar reparar la autenticación añadiendo cabeceras.

1. Establece el método de HTTP Request en GET. Usa HTTPS con el host www.googleapis.com y la ruta /drive/v3/files.
2. Deja vacío el cuerpo de la solicitud.
3. Establece Authentication en Predefined Credential Type, elige Google OAuth2 API como tipo de credencial y selecciona explícitamente la credencial Google OAuth2 generic que guardaste.
4. Mantén los secretos dentro de las credenciales, en lugar de incluirlos en los campos de la solicitud. No los sustituyas por Header Auth con un token de acceso: eso omite la gestión de la actualización OAuth.

## 3. Prepara una comprobación programada y define sus límites

![Un temporizador mecánico rosa está junto a una bandeja de archivos y una separación azul translúcida.](/blog/es/article-44b9c2b2-b1d2-44e5-b0c8-aa373765e936/5a1948637fa88e917460be3bf4ca614962373f3410a77dec5161891748d9ee32.webp)

Un temporizador, una bandeja de archivos y una separación ilustran el ejercicio de listado programado de Google Drive.

Añade un Schedule Trigger, configura sus Trigger Rules y Trigger Interval, y después guarda y publica el flujo preparado. Estas son instrucciones básicas de programación; no establecen la alineación con el reloj ni el comportamiento para recuperar ejecuciones omitidas.

Define el resultado esperado de la API antes de tratar esto como un ejercicio de renovación: la referencia de files.list de Google documenta una respuesta correcta que contiene un array files. Un array vacío puede ser coherente con el acceso drive.file. Las referencias traducidas de Drive que se citan advierten de posibles errores de traducción.

El artículo de n8n de 2026 sobre autenticación de API describe la actualización automática de tokens de acceso OAuth2 para las API que siguen el comportamiento estándar de OAuth2. En una comprobación del token de actualización OAuth en n8n, una solicitud programada correcta por sí sola no permite distinguir entre la renovación y la reutilización de un token de acceso que sigue siendo válido. Este ejercicio prepara la configuración sin verificar la renovación. Como sugerencia editorial, registra categorías de resultados sin datos sensibles, como autorización rechazada o listado devuelto.

## 4. Diagnostica los fallos en el orden correcto

![Un conector, unas bocallaves, una barrera y una cápsula sellada están junto a una mano que coloca una pieza verde con forma de marca de verificación.](/blog/es/article-44b9c2b2-b1d2-44e5-b0c8-aa373765e936/c5cfa7a608963d1d52a15f7e2f3cc87941885f7d23c3ecc5136e155c44bad884.webp)

Un conector, unas bocallaves, una barrera de permisos y una cápsula sellada ilustran las capas que deben inspeccionarse al diagnosticar fallos de OAuth.

Ante un problema con el token de actualización OAuth en n8n, [revisa estas capas antes de cambiar la lógica de negocio del flujo](<https://n8n-challenges.app/es/blog/depura-tus-workflows-de-n8n-antes-de-culpar-a-la-integracion>). Las causas documentadas por Google que aparecen a continuación son puntos de partida para el diagnóstico, no una explicación exhaustiva de los fallos de autorización.

**Comprobaciones para recuperar las credenciales y la autorización**

| Capa | Señal | Corrección |
| --- | --- | --- |
| Conexión del nodo | Authentication establecido en none | Selecciona la autenticación OAuth y la credencial |
| Redirección | redirect_uri_mismatch | Haz que el URI de redirección coincida exactamente con el registrado |
| Consentimiento | Acceso denegado en Testing | Añade el usuario de prueba previsto |
| Cliente | invalid_client | Vuelve a introducir el ID de cliente y el secreto correspondientes |

El ejemplo de Google para servidores web solicita acceso sin conexión para obtener un token de actualización y advierte de que solo se devuelve en la primera autorización. Esto no demuestra que tu credencial de n8n contenga uno. El código fuente de la rama master de n8n, sin fijar una versión concreta, indica que se vuelva a conectar cuando un token de acceso caducado no tenga un token de actualización disponible; las versiones instaladas pueden mostrar un mensaje distinto.

La documentación de OAuth de Google de 2026 indica que las aplicaciones externas en Testing reciben tokens de actualización que caducan a los siete días, salvo cuando los ámbitos se limitan a los ámbitos de identidad que especifica. La revocación y las políticas de la organización también pueden provocar fallos de actualización. Evitaríamos diagnosticar la causa únicamente a partir del tiempo transcurrido.
