## Requisitos previos y el objetivo: enrutar cada elemento a un lugar visible

Este tutorial sigue las prácticas de la documentación del nodo Switch de n8n para mostrar cómo enrutar elementos hacia la rama correcta de un workflow, y cómo evitar que los elementos que no coinciden con nada desaparezcan en silencio. Antes de empezar, necesitas un workflow de n8n existente que ya produzca elementos que quieras dividir de forma condicional, por ejemplo registros obtenidos con un nodo HTTP Request, un trigger o un paso de transformación anterior. También necesitas una idea aproximada de las condiciones que deben separar una rama de otra, como un campo de estado, un valor de categoría o un umbral numérico.

El objetivo es sencillo de enunciar pero fácil de hacer mal: cada elemento debe llegar a la rama que coincide con sus datos, y cualquier elemento que no coincida con ninguna de tus reglas debe seguir siendo visible dentro del workflow, no descartarse silenciosamente. Como explica la documentación oficial, el comportamiento predeterminado del nodo Switch para los elementos sin coincidencia es ignorarlos, que es exactamente el fallo que este tutorial te ayuda a evitar. La documentación oficial del nodo Switch citada a lo largo de este tutorial no lleva número de versión, por lo que el comportamiento de Mode y Fallback Output descrito a continuación refleja la documentación publicada actualmente y puede variar ligeramente entre versiones de n8n.

## Configurar el nodo Switch de n8n: Modo, reglas y Fallback Output

![Un diagrama de vías ferroviarias que se ramifican, ilustrando las reglas de enrutamiento de la documentación del nodo Switch de n8n, con una ruta de fallback separada.](/blog/es/article-fb7e0789-2f09-4ee0-80a5-4bc869a9b6e1/cca493a649de8115ed3e75d484318ebb917a2cb45fb5f34fa005762936aaa747.png)

Un esquema conceptual de reglas de enrutamiento que alimentan ramas separadas, con una vía de fallback distinta para los elementos sin coincidencia.

Configurar el nodo empieza con una única decisión descrita en la documentación del nodo Switch de n8n: elegir el Modo del nodo. El modo Rules te permite construir un enrutamiento basado en condiciones a través del editor, comparando un tipo de dato y un valor para cada output; esto se adapta a la mayoría de la lógica de ramificación donde las condiciones son suficientemente estáticas como para expresarse como comparaciones. El modo Expression, en cambio, enruta elementos de forma programática, permitiéndote calcular el output de destino con una expresión, lo cual se adapta a los casos en que el destino depende de una lógica que una comparación simple no puede capturar. Este tutorial se centra en el modo Rules porque es donde ocurre el fallo de elementos que se cuelan sin coincidir, descrito más abajo.

En el modo Rules, cada ruta de output se define creando una regla de enrutamiento: una comparación entre un tipo de dato elegido y una condición, una regla por cada rama que quieras crear. Añade una regla de enrutamiento por cada destino distinto al que puedan llegar tus elementos, manteniendo cada regla específica para la rama que alimenta. Escribir una regla manual pensada para capturar todo lo demás puede fallar en silencio en lugar de capturar algo, como explican las secciones de Resultados esperados y Solución de problemas más abajo.

**Configuración del enrutamiento del nodo Switch**

1. **Elegir el Modo**: Selecciona el modo Rules para ramas basadas en condiciones o el modo Expression para un enrutamiento programático.
2. **Añadir reglas de enrutamiento**: Crea una regla por cada output, comparando un tipo de dato y un valor para cada rama que necesites.
3. **Configurar el Fallback Output**: Dirige los elementos sin coincidencia a Extra Output u Output 0 en lugar de dejar la configuración predeterminada None.

## Resultados esperados cuando el nodo Switch está configurado correctamente

Con las reglas de enrutamiento en su lugar y el Fallback Output configurado en Extra Output u Output 0 en lugar de dejarlo en el valor predeterminado, los elementos que coinciden con una regla viajan a la rama de esa regla, y los elementos que no coinciden con ninguna viajan a la rama de fallback, donde puedes inspeccionarlos, registrarlos o generar alertas sobre ellos. Dejado en la configuración predeterminada None, los elementos sin coincidencia simplemente se ignoran: sin rama, sin error, nada aguas abajo que los detecte. Un informe de un foro comunitario de 2026 describe exactamente ese hueco: un workflow de bot de Telegram donde [los mensajes de texto libre que no coincidían con ninguna regla simplemente desaparecían](<https://n8n-challenges.app/es/blog/rastrear-errores-de-vinculacion-de-items-en-n8n-por-que-falla-item-y-como-solucionarlo>), sin ninguna ejecución fallida que señalara el problema.

La solución reportada en ese mismo caso fue dejar de depender de una regla manual y en su lugar usar la opción de fallback incorporada del nodo Switch configurada en el modo de output extra, lo que produjo un output extra automático que capturaba todo lo que las reglas de enrutamiento se dejaban escapar. Trata esto como el relato de un profesional y no como una solución garantizada para todos los workflows, pero coincide con el comportamiento documentado de la configuración de fallback.

## Solución de problemas: encontrar elementos que desaparecen sin error

![Un elemento perdido cayendo por un hueco junto a una rampa que atrapa sin problemas ese mismo elemento en una bandeja visible.](/blog/es/article-fb7e0789-2f09-4ee0-80a5-4bc869a9b6e1/a837a94cfb3a78f9cc8d78b3e3b91ef247ae02fec65e85ad6c4a3ac9856154c7.png)

Un contraste conceptual entre una regla manual que lo captura todo y puede fallar, y un output de fallback incorporado que sí captura los elementos.

Si los elementos parecen desaparecer en algún punto dentro de un nodo Switch y ninguna ejecución falla, una causa común es el comportamiento de fallback predeterminado, que descarta los elementos sin coincidencia en lugar de generar un error. La lección del informe comunitario descrito arriba —revisar la configuración de Fallback Output en lugar de depender de una regla manual que lo capture todo— es lo primero fiable que hay que comprobar cuando esto ocurre.

Dos comprobaciones ayudan a confirmarlo y solucionarlo:

- Abre las opciones del nodo y confirma que Fallback Output está configurado en Extra Output u Output 0, y no dejado en la configuración predeterminada None.
- Revisa cualquier regla escrita para "capturar todo lo demás"; es fácil que en la práctica una regla así no capture nada, como describe el informe comunitario.
