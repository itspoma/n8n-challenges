## Lista de comprobación: identificar las dependencias de seguridad de red de n8n

Antes de cambiar las reglas de seguridad de red de n8n, registra qué conexiones necesita tu [despliegue autoalojado](<https://n8n-challenges.app/es/blog/lista-de-comprobacion-para-preparar-n8n-autoalojado-para-produccion>). n8n identifica los cortafuegos de infraestructura, los grupos de seguridad y las políticas de red como la principal defensa de red. Consideramos que un inventario de conexiones revisado es un mejor punto de partida que un conjunto de reglas copiado.

Esta es una lista de verificación editorial, no una norma de cumplimiento, un conjunto completo de reglas de cortafuegos ni un tutorial de despliegue. Los puertos, selectores, destinos y rutas del proxy concretos deben obtenerse de tu despliegue. Empieza en un despliegue de práctica aislado con las mismas versiones y topología que producción; utiliza las siguientes comprobaciones sugeridas para definir cuándo dar la revisión por completada.

- [ ] Registra la versión instalada de n8n, la topología del despliegue y la versión del chart de Helm, cuando corresponda.
- [ ] Haz un inventario de los clientes que necesitan acceso entrante, los destinos de API salientes y las conexiones con DNS, la base de datos y Redis.
- [ ] Revisa por separado los procesadores dedicados de webhooks, los task runners, el almacenamiento opcional y las conexiones multi-main, si existen.
- [ ] Asigna a cada restricción propuesta un responsable, un resultado esperado, un resultado observado y una acción de reversión.

Sources: [n8n-docs/docs/deploy/host-n8n/configure-n8n/security/enable-ssrf-protection.md at main · n8n-io/n8n-docs · GitHub](<https://github.com/n8n-io/n8n-docs/blob/main/docs/deploy/host-n8n/configure-n8n/security/enable-ssrf-protection.md>)

## Lista de comprobación: mantener el acceso entrante de webhooks a través del proxy

n8n atribuye a quienes lo autoalojan la responsabilidad de gestionar TLS mediante un proxy inverso. Su documentación sobre proxy inverso utiliza N8N_WEBHOOK_URL para la dirección pública de los webhooks; WEBHOOK_URL está obsoleta desde n8n 2.35.0. Comprueba la versión instalada antes de modificar un despliegue antiguo.

La configuración de proxy documentada especifica N8N_PROXY_HOPS=1 y las cabeceras X-Forwarded-For, X-Forwarded-Host y X-Forwarded-Proto. Ese número de saltos corresponde a la configuración documentada. Utiliza estas comprobaciones sugeridas para completar la revisión del tráfico entrante.

- [ ] Verifica la gestión de TLS y la dirección pública anunciada para los webhooks.
- [ ] Ajusta la configuración de saltos de proxy y las cabeceras reenviadas a la cadena de proxies desplegada.
- [ ] Envía un webhook representativo que deba funcionar por la ruta pública restringida y confirma que se ejecuta el flujo previsto.

Sources: [n8n-docs/docs/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/configure-webhook-urls-with-reverse-proxy.md at main · n8n-io/n8n-docs · GitHub](<https://github.com/n8n-io/n8n-docs/blob/main/docs/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/configure-webhook-urls-with-reverse-proxy.md>), [Security](<https://n8n.io/legal/security/>)

## Lista de comprobación: conservar las conexiones de infraestructura del modo de cola

La documentación del chart oficial de Helm de n8n indica que el [modo de cola](<https://n8n-challenges.app/es/blog/n8n-queue-mode-con-redis-cuando-dejar-el-modo-de-instancia-unica>) requiere PostgreSQL y Redis externos. Describe workers que consumen trabajos de Redis, en lugar de recibir tráfico HTTP entrante de los flujos. La documentación citada cubre una versión en evolución: main describe el chart 2.0 como una versión candidata, mientras que el chart 1.x instala n8n 2.x. Contrasta estas afirmaciones con la versión del chart que tengas instalada.

Para ese chart documentado, el estado de preparación de los workers depende de la conectividad con la base de datos, las migraciones y Redis. Un fallo de preparación es una señal para investigar, no una prueba de un problema de cortafuegos. Las siguientes comprobaciones sugeridas vinculan el acceso a las dependencias con una ejecución observable.

- [ ] Conserva las conexiones necesarias con PostgreSQL y Redis para la topología instalada.
- [ ] Revisa el acceso a las comprobaciones de estado de los workers por separado del tráfico entrante de los flujos.
- [ ] Ejecuta un trabajo representativo activado por webhook y confirma tanto su ejecución en un worker como un estado de preparación correcto.

Sources: [n8n-hosting/charts/n8n/README.md at main · n8n-io/n8n-hosting · GitHub](<https://github.com/n8n-io/n8n-hosting/blob/main/charts/n8n/README.md>)

## Lista de comprobación: restringir el tráfico saliente y revisar las excepciones de SSRF

En n8n autoalojado, la protección contra SSRF está disponible desde la versión 2.12.0. En esa función documentada, las listas de nombres de host permitidos omiten las comprobaciones de la lista de IP bloqueadas. Esto describe el comportamiento de la aplicación, no el del cortafuegos de infraestructura.

En nuestra opinión, las excepciones de nombres de host merecen el mismo escrutinio que los nuevos permisos de salida. Para revisar la seguridad de red de n8n, examina la configuración real de la aplicación junto con las restricciones de infraestructura mediante estas comprobaciones sugeridas.

- [ ] Confirma si la versión desplegada admite protección contra SSRF y comprueba si está activada.
- [ ] Vincula cada excepción de nombre de host con una integración necesaria y un responsable identificado.
- [ ] Prueba destinos de API representativos que deban funcionar con las restricciones propuestas.

Sources: [n8n-docs/docs/deploy/host-n8n/configure-n8n/security/enable-ssrf-protection.md at main · n8n-io/n8n-docs · GitHub](<https://github.com/n8n-io/n8n-docs/blob/main/docs/deploy/host-n8n/configure-n8n/security/enable-ssrf-protection.md>)

## Lista de comprobación: verificar la aplicación de políticas en Kubernetes y el DNS

Kubernetes aplica NetworkPolicy mediante un complemento de red compatible. Las políticas aplicables suman sus permisos, por lo que una nueva política restrictiva no anula permisos más amplios de otra política. Denegar todo el tráfico saliente por defecto también bloquea el DNS.

En los despliegues de Kubernetes, completar la revisión significa observar en la práctica los permisos previstos. Estas comprobaciones sugeridas se centran en la aplicación de las políticas y en la ruta real de resolución de nombres del despliegue.

- [ ] Verifica que el complemento de red instalado aplica NetworkPolicy.
- [ ] Examina todas las políticas que seleccionan los pods de n8n para detectar permisos superpuestos.
- [ ] Identifica los destinos DNS necesarios y verifica la resolución de nombres con la política de salida propuesta.

Sources: [Network Policies | Kubernetes](<https://kubernetes.io/docs/concepts/services-networking/network-policies/>)
