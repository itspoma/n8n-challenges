## Decide primero: aprobación nativa de SAP o externa

Un flujo de aprobación SAP no tiene por qué vivir en n8n. SAP S/4HANA Cloud Public Edition tiene un flujo de trabajo flexible nativo para solicitudes de pedido, y el guion de pruebas de buenas prácticas de SAP para un scope item (versión 2608) comprueba que hay un flujo basado en escenarios activo para el tipo de documento NB. Cualquier diseño externo debe tenerlo en cuenta.

Nuestra recomendación es editorial, no una regla documentada: usa n8n solo para aprobadores o canales a los que SAP no llega, como aprobadores externos o aprobación por chat. En nuestra opinión, añadir un segundo motor de aprobación junto a uno nativo que funciona suele crear más confusión que comodidad.

Además, hay una pregunta abierta que conviene conocer antes de construir. Un hilo de SAP Community de julio de 2026 preguntaba si una API estándar puede activar el flujo de aprobación de la solicitud de pedido. La única respuesta fue una opinión de foro sin verificar y sin solución aceptada. Sugería una comprobación con BAdI o retener la solicitud en una app externa, y advertía de que SAP no tendría visibilidad hasta que se envíen los datos.

Sources: [Check Flexible Workflow for Purchase Requisitions Approval | SAP Help Portal](<https://help.sap.com/docs/s4hana-cloud-best-practices/procurement-of-production-components-consumer-products-5w3-my/check-flexible-workflow-for-purchase-requisitions-approval?version=2608>), [API or Business Object to Trigger Purchase Requisi... - SAP Community](<https://community.sap.com/t5/enterprise-resource-planning-q-a/api-or-business-object-to-trigger-purchase-requisition-approval-workflow-in/qaq-p/14432117>)

## Pausar y reanudar en n8n

![Lista de comprobación junto a un candado y un reloj que muestra una URL de reanudación protegida del nodo Wait con tiempo límite en n8n](/blog/es/article-cd6b7a7e-e2d6-42e6-b947-292830b5138f/e9f0ae2acd4c87931ae8c79106f8e5c72272b84036f15c56ab823c29196973cd.webp)

Una lista de comprobación junto a un candado y un reloj, que muestra las salvaguardas del paso de reanudación del nodo Wait.

El nodo Wait de n8n pausa una ejecución y traslada sus datos de ejecución a la base de datos, según la documentación de n8n. Puede reanudarse tras un intervalo de tiempo, a una hora fija, con una llamada a un webhook o con el envío de un formulario. La página de documentación no indica versión y no trata SAP.

En el modo On Webhook Call, n8n genera una URL de reanudación por ejecución que puedes enviar a un servicio de terceros o por correo. Puede protegerse con autenticación Basic, Header o JWT. La documentación advierte de que las ejecuciones parciales cambian la URL de reanudación, así que prueba en ejecuciones completas.

El nodo Wait también puede limitar el tiempo de espera para que el flujo se reanude solo, y puede restringir quién llama mediante una lista de IP permitidas, devolviendo 403 a los demás. La documentación no prescribe una política de tiempo límite de aprobación, así que los cuatro primeros puntos de la lista siguiente son sugerencias editoriales para un flujo de aprobación SAP; el último es una advertencia documentada de n8n.

- [ ] Protege la URL de reanudación con autenticación Header o JWT
- [ ] Añade una lista de IP permitidas para los llamantes
- [ ] Define un límite de espera con escalado o parada segura como alternativa
- [ ] No apruebes automáticamente por tiempo agotado en objetos financieros
- [ ] Prueba en ejecuciones completas, no parciales

En nuestra opinión, una URL de reanudación protegida con Header o JWT más una lista de IP permitidas es el mínimo para cualquier cosa que toque finanzas.

Sources: [Wait | Nodes | n8n Docs](<https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.wait>)

## Configuración del flujo de aprobación SAP: acceso y escritura

![Piezas encajadas de usuario de comunicación, sistema y acuerdo usadas para el acceso OData de SAP S/4HANA](/blog/es/article-cd6b7a7e-e2d6-42e6-b947-292830b5138f/0f2b58257e00dda1f37e4b9e74f59e18eb43599209de1a7379076e20cbd89d96.webp)

Piezas encajadas que muestran cómo se combinan usuario de comunicación, sistema y acuerdo para el acceso a la API.

SAP S/4HANA Cloud Public Edition (documentación de la versión 2608) ofrece APIs OData V2 y V4 y SOAP, que se pueden descubrir en SAP Business Accelerator Hub. El acceso se configura mediante escenarios y acuerdos de comunicación. Un ejemplo de SAP para otro escenario, SAP_COM_0837, muestra la secuencia de usuario de comunicación, sistema y acuerdo, y señala que una URL de endpoint incorrecta provoca un fallo de autenticación. Solo muestra el patrón; los roles difieren según el escenario.

Los métodos de autenticación incluyen Basic, x509, OAuth2 y SAML SSO, pero cada API admite unos distintos, así que consulta la API concreta en el Hub. En n8n, el nodo HTTP Request recomienda tipos de credencial predefinidos cuando existen, con credenciales genéricas Basic, Header y OAuth2 para otras APIs. Que las credenciales de cliente (client credentials) sirvan para tu acuerdo depende del propio acuerdo.

Antes de construir, confirma que tu objeto tiene una operación de aprobar o rechazar publicada. El listado de 2608 muestra Approve y Reject para Purchase Contracts (Version 2) y para Service Entry Sheets (Lean Services), pero el texto truncado no indica si son OData. Para las solicitudes de pedido muestra una API V4 con lectura, actualización y validación, y la API V2 como obsoleta.

Ninguna fuente oficial de SAP aportada muestra una operación OData publicada para aprobar o rechazar una solicitud de pedido desde fuera de SAP, así que este artículo no afirma que exista. Nada de esto se probó de primera mano y varias páginas de ayuda de SAP están truncadas. Consulta el Hub para tu propio objeto.

## Escribe la decisión de vuelta con seguridad

![Secuencia de obtención de un token CSRF, lectura de un ETag y envío de una actualización OData desde n8n](/blog/es/article-cd6b7a7e-e2d6-42e6-b947-292830b5138f/b46e30474d75271b7cff445f50f0443d6bc65b4f7b628a9d274b509d5f52de67.webp)

Una secuencia de izquierda a derecha de los pasos de escritura: token, lectura, actualización.

Las llamadas que modifican datos, como POST, necesitan un [token CSRF](<https://n8n-challenges.app/es/blog/gestion-de-tokens-csrf-en-n8n-prepara-una-escritura-en-un-entorno-de-pruebas-de-sap-gateway>) en S/4HANA Cloud Public Edition (2608). El cliente lo obtiene con una llamada no modificadora que envía la cabecera X-CSRF-Token con el valor Fetch, y luego lo reutiliza en la petición modificadora. La página de SAP está escrita para otro servicio, así que no cubre el manejo específico de n8n.

Las actualizaciones usan [concurrencia optimista con ETags](<https://n8n-challenges.app/es/blog/gestion-de-etag-en-sap-odata-un-ejercicio-editorial-en-n8n-antes-de-reintentar>). El cliente debe enviar el ETag recibido anteriormente, y si no coincide se devuelve un error y no se cambia nada. La lista general de errores de SAP incluye 403 Forbidden, 412 Precondition Failed (el recurso cambió, vuelve a leer) y 428 Precondition Required (envía una cabecera if-match). No se indica si una API de aprobación concreta necesita un ETag.

Como secuencia editorial, los pasos siguientes trasladan esos comportamientos a la escritura de vuelta en n8n.

## Gestión de errores, idempotencia y alternativa

Una demo de la comunidad de SAP Inside Track Ankara 2026, publicada en un repositorio comunitario de GitHub, muestra el patrón general: un webhook CAP hacia n8n, un umbral IF, envío y espera por Telegram, y luego aprobar o rechazar escribiendo de vuelta mediante acciones OData V4. Usó un mock CAP local con n8n 2.x, no S/4HANA, así que solo demuestra el patrón. El autor describe el webhook como fire-and-forget y las acciones como idempotentes.

La misma demo señala que SAP no depende de n8n: los pedidos se crean aunque n8n esté caído, con el estado en pendiente, y un flujo de errores avisa de los fallos. Ninguna fuente oficial indica cómo S/4HANA Cloud Public Edition entrega a n8n un evento de aprobación saliente, así que ese disparador sigue siendo un punto abierto.

Como sugerencia editorial, mantén el paso de escritura de vuelta reejecutable. En 412, vuelve a leer el objeto y reintenta una vez; en 403, detente y avisa en lugar de reintentar. En nuestra opinión, un flujo con Error Trigger debería existir antes de la primera aprobación en producción, no después del primer fallo.

Sources: [GitHub - gzmilgar/sap_n8n: SAP CAP + n8n live demo: order approval loop with Telegram human-in-the-loop and an AI agent over OData (SAP Inside Track Ankara 2026) · GitHub](<https://github.com/gzmilgar/sap_n8n>), [APIs on SAP Business Accelerator Hub | SAP Help Portal](<https://help.sap.com/docs/SAP_S4HANA_CLOUD/0f69f8fb28ac4bf48d2b57b9637e81fa/1e60f14bdc224c2c975c8fa8bcfd7f3f.html>)

## Gobernanza y auditoría

![Insignia de usuario técnico genérico comparada con un libro de registro solo-añadir de aprobadores con nombre para aprobaciones SAP](/blog/es/article-cd6b7a7e-e2d6-42e6-b947-292830b5138f/b1dd82b733fadc5dadf4a14db15b74b3232033bc8ecfba21b59ea9c97ccf90e1.webp)

Una insignia genérica frente a un libro de firmas con nombre, que contrasta un usuario técnico con un aprobador humano registrado.

El usuario técnico es lo que SAP verá. Un blog de SAP Community de 2025 sobre SAP Build Process Automation, que no es OData de S/4HANA, indica que llamar a una API de finalización de tareas con credenciales de cliente muestra el formulario como aprobado por un usuario genérico basado en el ID de cliente. Tómalo como una advertencia sobre la atribución cuando uses credenciales de servicio.

Un blog de SAP Community de 2026 escrito por un SAP AI Solution Architect sobre agentes con intervención humana recomienda entradas de auditoría que registren entradas, razonamiento, decisión, revisor y objetos SAP afectados, conservadas en modo solo-añadir. También dice que nunca debe usarse como alternativa por tiempo agotado el continuar en contabilizaciones financieras. Es la opinión de diseño de un autor para otra pila, no un estándar de SAP.

No se aportaron requisitos de auditoría específicos de SAP, así que el resto es editorial: usa un usuario de comunicación dedicado por escenario en lugar de un usuario de diálogo compartido, y registra al aprobador humano en los datos de ejecución de n8n y en un registro aparte de solo-añadir.

## Diseño recomendado y puntos abiertos

Nuestro diseño sugerido de flujo de aprobación SAP: confirma que el flujo nativo no encaja, lee el objeto desde SAP, pausa en el nodo Wait con una URL de reanudación autenticada y un tiempo límite, y luego obtén el token CSRF, lee el ETag y escribe la decisión de vuelta. Pruébalo primero en un tenant que no sea de producción.

Puntos abiertos que debes resolver en tu tenant: si tu objeto tiene una operación de aprobar o rechazar publicada (consulta la sección de configuración), qué método de autenticación admite esa API y cómo llega a n8n la solicitud de aprobación.
