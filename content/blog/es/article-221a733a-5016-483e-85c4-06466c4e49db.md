## Tu tarea de pruebas de contratos de API y sus límites

Este ejercicio editorial utiliza pruebas de contratos de API para responder a una pregunta concreta: ¿contiene una respuesta controlada los campos que necesita la escritura propuesta? Crea tres nodos Code llamados Mock response, Check contract y Simulated write. Tu tarea consiste en dejar que las respuestas compatibles lleguen a un marcador de escritura y detener las incompatibles antes de que lo alcancen.

Los requisitos previos son un flujo de desarrollo editable en n8n y conocimientos básicos de JavaScript. n8n documenta la generación de datos de prueba con nodos Code o Edit Fields. Utiliza únicamente datos sintéticos: sin credenciales, solicitudes a API externas ni escrituras reales. La documentación proporcionada no especifica ninguna versión ni edición de n8n, por lo que no establece una compatibilidad universal con todos los entornos de ejecución o planes.

Los casos de prueba, el algoritmo y los resultados esperados que aparecen a continuación son material didáctico propuesto, no un flujo ejecutado ni validado. Son aserciones de JavaScript escritas a mano, no JSON Schema ni un contrato dirigido por el consumidor y verificado por el proveedor. La gestión de estados HTTP, la infraestructura de regresión, la reversión de cambios y el despliegue en producción quedan fuera de este ejercicio.

## Prepara un ejemplo de pruebas de contratos de API

![Casos de prueba de respuestas correctas e incompatibles representados por objetos que encajan o no en cajas de muestras.](/blog/es/article-221a733a-5016-483e-85c4-06466c4e49db/a137f5b94d56ab303f88e885329ee2c28347ed75a4efc813fd548e57411be293.webp)

El contraste entre las cajas de muestras representa casos de prueba de respuestas sintéticas compatibles e incompatibles.

Utiliza una estructura envolvente definida para este ejercicio que contenga fixtureName y body. En Mock response, devuelve un caso de prueba por ejecución como un array que contenga un objeto cuya propiedad json almacene esa estructura. n8n exige que json tenga un objeto como valor dentro de su estructura de array de elementos; un envoltorio correcto no valida por sí solo la respuesta que contiene.

El contrato de éxito propuesto exige que body sea un objeto que no sea null ni un array, con las propiedades propias id de tipo string y amount de tipo number. Permite campos adicionales no relacionados y no conviertas los tipos de los valores. Creemos que un contrato útil para practicar debe expresar lo que necesita el consumidor, en lugar de fijar todos los campos que el proveedor devuelva en ese momento.

Utiliza estos casos de prueba sugeridos. Asigna a fixtureName el nombre de su fila; la tabla muestra el valor de body y el resultado propuesto.

## Construye la comprobación del contrato antes del marcador

![Mock response, Check contract y Simulated write representados por tres estaciones físicas.](/blog/es/article-221a733a-5016-483e-85c4-06466c4e49db/fd6af1075c872ef3736fd006162989a4dcf2f134d87b0742c87e15fe11ca4f5f.webp)

Las tres estaciones representan la secuencia propuesta de simulación, validación y marcador.

Configura Check contract en Run Once for All Items y lee const items = $input.all(). n8n documenta este modo y este método de acceso a los datos de entrada. Implementa el siguiente algoritmo sugerido, examinando todos los elementos antes de devolver nada.

1. Recorre items y lee json.fixtureName y json.body de cada elemento.
2. Rechaza body cuando sea null, typeof body no sea "object" o Array.isArray(body) sea true.
3. Si Object.hasOwn(body, "error"), exige que error sea un objeto que no sea null ni un array. Exige que sus propiedades propias code y message tengan typeof "string".
4. Para los objetos de error mal formados, lanza new Error con el nombre del caso de prueba, "Contract error" y el campo que ha fallado. Si la estructura del error es válida, lanza un "Upstream error" que contenga el nombre del caso de prueba y error.code.
5. En caso contrario, exige Object.hasOwn(body, "id") y typeof body.id === "string"; exige Object.hasOwn(body, "amount") y typeof body.amount === "number". Lanza un error de contrato descriptivo si falla cualquiera de estas comprobaciones.
6. Devuelve items solo después de que termine todo el bucle. No devuelvas los elementos aceptados desde dentro del bucle.

Object.hasOwn() distingue una propiedad propia de una ausente o heredada; aun así, hay que comprobar su valor. En JavaScript, typeof indica que tanto null como los arrays son objetos, así que exclúyelos explícitamente. Confirma que Object.hasOwn() esté disponible en tu entorno de ejecución.

Configura la opción On Error del validador en Stop Workflow: n8n documenta que impide la ejecución de los siguientes nodos tras un error. Continue, en cambio, continúa con los últimos datos válidos. Detener el flujo no deshace escrituras anteriores, por eso este ejercicio sitúa el marcador después de la validación.

## Ejecuta cada caso por separado y registra las evidencias de finalización

![Un único caso de prueba de respuesta entra en un dispositivo de pruebas junto a un cuaderno para registrar las observaciones de la ejecución.](/blog/es/article-221a733a-5016-483e-85c4-06466c4e49db/4b203c78ea9da1e82fe2c7aedb722e900d7af2e351751532dafe3d23a0fe7131.webp)

Probar un caso cada vez facilita registrar su diagnóstico y observar si se alcanza el marcador.

En Simulated write, utiliza $input.all().map(item => ({json: {wouldWrite: true, id: item.json.body.id}})) como valor de retorno. Este marcador es únicamente un recurso del ejercicio. Ejecuta la secuencia completa por separado para cada caso de prueba y registra el diagnóstico observado y si se ejecutó el nodo marcador.

Utiliza la siguiente lista como criterios de finalización sugeridos para las pruebas de contratos de API. A nuestro juicio, la observación decisiva es si la ejecución llega al marcador después de un rechazo; un mensaje de error legible no basta.

- [ ] Completa un registro de observaciones para cada caso de prueba, con su diagnóstico y si se ejecutó Simulated write.
- [ ] Compara cada resultado registrado con la tabla de casos de prueba.
- [ ] Confirma en la ejecución actual de cada caso rechazado que nunca llegó a Simulated write.

Si aparece un marcador inesperado, revisa la opción On Error del validador y comprueba que lance el error antes de devolver datos. Si falla la salida de Code, revisa el envoltorio de array y que json tenga un objeto como valor. Si se aceptan null o arrays, revisa las comprobaciones de body en lugar de confiar solo en typeof.

## Reflexiona sobre lo que demuestra superar las pruebas simuladas

Para este ejercicio de pruebas de contratos de API, la solución sugerida consiste en validar todos los datos de entrada y, después, pasar a un nodo marcador independiente. Reflexiona sobre por qué se permite un campo adicional, por qué un error bien formado del servicio de origen sigue bloqueando el marcador y qué campos obligatorios necesitaría tu consumidor real.

Superar estas pruebas simuladas no demuestra que un proveedor real siga cumpliendo el contrato. El artículo Contract Test de Martin Fowler, publicado en 2011, distingue entre probar con un doble de prueba y comprobar si el servicio externo se ajusta a él. Trata los resultados registrados como evidencia sobre estos casos de prueba y esta configuración del flujo.

Sources: [Contract Test](<https://martinfowler.com/bliki/ContractTest.html>)
