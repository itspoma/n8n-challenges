## Dos direcciones de la integración de n8n con MCP: servidor o cliente

Una integración de n8n con MCP puede funcionar en dos direcciones, y confundirlas es la fuente de confusión más común cuando intentas conectar por primera vez un asistente de IA a n8n. En una dirección, n8n actúa como servidor MCP: un workflow expone sus propias herramientas para que un asistente de IA externo pueda llamarlas. En la otra dirección, n8n actúa como cliente MCP: un AI Agent dentro de n8n llama a herramientas expuestas por el servidor MCP de otra persona.

La dirección de servidor se apoya en el nodo MCP Server Trigger, que convierte un workflow en un servidor MCP para que asistentes de IA externos puedan llamar a las herramientas que expone. A diferencia de un trigger normal, que pasa el control al siguiente nodo en línea, este trigger solo se conecta y ejecuta los nodos de herramienta conectados a él, así que cada capacidad a la que quieras que el asistente acceda debe cablearse explícitamente.

La dirección de cliente utiliza el [nodo MCP Client Tool](<https://n8n-challenges.app/es/blog/cliente-mcp-en-n8n-conecta-claude-o-chatgpt-de-forma-segura>), que permite que un AI Agent construido dentro de n8n use herramientas expuestas por un servidor MCP externo, lo inverso de la configuración anterior. Este tutorial se centra en la dirección de servidor, ya que es lo que permite que un asistente externo como Claude u otro chatbot vea y actúe sobre un workflow de n8n.

## Requisitos previos

Antes de conectar nada, comprueba que tu configuración cumple algunos requisitos documentados por el propio n8n. Equivocarse en esto es la razón más común por la que un intento de conexión se estanca antes de empezar.

- [ ] Un workflow de n8n con una tarea que quieras que un asistente llame como herramienta
- [ ] El nodo MCP Server Trigger disponible en tu instancia de n8n
- [ ] Un cliente de asistente de IA que hable streamable HTTP o SSE, ya que el trigger no admite transporte stdio
- [ ] Una forma de autenticar la conexión, ya que el endpoint del trigger necesita credenciales configuradas
- [ ] Nodos de herramienta listos para conectarse al trigger, ya que solo ejecuta los nodos de herramienta conectados

Sources: [MCP Server Trigger | Nodes | n8n Docs](<https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.mcptrigger>)

## Objetivo y pasos: exponer un workflow mediante MCP Server Trigger

![Una secuencia de nodos conectados muestra la integración de n8n con MCP exponiendo las herramientas de un workflow a un asistente de chat.](/blog/es/article-1aacee72-c4aa-4547-8754-16f3898c4061/5d79416f804ecc3aff71ae36c63bdaba3f628a38c4556d06363074ee6102117c.png)

Una ilustración conceptual de los pasos para exponer las herramientas de un workflow mediante el nodo MCP Server Trigger.

El objetivo de este tutorial es concreto y acotado: exponer un workflow de n8n a un asistente de IA para que pueda llamarlo como herramienta, usando el nodo MCP Server Trigger. Los pasos siguientes siguen la forma de una integración de n8n con MCP tal como la describe la propia documentación de n8n.

**Exponer un workflow mediante MCP Server Trigger**

1. **Añade el trigger**: Coloca un nodo MCP Server Trigger en el workflow que quieres exponer.
2. **Conecta los nodos de herramienta**: Cablea los nodos de herramienta específicos al trigger, ya que solo ejecuta los nodos conectados a él y no un paso lineal siguiente.
3. **Configura la autenticación**: Configura las credenciales que exigirá el endpoint del trigger antes de aceptar llamadas.
4. **Copia la URL de producción**: Toma la dirección del endpoint que expone el trigger una vez que el workflow está activo.
5. **Configura el cliente**: Apunta la configuración del cliente MCP del asistente de IA a esa URL mediante streamable HTTP o SSE, no stdio.
6. **Prueba una llamada a una herramienta**: Pide al asistente que llame a una herramienta expuesta y confirma que el workflow se ejecuta.

Sources: [MCP Server Trigger | Nodes | n8n Docs](<https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.mcptrigger>)

## Resultado esperado y solución de problemas

Una vez configurado, llamar a una herramienta desde el asistente debería activar el workflow conectado, ejecutar solo los nodos de herramienta cableados al MCP Server Trigger, y devolver su salida al asistente como respuesta de la herramienta. Si llega una llamada pero no ocurre nada, probablemente el nodo de herramienta en cuestión no está realmente conectado al trigger.

La mayoría de los problemas iniciales se deben al transporte o al cableado, no a la autenticación. El soporte de n8n para MCP en este trigger solo cubre streamable HTTP y SSE, así que una librería cliente que use stdio por defecto no podrá conectarse, sin importar cómo se configuren las credenciales.

- El cliente no puede conectarse en absoluto: confirma que usa streamable HTTP o SSE, ya que stdio no es compatible
- La llamada a la herramienta tiene éxito pero no devuelve nada: comprueba que el nodo de herramienta esté realmente conectado al MCP Server Trigger
- El asistente no ve una herramienta que esperabas: recuerda que solo se ejecutan los nodos de herramienta conectados, a diferencia de un trigger lineal
- La conexión se corta a mitad de la llamada: revisa la URL del endpoint y la autenticación configurada en el trigger

Sources: [MCP Server Trigger | Nodes | n8n Docs](<https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.mcptrigger>)

Cuando un equipo entero, no solo el chatbot de una persona, empieza a llamar a workflows de n8n a través de MCP, las preguntas pasan de cablear un trigger a gobernar el acceso. ## Qué cambia cuando un equipo comparte el acceso MCP en lugar del chatbot de una sola persona

![Un solo candado junto a un llavero compartido con varias etiquetas muestra el acceso de una persona frente al acceso MCP compartido de un equipo.](/blog/es/article-1aacee72-c4aa-4547-8754-16f3898c4061/71a73a905c88977bde11a09b564f662bffcae9a825b7b9d3221b2798914a8cd7.png)

Una ilustración conceptual que contrasta el acceso MCP privado de una persona con el acceso compartido a nivel de instancia de un equipo.

Un único MCP Server Trigger expone las herramientas de un workflow. Conectarse al servidor MCP de n8n de esta forma es distinto a habilitar el acceso MCP a nivel de instancia, donde los workflows habilitados de toda una instancia quedan accesibles para cualquier cliente conectado a la vez.

Con el acceso a nivel de instancia, cada cliente conectado puede ver todos los workflows habilitados para MCP; no hay forma de restringir workflows específicos a clientes específicos. Un administrador puede revisar y revocar el acceso de un cliente concreto sin desactivar MCP para todos, algo que importa en cuanto más de una persona llama a la misma instancia.

Compartir una credencial para uso en equipo comparte el registro de la credencial, no una sesión en vivo: cada miembro del equipo sigue conectándose con su propia cuenta en lugar de tomar prestada la de otro. Ese tipo de compartición de credenciales de equipo está disponible en todos los planes de n8n Cloud, pero solo en los [planes autoalojados Business o Enterprise](<https://n8n-challenges.app/es/blog/precios-enterprise-de-n8n-vs-community-que-queda-restringido>).

La visibilidad sobre quién hizo qué también cambia con la escala. Transmitir registros y eventos de auditoría a una herramienta de monitorización externa es una función Enterprise tanto en Cloud como en n8n autoalojado, y los eventos de auditoría MCP dedicados, incluido un registro de qué cliente llamó a qué herramienta, solo existen a partir de la versión 2.34.0 de n8n.

**Trigger de un solo workflow frente a acceso MCP a nivel de instancia**

| Dimensión | MCP Server Trigger individual | Acceso MCP a nivel de instancia |
| --- | --- | --- |
| Alcance | Las herramientas conectadas de un workflow | Todo workflow habilitado para MCP en la instancia |
| Restricción de cliente | Limitado a lo que ese trigger expone | Sin restricción por cliente entre los workflows habilitados |
| Revocación | No documentado | El administrador puede revocar el acceso de un cliente concreto |
| Detalle de auditoría | No documentado para el trigger por sí solo | Eventos de llamada a herramientas MCP desde n8n 2.34.0 con streaming de registros Enterprise |

Sources: [Connect to n8n MCP server | Connect | n8n Docs](<https://docs.n8n.io/connect/connect-to-n8n-mcp-server>), [Share credentials securely | Administer | n8n Docs](<https://docs.n8n.io/administer/manage-credentials/share-credentials-securely>), [Stream logs to external systems | Administer | n8n Docs](<https://docs.n8n.io/administer/observe-and-log/stream-logs-to-external-systems>)

## Una alternativa de terceros: n8n-mcp

Fuera del propio producto de n8n, algunos desarrolladores informan que usan un proyecto independiente y mantenido por la comunidad llamado [n8n-mcp](<https://n8n-challenges.app/es/blog/proyecto-de-github-del-servidor-mcp-de-n8n-frente-a-las-opciones-mcp-integradas-de-n8n>), que su creador describe como un puente que da a los asistentes de IA acceso a nivel de documentación a los nodos de n8n, distinto de los propios nodos MCP Server Trigger y MCP Client Tool de n8n.

La propia documentación del proyecto incluye una advertencia de seguridad muy directa: nunca dejes que un asistente de IA edite workflows de producción directamente a través de él. Esa precaución importa para cualquier integración de n8n con MCP construida con herramientas de terceros, oficiales o no.

El creador también ha compartido un ejemplo autoinformado de antes y después sobre la velocidad de construcción de workflows en el foro de la comunidad de n8n, describiendo una gran ganancia personal de productividad. Esa cifra proviene del relato de un solo desarrollador sobre un caso individual, no de una comparación medida de forma independiente, así que debe leerse como un informe personal y no como un resultado documentado.

Esa descripción proviene de la misma publicación del foro de la comunidad de n8n donde el creador presentó el proyecto, junto con las instrucciones de configuración para conectarlo a Claude Desktop.

## Recomendaciones editoriales

Estas son sugerencias para valorar junto a tu propia configuración, no una lista de verificación validada ni un procedimiento garantizado.

- [ ] Empieza con el MCP Server Trigger de un solo workflow antes de considerar el acceso a nivel de instancia, ya que es más fácil de acotar y razonar
- [ ] Antes de habilitar más workflows de los previstos, revisa el comportamiento de 'todos los clientes ven todos los workflows habilitados' con quien gestione las decisiones de seguridad o plataforma
- [ ] Si tu plan incluye el streaming de registros Enterprise, activa los eventos de auditoría MCP desde el principio en lugar de esperar a que aparezca un problema
- [ ] Trata cualquier servidor MCP de terceros para n8n como un proyecto separado de los propios nodos de n8n, y lee sus propias advertencias de seguridad antes de apuntarlo a producción
- [ ] Pide a quien lidere este despliegue para un equipo que investigue la formación oficial AI Agents with n8n de n8n en lugar de depender solo de la configuración de chatbot personal de una persona
